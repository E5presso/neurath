# Task ledger integration

The new ledger is composed by `transport.core_requests.build_task_ledger(path)` over the same user-wide database as `build_core(path)`. Explicit initialization upgrades core schema `core_0001` to `core_0002`; requests never initialize storage or migrate original legacy databases.

- `record_source` preserves the supplied text, reference, author and optional parent source. `request` and `correction` can define work; `question` and recalled `context` cannot. Attribution is metadata, not a human-authentication gate. An existing project source can be reused by another session.
- `create_task` creates a pending obligation. `revise_task` targets only that task, appends its definition history and checks the expected task revision. A correction can invalidate cancelled work. Old definitions, sources and attempt results remain readable through `history` and `get_source`.
- `start_task` checks dependencies and returns `(task, attempt)`. A retry of failed work preserves the same task and creates another attempt. Returning from an external wait reuses the outstanding attempt rather than resubmitting the external operation.
- `report_result` records an observed submission, success, failure or partial result with artifact/command/review references. Submission leaves the task active. Failure or partial completion requires remaining work or a concrete blocker and leaves the obligation retryable. A final attempt cannot be resolved twice. Results for an old definition are retained without completing a revised or cancelled task.
- `add_dependency` rejects cross-project references and cycles. `wait_for_external` requires a target, observed evidence and resolution condition; `resolve_external` requires an observation of resolution. These APIs record caller-observed conditions; they do not independently prove a remote fact. Independent tasks remain ready. Monitoring and notifications belong to the later monitoring adapter.
- `list_tasks(project_id, session_id)` returns the full ledger with `ready_ids` and a derived `todo` view. `all_terminal` includes failed and invalidated records; `all_successful` includes only succeeded records. An empty list satisfies both predicates. Neither is a complete Stop implementation. TODO rendering cannot mutate task results.

The ledger cannot verify artifact semantics from a reference string. Host adapters must supply actual execution results, and the phase runner must enforce the selected procedure, including evaluation, before applying its final result. Runner, hooks, evaluator and CLI wiring are separate implementation tickets; this API adds no public command or automatic polling.
