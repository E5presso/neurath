# 결과 평가·선택 회고·교훈

[English](../en/result-evaluation.md) · [단계 실행](workflow-runner.md) · [수용 기준](acceptance.md)

#138은 기존 `WorkflowRun`의 평가 phase, `Delegation`의 실제 독립 보고, `Task`의 외부 대기와 성공 보고를 연결합니다. 별도 평가 태스크·승인 원장·토큰을 만들지 않습니다. `workflow start/report/revise`와 `collaboration delegate/observe`가 실제 호스트 흐름으로 연결하며 원문·TODO·현재 후보를 함께 확인합니다.

## 실행과 보고 수용

`PhaseDefinition.evaluation`에 `EvaluationTarget`을 지정합니다. `RESULT`는 사용자 결과 평가이며 생략 조건을 허용하지 않습니다. `REFLECTION`은 사용자 요청 때만 활성화하는 선택 분기입니다. 대상은 기존 `target_revision`, 관련 `task_ids`, 실제 `artifacts`와 `verification` 참조로 구성합니다. 연결 태스크는 항상 관련 범위에 포함됩니다.

1. `GetEvaluationUseCase`는 조건·범위와 현재 후보를 조회합니다. TODO에 아직 연결되지 않은 원문을 포함한 원문·정정 이력, 같은 세션의 전체 TODO, 실제 산출물·검증 참조를 함께 구성합니다. 전체 TODO에는 성공·실패·미완료 상태가 그대로 포함됩니다.
2. `RequestEvaluationUseCase`는 현재 평가 순서·회고 선택과 지원 모델·정책을 확인합니다. 기존 `PrepareDelegationUseCase`로 검토 배정을 준비하고 `BindEvaluationUseCase`로 phase 시도와 외부 대기를 커밋한 다음 기존 피어·네이티브 자식·provider 경로를 사용합니다. 외부 실행 중 DB 쓰기 잠금을 유지하지 않습니다.
3. 피어·자식은 기존 수락·보고 경로로 원 보고를 제출합니다. provider는 실제 완료 상태·네이티브 세션·출력·실행 참조가 모두 있어야 합니다. 요청·전달·실패·결과 불명은 성공한 보고가 아닙니다.
4. `ConsumeEvaluationUseCase`는 저장된 실제 보고와 현재 후보를 대조합니다. 실행자가 원문·증거에 근거한 수용 또는 기각 이유를 남깁니다. 오판은 근거와 함께 기각할 수 있고, 보고의 제안 자체를 새로운 사용자 지시로 승격하지 않습니다.
5. 확인된 미달은 같은 태스크 목록의 기존 작업 또는 원래 출처를 사용하는 후속 작업에 반영합니다. 관련 수행 단계를 기존 절차 개정으로 다시 열고 변경된 결과를 평가합니다. 평가가 성공하기 전에는 `ReportResultUseCase`가 연결 작업의 성공을 거절합니다. 평가자가 태스크를 직접 성공시키지 않습니다.

수신자·역할·범위·경로·후보가 같은 요청은 기존 배정을 재사용합니다. 다른 검토자·범위는 별도 정당한 요청이며, 종료를 확인한 실패·완료 배정은 `--retry-of`로 명시적으로 다시 평가할 수 있습니다. 대기·실패를 조회한다고 새로운 모델 실행을 만들지 않습니다. 평가 배정은 다시 평가자를 재귀 위임할 수 없습니다. 후보가 바뀐 대기 시도는 실패 이력으로 보존하고 새 후보를 연결하며 원 배정·늦은 보고는 삭제하지 않습니다. 사용자가 취소하거나 요구를 정정하면 기존 협업 취소 경계가 적용됩니다.

## 관련 변경의 대조

`SQLAlchemyEvaluationContextService`는 관련 작업 정의·원 출처·명시한 대상·산출물·검증 자료로 후보 지문을 만듭니다. 전체 TODO를 검토자에게 보여 주되 무관한 작업의 상태 변경이나 평가 기록 자체를 지문에 넣지 않습니다.

`GitEvaluationArtifactService`는 지정한 로컬 파일의 실제 내용 해시를 읽습니다. 상대 경로는 phase의 작업 폴더를 기준으로 하고 `file:` 절대 경로도 지원합니다. PR 검토처럼 현재 HEAD가 관련 대상이면 참조에 `git:HEAD`를 명시합니다. 선택하지 않은 HEAD·파일의 변경은 평가를 무효화하지 않습니다. `artifact:...`처럼 외부 참조를 사용할 때는 호출자가 현재 산출물을 식별하는 불변 개정 참조를 제공해야 합니다. 외부 URL의 내용을 자동 다운로드하거나 외부 게시 권한을 부여하지 않습니다.

보고 수용과 최종 태스크 성공 전에 현재 후보를 다시 대조합니다. 따라서 평가 후 로컬 산출물·선택한 HEAD·관련 요구가 변경되면 이전 평가로 완료할 수 없습니다. 원 보고의 조회·내부 수용과 외부 게시 권한은 별개이며 게시 자체는 사용자 권한 범위의 호스트 도구가 담당합니다.

## 종료와 회고 선택

Stop은 기존 최신 태스크 원장을 결정론적으로 검사합니다. 결과 평가 대기는 해당 `Task`의 외부 대기이며 정상 성공과 구분해 제어권을 반환합니다. Stop에 모델 호출이나 별도 완료 투표를 추가하지 않습니다. 새로운 미완료 TODO, 실패·대기, 오래된 턴과 실제 취소는 기존 런타임 계약을 유지합니다.

`ChooseReflectionUseCase`는 `WorkflowRun`에 제안·요청·거절·무응답과 실제 발화 또는 문제 근거를 보존합니다. 문제가 있으면 한 번 제안하고, 이미 요청했다면 다시 확인하지 않습니다. 미요청·제안만 한 상태·거절·무응답의 회고 단계는 원 작업 완료를 막지 않습니다. 요청 또는 일반 수락 후에만 같은 독립 평가 경로가 활성화됩니다. 사용자용 승인 객체나 전용 토큰은 없습니다.

요청한 회고도 철회할 수 있습니다. 기존 회고 배정의 중단 요청과 관련 대기 해소를 연결하며 늦은 보고가 철회한 분기를 완료시키지 못합니다. 실제 파일·Git 관찰은 DB 읽기 트랜잭션 밖에서 수행하고, 저장 직전에 원장 개정과 후보를 다시 대조합니다.

## 교훈의 수명

성공한 현재 회고 평가와 사용자 요청이 있을 때만 `CreateLessonUseCase`가 출처 있는 `MemoryKind.LESSON`을 생성합니다. `ObserveLessonUseCase`는 같은 프로젝트의 후속 세션에서도 관찰을 추가할 수 있습니다.

- `PROPOSED`: 개선 후보와 적용 범위를 보존하며 아직 적용하지 않습니다.
- `VALIDATED`: 원 실패 사례 개선과 정상 대조의 근거를 모두 요구합니다.
- `APPLIED`: 검증 이후 실제 적용 관찰을 남깁니다. 실제 효과의 미확인·성공·실패를 구분합니다.
- `DEFERRED`: 이유와 미적용 상태를 보존합니다. 보류를 성공으로 승격하지 않습니다.
- `WITHDRAWN`: 뒤의 실패·악화에 해당 교훈의 철회를 연결합니다. 과거 효과를 덮어쓰지 않습니다.

`memory propose-lesson`은 요청된 독립 회고에서 후보를 저장하고 `memory observe-lesson`은 실제 검증·적용·철회 효과를 기록합니다. `memory search/read`는 종류·교훈 상태로 조회하며 적용된 프로젝트 교훈은 다음 시작·압축 복원에 현재 지시보다 낮은 과거 맥락으로 포함됩니다. 적용 관찰은 호스트에서 실제 수행한 변경·검사의 근거를 기록하는 계약이며, 저장 자체가 사용자 규칙·목표·권한을 변경하거나 파일을 자동 편집하지는 않습니다.

## 보존과 검증 경계

`core_0013`은 기존 배정을 빈 후보로 유지하고 후보별 유일성, phase의 배정 연결, 회고 선택, 교훈 이력만 추가합니다. 이전 원문·태스크·배정·보고의 ID와 외래 키를 보존합니다. 새 평가·회고·교훈 자료를 잃는 downgrade는 거절합니다.

`tests/test_evaluation.py`와 `tests/test_evaluation_domain.py`는 공통 pre-commit과 CI에서 실행합니다. 원문·TODO 전달, 실제 subprocess fixture 출력, 현재 후보 수용, 중복 방지, 미달 보완, 오판 검토, 관련 변경, 선택 회고, 교훈 검증·철회, 결정론적 Stop과 실제 migration 경계를 검사합니다. 기존 runtime·협업·provider 시험은 취소·미확인·재개·수신·저장 실패 경계를 계속 검사합니다.

격리 subprocess와 프로토콜 fixture는 실제 모델의 의미 판단이나 운영 호스트 활성화를 입증하지 않습니다. 이번 변경에서는 사용자 설치·운영 DB를 수정하지 않으며, 설치된 모델 목록 조회와 모델 평가 실행을 구분합니다.

배정·phase 커밋 직후 전달 전에 중단되면 같은 요청으로 최초 전달을 이어갑니다. 이미 전달하거나 실행 요청한 배정은 다시 제출하지 않습니다. 교훈 효과 기록에는 표준 낙관적 revision을 적용해 오래된 동시 저장으로 이력을 잃지 않습니다. 평가 목적·검사 조건 변경도 관련 후보 변경에 포함됩니다.
