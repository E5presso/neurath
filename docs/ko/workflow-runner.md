# Workflow runner

[English](../en/workflow-runner.md)

새 코어의 workflow runner는 태스크 원장 위에서 #141을 구현합니다. 내부 Python 유스케이스 API이며 CLI, 런타임 훅, provider 어댑터와 독립 평가 정책은 별도 티켓입니다. 설치된 0.3.1 런타임을 활성화하지 않습니다.

`transport.core_requests.build_workflow_runner(path)`는 stateless `WorkflowRunner`를 구성합니다. 명시적인 `CoreDatabase.initialize()`가 새 코어 스키마를 `core_0002`에서 `core_0003`으로 이전하며 일반 요청은 이전하지 않습니다. 기존 식별 정보·원문·미완료 태스크를 보존하고 원본 legacy DB는 열지 않습니다.

## 정의와 실행

`Definition`은 이름·버전·원래 목적·필수 입력·순서 있는 `Phase`를 고정합니다. 각 phase는 동작을 대상과 대상 리비전, 결과 조건, 필요한 경우 지정 검토자, 의존 단계, 조건부 입력, 실행·재시도 제한에 연결합니다. 대상 리비전은 실제 산출물 digest나 Git 리비전처럼 호스트가 관측해 제공하며 관련 대상 변경 시 갱신해야 합니다.

`start(project_id, task_id, definition=..., inputs=..., expected_task_revision=...)`가 정의를 고정하고 run을 반환합니다. `current`와 `history`는 조회만 합니다. run에서 현재 phase·입력·조건·상태·이유·시도 횟수를 확인할 수 있습니다. 선택한 절차가 미완료이면 기존 태스크 결과 경로에서 성공 처리할 수 없습니다.

`dispatch(..., phase_id=..., expected_revision=..., host=...)`는 시도를 저장하고 트랜잭션을 종료한 다음 `ExecutionHost.execute`를 호출합니다. `report_result(..., attempt_id=..., observation=...)`는 관측 결과를 중복 제거하고 현재 시도·세대·대상 리비전이 맞을 때만 진행합니다. 성공 결과는 모든 조건과 설정된 검토자를 만족해야 합니다. 실패한 검토는 결함과 수정 내용을 보존합니다. 최대 시도와 반복 무진전 제한으로 검토 루프를 유한하게 유지합니다. 절차 종결은 자동으로 중복 없이 반영하며 사용자 목표 성공은 태스크 결과 유스케이스에서 판단합니다.

호스트 프로토콜은 `execute`, `lookup`, `notify`와 명시적인 `deduplicates` 기능을 갖습니다. 네이티브 실행 권한은 호스트 책임입니다. Provider 또는 네이티브 도구 어댑터가 동작을 수행하거나 검토자에게 위임하고 실제 관측 근거를 반환할 수 있습니다. 검토자 이름은 일반적인 발신 맥락이며 인증·승인 체계가 아닙니다.

`CommandHost(directory)`는 셸 보간 없이 argv를 실행합니다. 출력을 계속 소비하면서 설정된 앞부분만 보존하고 실제 제한 시간과 `threading.Event` 취소를 처리하며 중단 시 프로세스 그룹을 종료하고 종료 결과를 보고합니다. 기계적 `execution` 조건만 제공하며 의미 검토를 만들지 않습니다. 알림은 기본적으로 stderr에 실제 출력하거나 주입된 전달 함수를 사용합니다. 알림 실패는 대기 결과 저장 이후 예외로 드러납니다.

## 복구와 정정

Dispatch 응답이 유실되면 해당 시도는 대기로 남습니다. `reconcile(..., attempt_id=..., host=...)`가 먼저 같은 결과를 조회합니다. 어댑터가 중복 제거를 보장할 때만 동일한 외부 요청 키를 재사용합니다. 조회와 보장된 중복 제거가 없으면 결과 불명을 저장하고 알림을 전달하며 변경을 무조건 반복하지 않습니다. 로컬 명령 어댑터는 영속 외부 영수증이나 중복 제거가 없으므로 재시작 중 유실된 프로세스는 외부에서 확인한 관측을 `report_result`로 전달해야 합니다.

실패하거나 교체된 시도의 늦은 결과는 이력으로 보존하며 새 시도를 완료시키지 않습니다. 태스크 정정이 아직 조정되지 않았을 때 받은 결과는 미적용 상태로 남습니다. 관련 없는 정정을 조정한 뒤에는 같은 관측 결과를 현재 시도에 적용할 수 있으며 다시 실행하지 않습니다.

`revise(..., definition=..., inputs=..., reason=..., correction_source_id=None, invalidate=())`는 이전 정의와 결과를 보존합니다. 방법 수정은 원래 목표와 필수 조건을 유지하며 범위 변경은 태스크에 이미 반영한 현재 정정을 참조합니다. 변경한 phase 계약과 명시된 의존 단계만 무효화하며 나머지 유효 근거를 유지합니다. 입력 변경은 보수적으로 모든 phase를 무효화합니다. 대상 식별자가 같더라도 관련 실패가 발생했다면 `invalidate`로 해당 근거를 명시적으로 무효화합니다. 영향을 받는 미확인 외부 변경은 정의 변경 전에 조정해야 합니다. 방법 수정으로 소진한 재시도 예산을 초기화할 수 없습니다.

`skip`은 현재 선택 단계 또는 정의의 입력 조건이 거짓인 분기에 이유를 기록합니다. 필수 범위를 없애려면 실제 정정이 필요합니다. `yield_run`은 실제 중단 이유를 남기고 `resume`은 같은 run과 미완료 시도를 유지합니다. 이 API는 수명주기 상태를 기록하며 네이티브 제어권 반환과 소유권 검사는 런타임 티켓 #142에서 연결해야 합니다.

## 검증 경계

시험은 임시 SQLite와 실제 로컬 하위 프로세스를 사용합니다. 필수 단계 보존·실패/재시도·조건부 생략·유실 응답 조회와 알림·실행 제한·관련 근거 무효화·늦은 결과·유한 검토 회차·스키마 이전을 확인합니다. 설치된 호스트의 활성화, 실제 provider 전달, 독립 평가자의 품질이나 릴리스 준비를 증명하지 않습니다.
