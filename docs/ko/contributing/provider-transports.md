# 프로바이더 세션과 네이티브 전송

[English](../../en/contributing/provider-transports.md) · **한국어**

[기여 안내](index.md) · [에이전트 협업](agents-reference.md) · [작업 도구](task-tools.md)

[협업 계약](collaboration-contract.md)은 프로바이더 중립 권한 승계, 프로세스 수명과
at-least-once 전달을 정의합니다. [모델 계획](model-planning-mcp.md)은 새 작업 전 모델 선택을
정의합니다. 이 문서는 현재 소스 구현을 설명하며, 설치된 Codex·Claude의 실제
호스트 수용 검증은 소스·스키마 검사와 별도로 수행합니다.

## 실행 경로

프로바이더는 모델 서비스를 선택하고, 전송 계층은 네이티브 실행을 생성·메시징·중단하는
연결을 소유합니다. 최초 루트는 Codex와 Claude 모두 가능합니다. 한 프로바이더 인스턴스의
세션·네이티브 서브에이전트는 해당 프로바이더가 지원하는 내부 통신을 사용합니다. 인스턴스 간
메시지는 Neurath가 담당합니다. 앱 프로젝트 소속, 원격 관측과 사용자 접속은 실행 전제나
완료 기준이 아닙니다.

| 경로 | 현재 구현 | 경계 |
| --- | --- | --- |
| Codex app-server | 소유 세션 생성·조회·시작·조향·중단과 기록된 세션 복원 | 실행 프로세스가 소유한 JSON-RPC 연결. 다른 실행 중 클라이언트에 붙지 않음 |
| Claude Agent SDK | 소유 비동기 클라이언트, 응답 스트림, 순차 query·중단과 기록된 세션 복원 | 요청 옵션, 네이티브 모드와 실제 준비 상태는 별도 관측 |
| 기존 앱·네이티브 동료 도구 | 호스트가 반환한 정확한 도구·수신자를 발견해 사용 | 선택적 경로. 경로 제안은 전달이나 권한 승계가 아님 |
| 제한된 CLI 호환 실행 | 짧은 읽기 전용 구 실행과 해당 실행의 상태·취소·후속 처리 | 일반 세션 실행 경로나 에이전트용 MCP 대체 수단이 아님 |
| Claude Desktop/Cowork | 외부 수명 관리 어댑터 없음 | UI 제공만으로 호출 가능한 네이티브 실행 연결이 생기지 않음 |

Codex 어댑터는 명시한 네이티브 프로젝트 ID를 검증하고 생성 응답도 확인합니다.
ID를 생략하면 저장된 프로젝트를 필수로 요구하지 않습니다. 선택적인 앱 준비 경로는
앱 프로젝트 ID를 사용할 수 있지만, 그 메타데이터로
네이티브 정책을 증명하거나 일반 프로바이더 실행에 앱 소속을 요구하지 않습니다. 앱 DB 편집,
신원 합성, 경쟁 연결에서 실행 중 세션을 resume하는 방식은 사용하지 않습니다.

## 모델 계획과 권한 승계

`provider_models`, `provider_plan`, `provider_plan_read`로 관측된 목록과 선택 계획을 다룹니다.
`provider_run`은 계획 ID·revision, 작업 revision, 정확한 모델 또는 계획된 상속, 추론 설정과
안정적인 실행 키를 소비합니다. dispatcher는 영속 접수 전에 현재 작업·정책·목록과 계획을
대조하고 본 작업 전에 실제 모델을 비교합니다. 모델 변경에는 새 계획 revision이 필요하며
조용한 대체는 하지 않습니다. 요청·준비·관측·접수는 서로 다른 상태입니다.

모델 목록에는 프로바이더별 제약이 있습니다. Codex는 네이티브 어댑터를 사용하고, Claude는
기존 설정을 보존한 짧은 공식 SDK 제어 연결에서 모델 질의 없이 메타데이터를 조회합니다.
제어 프로세스는 부모의 신원 환경 변수를 제거합니다. 목록 응답이 인증·추론 성공이나 설정된
기본값을 증명하지는 않습니다. 유지보수 선택은 [작업 도구](task-tools.md)의 정확한 질문과
네이티브 사용자 응답 결속을 사용합니다.

`provider_run`의 기본값은 `mode="inherit"`입니다. worktree·assignment가 있고 명시적인 요청
정책이 없으면 `provider_route`도 상속 경로를 제안합니다. 루트가 Claude인 경우를 포함해
바로 위 생성자의 현재 네이티브 정책을 기준으로 삼습니다. 명시적인 모드·정책 필드는 상속과
대조하며 권한을 몰래 넓히는 입력이 아닙니다.

Codex의 승인 정책·검토자·협업 모드·네이티브 sandbox 필드는 각각 유지합니다. 같은 프로바이더는
관측된 정책을 보존합니다. 현재 교차 프로바이더 대응은 알려진 제한을 보존할 수 있을 때
폭넓은 무인 승인(`never`·`danger-full-access`·Plan이 아닌 협업 모드 또는 Claude
`bypassPermissions`)을 지원합니다. 다른 조합은 모드 별칭을 추측하지 않고 지원하지 못하는
항목을 정확히 반환합니다.

Claude는 `plan`, `dontAsk`, `default`, `acceptEdits`, `auto`, `bypassPermissions`를 받습니다.
`dontAsk`는 기존에 허용되지 않은 도구의 권한을 만들지 않습니다. 폭넓은 승인도 명시적 deny,
훅, worktree 소유권을 없애지 않습니다. Claude 요청에 Codex 정책 필드를 혼용하지 않습니다.
Plan·읽기 전용 관측은 구현 권한이 아닙니다.

네이티브 모드, 설정 파일에서 발견한 후보, 실제 로드가 확인된 설정을 구분합니다. 파일 후보는
메모리 override의 증명이 아닙니다. 정확한 네이티브 관측이 있으면 우선 사용하고, 알려진 규칙,
훅 차이와 설정 제한을 보존합니다. OS 실행 환경의 제한은 `unobserved`를 포함해 별도로 보고합니다.
SDK sandbox 비활성화는 OS 무제한 접근 증명이 아닙니다. 대응 결과는 준비이며 실제 적용
증명이 아닙니다. MCP 직접 실행의 더 좁은 지원 범위는 [작업 도구](task-tools.md)에 설명합니다.

## 준비 상태와 프로세스 수명

본 구현 전에 설치 배포·배치, 네이티브 활성화, 현재 정책, 활성 worktree claim을 각각 확인합니다.
새 worktree에 Git에서 제외된 설치 파일이 있다고 가정하지 않습니다. 발행자가 설치를 준비하고
준비 결과를 읽습니다. 준비 진단은 다른 에이전트의 claim이나 독립 검토자 권한을 부여하지 않습니다.

Claude는 준비 응답의 네이티브 Result와 스트림 종료를 모두 확인한 뒤 본 작업을 별도 query로
전달합니다. 전달 직전에 소유 SDK 연결의 제어 요청과 네이티브 상태 조회로 같은 세션,
프롬프트 세대, 권한, 설치, claim이 유지됐는지 확인합니다. 준비 턴이 닫혔다면 다음 입력을
받을 준비가 된 소유 세션으로 구분하며, 닫힌 턴을 active라고 표시하지 않습니다.

영속 접수는 모델 작업이 끝나기 전에 실행 ID를 반환합니다. 분리된 실행 프로세스는 네이티브
이벤트를 받아 발행자에게 접수·시작·대기·오류·연결 종료·취소·완료를 보고합니다. 네이티브 턴
종료는 작업 효과의 증명이 아닙니다. 발행자가 본문을 읽고 다음 행동을 책임집니다.

일반 프로바이더 작업에는 수명 timeout이 없습니다. 개별 연결·쓰기·응답에는 제한 시간이
있을 수 있습니다. 이벤트 처리 중에도 메시지·취소 경로를 사용할 수 있습니다. `provider_status`는
기록된 이벤트나 실패를 진단하며 완료 폴링에 쓰지 않습니다. `provider_cancel`은 취소를 요청하고
실제 네이티브 결과 보고가 그 결과를 확인합니다.

위임 작업이나 미확인 메시지가 남으면 턴이 끝나도 발행자의 소유 연결을 유지합니다.
Codex 발행자가 idle이면 같은 연결에서 새 턴을 시작하고 active이면 실제 턴 ID로 조향합니다.
Claude는 같은 SDK 클라이언트를 사용하되 응답 중 도착한 알림을 영속 보관하고, Result와
응답 스트림이 끝난 뒤 다음 query로 전달합니다. 응답 중 입력 쓰기를 별도 턴 접수로 세지
않습니다. heartbeat, 주기적 완료 조회, 별도 수신 LLM을
만들지 않습니다. 종료 중인 연결에 늦게 온 알림은 복구 대상으로 남으며 이미 시작한 입력
쓰기는 닫기 전에 마칩니다. 다른 인스턴스의 승인된 작업을 발행자 종료만으로 취소하지 않습니다.

## 영속 전달과 재처리

메시지를 커밋한 뒤 알립니다. 메시지의 식별자·내용을 유지하며 재전달에도 같은 키를 사용합니다.
수신자는 `collaboration_message` 또는 인증된 전체 본문 조회로 읽은 뒤 `collaboration_ack`나
`collaboration_reply`를 사용합니다. ID만 담긴 알림은 본문 수신이 아닙니다. ACK는 수신 확인이며
작업 수락·완료가 아닙니다. LLM은 반복 키를 식별할 수 있지만 작업 효과의 exactly-once는 보장하지 않습니다.

소유 전달 서비스는 ACK 없는 `queued`·`submitted` 메시지를 보존합니다. 실패·불확실·중단된
전달 시도도 복구 가능합니다. DB 변경·네이티브 준비 이벤트, 등록, 메시지별 재시도 기한이
전달을 유발합니다. backoff는 빈도를 제한하며 메시지 수명을 제한하지 않습니다. 승인·입력
대기는 관련 준비 이벤트를 기다리고, 일시적인 연결 부재는 메시지별 backoff로 재시도합니다. endpoint generation과
소유 lease로 이전 전달 시도의 늦은 결과를 제한합니다.

TTL·대화 예산은 새 메시지를 제한할 수 있지만 이미 접수된 대기 메시지를 버리지 않습니다.
`collaboration_close`는 대기 메시지가 있으면 이를 반환하며 몰래 닫지 않습니다.
Newsroom은 별도의 일시적인 active 동료 피드로 유지합니다.

`delivery_status(message_id)`는 참여자에게 메시지 상태, 최근 전달 시도와 복구 보류를 반환합니다.
`delivery_redrive(message_id, expected_revision, repair_reference, key)`는 복구된 기존 보류를
해제해 다시 시도하게 합니다. 현재 분류는 `envelope-version`과 `recipient-binding`입니다.
재처리는 복구 참조를 기록하고 수신자·본문·키를 유지하며 소유 전송 경로가 여전히 검증합니다.
권한을 새로 부여하거나 작업 효과를 재실행하지 않습니다. 복구 참조 자체가 원인 해결의 증명은 아닙니다.

## 프로바이더 프로세스 복구

`provider_recover(run_id, key)`는 현재 발행자가 소유한 기록된 실행을 다룹니다. 접수 전에
이전 worker generation, 저장된 네이티브 세션, 확인된 프로세스·연결 종료가 필요합니다.
OS가 유지하는 worker lease로 경쟁 복구를 막고 명시적으로 취소된 실행은 되살리지 않습니다.
같은 복구 키는 기존 접수를 재사용하며 새 논리적 실행을 만들지 않습니다.

복구 worker는 소유 연결로 기록된 네이티브 세션을 복원하고 정책·정상 준비 상태를 확인한 뒤
전달을 다시 연결합니다. 수신 프로세스가 죽었다는 이유로 원래 작업을 재실행하지 않습니다.
`recovery-accepted`는 접수이며 실행 복원이나 수신 성공이 아닙니다. 종료 근거가 없거나 네이티브
세션을 복원할 수 없으면 정확한 차단 결과와 기존 상태를 보존합니다. 모든 급작스러운 종료나
저장소 손실을 자동 복구한다고 보장하지 않습니다.

Desktop이 소유한 대화의 자동 재개에는 해당 소유 연결의 지원이 필요합니다. 분리된 worker가
공유 이력을 읽었다고 그 연결을 소유하지 않습니다. 이 선택적 전송 제약을 이유로 네이티브
협업에 앱·원격 관측 게이트를 다시 도입하지 않습니다.

## 검증 범위

현재 소스 진입점은 `runtime/provider_execution.py`, `runtime/provider_policy.py`,
`providers/jobs.py`, `providers/job_recovery.py`, Codex·Claude 어댑터, `agents/delivery.py`,
`agents/delivery_recovery.py`입니다. 해당 구성 요소의 테스트는 설치된 실제 호스트 수용 검증이 아닙니다.
검증 원문을 비공개로 보존하고 schema·fixture, 패키지 설치, 실제 모드·준비, 본문 조회·ACK,
프로세스 복구와 발행자의 후속 응답을 구분합니다. 최종 설치본의 Codex·Claude 교차 프로바이더와
idle 발행자 시나리오는 각각의 네이티브 근거로 입증합니다.
