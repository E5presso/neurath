# Neurath 코어 재구축 계약

[English](../../en/contributing/core-v2-spec.md)

상태: 새 코어의 설계 계약. 기존 런타임의 동작 설명이나 구현 완료 선언이 아니다.

## 1. 제품 목적과 확정 결정

Neurath는 사용자의 일을 에이전트가 끝까지 수행하도록 돕고, 선택한 skill의 절차와
사용자가 요구한 완료 조건을 강제하는 하네스다. 모델 실행·파일 접근·네트워크 권한은
호스트가 소유한다. 코어는 호스트의 보안 경계를 다시 구현하지 않는다.

2026-10-03 확정한 요구는 다음과 같다.

| 결정 | 계약 |
| --- | --- |
| D1 | 기존 코어를 예외 추가로 연장하지 않고 이 스펙에서 다시 구현한다. |
| D2 | 서브에이전트, 독립 세션, Claude/Codex 업무 위탁을 작업의 성격·난이도·필요에 따라 선택한다. |
| D3 | 실행 중인 skill이 정의한 phase를 건너뛰거나 완료 전에 다음 phase로 넘어갈 수 없다. |
| D4 | 미완료 태스크가 남아 있으면 에이전트 세션의 정상 종료를 허용하지 않는다. |
| D5 | 실패·차단·시간 초과·검사 통과·구현 시도 종료는 사용자 태스크의 완성을 대신하지 않는다. |
| D6 | 원래 사용자 지시와 실제 관측을 에이전트가 작성한 인용·요약·보고로 대체하지 않는다. |
| D7 | 기존 설치 프로젝트의 사용자 파일, 호스트 보안 설정, 진행 중 작업 기록은 코어 소스 교체와 별도로 보존한다. |

진행 상태를 권고 수준으로만 관리하는 설계는 D3·D4에 의해 기각됐다.

## 2. 핵심 개념과 단일 책임

| 개념 | 의미와 책임 | 책임이 아닌 것 |
| --- | --- | --- |
| Source | 호스트에서 받은 원래 사용자 입력 또는 실제 도구 결과의 불변 원문과 출처 | 산문·해시만으로 권한이나 의미를 증명 |
| Actor | 작업을 수행하거나 보고하는 실행 참여자. 호스트가 식별하며 프로젝트와 연결 | CWD와 결속된 별도 권한 주체, worktree마다 새로 만들 신원 |
| Session | 호스트의 대화·실행 수명과 그 세션이 책임지는 태스크 집합 | worktree·task·phase와 같은 것 |
| Task | 사용자가 요구한 결과, 범위, 인수 조건, 지시 출처, 책임 주체 | 에이전트가 선택한 검사·시도·복구 절차 자체 |
| Skill run | 하나의 태스크에 연결한 skill 정의의 불변 스냅샷과 현재 phase | 별도 완료 원장이나 두 번째 목표 |
| Phase | skill에 정의된 순서 있는 단계와 명시적 완료 조건 | 증거 문자열을 요구하는 독립 상태 기계 |
| Assignment | 태스크의 한 범위를 다른 actor에게 맡긴 관계와 결과 반환 약속 | 새로운 사용자 지시, 전체 태스크 소유권의 묵시적 이전 |
| Worktree lease | 특정 checkout에 실제로 쓰는 actor 하나를 지정하는 충돌 방지 임대 | 읽기·리뷰·상태 조회를 위한 필수 자격 |
| Evidence | 실제 관측 또는 명시적으로 표시된 에이전트 보고와 그 출처 | 출처를 참조했다는 이유만으로 보장되는 진실 |
| Approval | 실제 사용자 입력에 근거한 특정 행동·대상·범위의 허용 | 에이전트의 yes 문자열, 동료의 지시, 이전의 비슷한 승인 |

Actor, session, task, checkout은 서로 다른 식별자를 가진다. Actor의 신원은 CWD를
바꾼다고 바뀌지 않는다. 같은 actor가 호스트 권한 안에서 다른 linked worktree를
대상으로 작업할 수 있으며, 그 이유만으로 새 세션을 만들지 않는다.

## 3. 상태 소유권

사용자 작업의 상태 소유자는 **Task 하나**다. Task 안에 skill run의 현재 phase,
phase 완료 기록, 인수 조건 결과, assignment 결과 참조를 둔다. 별도의 workflow 완료,
adaptive 완료, task 완료를 다시 동기화하지 않는다. 화면 TODO는 Task의 조회 결과다.

영속성은 프로젝트별 하나의 트랜잭션 저장소로 제한한다. 변경 명령은 대상 ID,
예상 revision, 호스트가 제공한 호출 ID로 원자적으로 처리한다. 동일 호출과 동일
입력의 재전달은 저장된 결과를 반환한다. 같은 호출 ID의 다른 입력은 거부한다.
목표 문장의 문자열 일치, 최근 수정 시간, 파일 경로 추측으로 작업을 연결하지 않는다.

Source·Evidence·완료된 phase 기록은 불변이다. 수정은 기존 기록을 덮어쓰지 않고
새 사용자 지시 또는 새 시도와 연결한다. 호스트 표시 상태는 저장소의 상태를 바꾸지 않는다.

## 4. 태스크 수명과 세션 종료

Task의 실행 상태는 `open`, `running`, `waiting`, `completed`다. `waiting`은 이유와
필요한 외부 사건을 보존하며 미완료 상태다. 실패는 **attempt의 결과**로 기록한다.
실패한 attempt 때문에 Task를 완료하거나 요구사항을 지우는 명령은 제공하지 않는다.

태스크 완료는 다음을 모두 만족할 때만 허용한다.

1. 현재 유효한 사용자 범위와 모든 인수 조건에 결과·출처가 연결됐다.
2. 연결된 skill run의 모든 phase가 정의된 순서로 완료됐다.
3. 완료에 필요한 assignment와 review 결과를 책임 주체가 실제로 읽고 수락했다.
4. 실패하거나 미해결인 필수 조건이 없다.

사용자가 목표를 바꾸거나 취소하면 원래 요청을 `withdrawn` 이력으로 보존하고 새 요청과
연결한다. 이는 완료가 아니며 사용자 출처 없이 에이전트가 사용할 수 없다. 단순 상태
질문, 중단된 도구 호출, Stop 거부는 취소 출처가 될 수 없다.

정상 Stop은 세션 책임 범위에 유효한 미완료 Task 또는 미종결 Assignment가 하나라도
있으면 거부한다. 응답은 정확한 작업 ID, 현재 phase, 다음 필요한 행동을 알려준다.
Stop 거부 때문에 성공·실패·취소를 만들어내지 않는다.

사용자에게 답을 기다리는 동안에는 호스트가 지원하는 대기 상태를 사용한다. 대기와
정상 종료를 구분한다. 호스트 강제 종료·충돌·사용자 인터럽트는 코어가 물리적으로 막을 수
없으며, 미완료 기록을 유지하고 재개 시 복구한다. 이를 태스크 완료로 해석하지 않는다.

## 5. Skill과 phase 강제

Skill의 phase 순서와 각 완료 조건은 skill과 함께 배포되는 한 정의에서 읽는다.
Skill run 시작 시 그 정의와 버전을 Task에 고정한다. 실행 중 설치 업데이트가 와도
진행 중 phase의 의미를 몰래 바꾸지 않는다.

| 명령 | 허용 조건 | 결과 |
| --- | --- | --- |
| 시작 | 실제 Task ID가 존재하고 이 skill이 그 작업에 적용됨 | 첫 phase를 현재 단계로 고정 |
| 현재 단계 읽기 | 해당 작업을 볼 수 있음 | 상태 변경 없이 현재 phase·미충족 조건 반환 |
| 단계 완료 | 요청한 phase가 현재 phase이고 모든 필수 조건 충족 | 한 트랜잭션에서 현재 phase 완료 및 다음 phase 선택 |
| 마지막 단계 완료 | 같은 조건 | skill run 완료. 태스크 인수 조건을 다시 확인할 수 있게 함 |
| 실패·차단 기록 | 현재 phase에서 관측된 실패 또는 외부 대기 | 현재 phase 유지. attempt와 이유만 추가 |

일반적인 `skip`, 임의 phase 번호 지정, phase를 완료로 가장하는 `not-applicable`는
제공하지 않는다. Skill에 조건부 경로가 필요하면 skill 정의가 조건·선택 시점·완료 기준을
미리 명시해야 한다. 에이전트가 실행 중 임의로 단계를 없앨 수 없다.

단계 완료 증거는 정해진 종류의 참조로 받는다. `PASS` 산문, 정규식에 맞춘 문장,
다른 phase의 label을 나열한 텍스트는 실제 검사·리뷰·게시 결과를 대신하지 못한다.
Semantic 인수 판단은 그 판단 주체와 근거를 명시하고, 코어가 의미적 진실을 증명했다고
주장하지 않는다. 필수 독립 리뷰 여부는 해당 skill이 정의한다.

Phase는 실행할 하위 skill을 명시할 수 있다. 하위 skill은 같은 Task 안에서 자체 phase를
순서대로 끝낸 뒤 원래 부모 phase로 돌아온다. 하위 skill 완료가 부모 phase를 완료하거나
부모의 허용 효과를 확장하지 않는다. 정의에 없는 하위 skill로 진행 중 절차를 대체할 수 없다.
Task 완료 시 연결된 모든 skill run의 완료를 검사한다.

### 재작업과 실제 효과

Skill은 각 단계의 실패와 최종 인수 실패에 대해 돌아갈 `restart_from` phase를 미리
정의한다. 리뷰에서 결함이 발견되면 같은 Task의 새 attempt를 시작하고 그 phase부터
다시 순서대로 진행한다. 실패한 리뷰나 달라진 입력의 실제 Evidence가 restart의 출처다.
완료 기록은 삭제하지 않고 이전 attempt의 역사로 유지한다. 재시작 지점 이후의 결과는
새 attempt의 완료를 충족하지 못한다. 이전 지점의 결과도 소비한 입력이 달라지면
가장 이른 영향 단계부터 다시 수행한다. 영향 범위를 판단할 수 없으면 첫 단계로 돌아간다.
관측을 재사용할 때는 같은 조건·입력·대상 revision을 확인하며 새 실행으로 기록하지 않는다.
임의 phase 번호로 현재 위치를 설정하거나 새 Task를 만들어 실패를 숨기지 않는다.

Native adapter는 실제 tool 호출을 Task와 현재 phase에 연결하고 호출 전에 효과를
분류한다. 최소 종류는 `read`, `edit`, `check`, `delegate`, `publish`, `cleanup`,
`execute`다. Skill은 phase마다 허용한 종류를 명시한다. 알려진 파일 편집·게시·삭제
도구와 명령을 다음 phase에서만 허용했다면 현재 phase에서는 거부한다. 등록된 검사
명령은 정확한 argv와 작업 경로로 `check`를 식별한다. 혼합 호출은 모든 효과가 허용돼야 한다.
분류되지 않은 일반 shell/program 호출은 `execute`이며 read-only 단계에서는 허용하지 않는다.
임의 프로그램 내부의 모든 효과를 정적으로 증명한다고 주장하지 않는다. 호스트 권한과
실제 관측 범위를 유지하며 알려진 효과를 일반 execute로 낮춰 분류하지 않는다.

상태 조회·실패 보고·정상 lease 반환 같은 코어 제어 명령은 phase의 작업 효과와 별개로
허용한다. Task/phase가 모호하면 쓰기 효과를 추측해서 실행하지 않고 정확한 대상 선택을
요구한다. 필수 PreToolUse 같은 호스트 관측 경로가 없으면 강제가 검증됐다고 주장하지 않는다.
해당 효과를 실행하기 전에 capability 부족을 반환하며, 상태 조회·보고·사용자 입력 대기는
계속 가능하다. 실제 호스트에서 단계 밖 native 편집과 게시가 거부되는지 확인해야 한다.

## 6. 위임과 리뷰

위임 선택은 `subagent`, `session`, `cross-provider` 세 가지다. Task의 성격, 난이도,
필요한 능력, 독립적인 작업 수명과 호스트의 실제 지원을 근거로 선택한다. `worker`라는
네 번째 선택지를 만들지 않는다. Worker는 assignment를 수행하는 actor의 역할 이름이다.

- 서브에이전트: 현재 작업에 속한 범위가 정해진 일을 수행한다. 기본 선택이다.
- 독립 세션: 별도 대화·수명이 실제로 필요한 일을 맡는다. 새 세션이라는 사실을 숨기지 않는다.
- 교차 provider: 다른 provider의 능력·관점이 필요한 일을 맡는다. 목적과 결과 책임을 유지한다.

Root 경로, worktree 필요, 실행 시간, 티켓 수만으로 독립 세션을 강제하지 않는다.
앱 프로젝트 생성·사용자용 채팅 생성의 호스트별 명시적 요청 조건을 유지한다.

Assignment는 원래 Task와 범위·부모·수신자·결과를 연결한다. 부모·자식 관계는 호출과
결과를 연결하기 위한 사실이며 새 OS 권한을 발급하지 않는다. 동일 provider 자식과
다른 provider 세션 모두 같은 Assignment 계약으로 결과를 반환한다.

Assignment 역할은 범위가 정해진 작업자(`worker`), 읽기 검토자(`reviewer`), 해당 Task의
skill 절차를 맡은 실행자(`executor`)로 구분한다. 역할은 세 실행 방식과 별개다.
Executor는 명시적으로 맡은 Task의 phase를 진행할 수 있지만 목표·인수 조건·사용자 승인을
바꾸거나 사용자 Task의 최종 완료를 대신 확정할 수 없다. Task마다 동시에 하나의 executor만
phase를 제어하며, owner는 취소·보고 수락·책임 회수 같은 제어를 유지한다. 병렬 worker는
같은 phase의 범위 안에서 작업하고 phase 진행은 controller 하나가 결정한다.
이 구조로 전체 skill 위임에도 Task/phase 원장을 복제하지 않는다.

독립 리뷰는 구현에 참여하지 않은 별도 actor가 고정된 변경 버전을 읽고 판정하는 일이다.
리뷰어가 원본 checkout을 읽는 데 쓰기 lease나 전체 실행 정책 재증명을 요구하지 않는다.
호스트에서 관측할 수 없는 policy 정보는 `unknown`으로 남긴다. 그것만으로 상태 조회나
리뷰 보고를 차단하지 않는다. 실제 쓰기·외부 효과는 호스트의 권한 검사를 그대로 따른다.

리뷰 결과는 검토한 commit 또는 diff digest에 결속한다. 변경이 생기면 영향 범위를 다시
검토해야 하며 이전 결과를 새 변경의 승인으로 재사용하지 않는다. 읽지 않은 결과,
접수 ACK, worker 종료를 완료 판정으로 소비하지 않는다.

Assignment의 전이는 `issued → active → reported → accepted|rejected`다. `reported`는
결과가 저장소에 실제로 저장됐다는 뜻이다. 수신자의 반환 의무는 여기서 끝나며 수신자는
자기 책임의 다른 미완료 Task/Assignment가 없다면 종료할 수 있다. 부모의 읽기·수락 의무는
남아 있으므로 부모 Task나 세션은 완료되지 않는다. 자식 종료 전에 보고를 저장할 수 있어야 한다.

실패·차단 보고도 실제 attempt 결과로 반환할 수 있지만 부모의 인수 조건을 충족하지 않는다.
Owner가 결과를 거절하거나 재시도하면 원래 Task 아래 새 Assignment attempt를 만들고
이전 결과를 보존한다. 독립 세션도 부모의 한 attempt를 실행하는 경우 같은 규칙을 따른다.
별도 사용자 Task를 소유한 독립 세션은 그 Task가 미완료인 한 종료할 수 없다.

## 7. Worktree 소유권

Checkout은 Git common directory와 canonical worktree 경로로 식별한다. 한 checkout에는
동시에 한 writer만 허용한다. Claim·release·handoff는 단일 원자적 상태 전이로 처리한다.
획득마다 증가하는 generation으로 오래된 writer의 후속 쓰기를 거부한다.

읽기, 상태 조회, 분석, 리뷰, 실패 보고에는 lease를 요구하지 않는다. Task owner와
현재 writer를 구분한다. 위임 때문에 전체 태스크 소유권을 넘기지 않는다.

Actor가 다른 linked worktree를 선택하면 그 대상을 명시적으로 claim한다. 원래 session의
CWD나 신원을 위조하지 않는다. 실제 native 파일 작업이 그 경로에서 허용되는지는 호스트가
판단한다. 같은 파일의 동시 쓰기가 필요한 경우 독립 worktree를 사용한다.

다른 writer의 lease를 강제로 덮어쓰지 않는다. 정상 반환·명시적 인계 또는 실제 호스트
종료 확인 뒤 복구한다. 시간 경과나 에이전트의 추측만으로 살아 있는 writer를 쫓아내지 않는다.

## 8. 출처, 인용, 승인

네이티브 입력과 도구 원문은 native adapter의 관측 경로에서만 Source로 등록한다.
일반 입력 훅의 출처는 `native_input`이며 사람이 작성했다는 증명이 아니다.
일반 에이전트 API가 보내는 문서는 `agent_report`다. 같은 본문·해시를 넣어도
사용자 입력이나 실제 도구 실행 결과로 승격되지 않는다.

인용은 Source ID와 정확한 원문 구간을 가리킨다. 원문에 없는 구절, 다른 source의 문장,
변경된 digest를 붙인 인용은 거부한다. 외부 문서·peer 메시지·과거 대화 인용을 현재
사용자의 행동 승인으로 소비하지 않는다.

승인은 행동, 대상, 허용 범위와 실제 사용자 입력을 연결한다. 분명한 직접 지시와
유일한 대기 질문에 대한 실제 응답을 처리한다. 에이전트가 작성한 `user_confirmed=true`,
선택지 digest, XML/JSON 모양 또는 임의로 인용한 yes는 승인 출처가 아니다.
대상이나 범위가 바뀌면 기존 승인으로 외부 효과를 실행하지 않는다.

현재 구현 가정은 코어가 원문·정확한 인용·행동/대상/태스크 범위를 검증하고, 사용자 승인
의미에 대한 에이전트의 판단을 `agent-interpretation`으로 기록하는 것이다. 태스크 등록에는
보존된 네이티브 입력을 사용하되 사람의 입력이라고 출처를 승격하지 않는다. peer·예약 실행·
자동 재개임이 확인된 입력은 새 작업의 승인이 될 수 없다. 에이전트는 실제 대화 맥락에서
사용자 지시와 자동 입력을 구분한다. 이미 명확한 승인은 재확인 질문 없이 사용할 수 있다.
별도 사람 확인 경로 선택에 관한 선택 질문에는 아직 답이 없으며 이 방향을 작업 가정으로
명시했다.

해시는 원문 동일성 확인용이며 발화자나 의미적 동의를 증명하지 않는다. 동일 OS 사용자
권한으로 호스트 저장소를 악의적으로 변조하는 공격까지 코어가 격리한다고 주장하지 않는다.

## 9. 실패와 복구

모든 명령은 `ok` 또는 안정된 오류 코드와 실제 미충족 조건, 보존된 작업 ID를 반환한다.
예를 들어 task ID 부재와 목표 문장 불일치를 같은 오류로 반환하지 않는다. 목표 문장은
애초에 연결 키가 아니다.

진단 읽기, attempt 실패·차단 기록, 이미 맡긴 assignment의 실패 보고, 원래 writer의
정상 lease 반환은 작업 실행과 다른 명령 종류다. 실행 전제조건 실패가 이 명령들까지
막아 복구 불가능한 순환을 만들지 않는다. 이 경로는 task나 phase를 완료하지 않는다.

복구는 관측한 상태에서 계속한다. 새 세션 생성, 전체 검사 반복, 새 승인 질문을 기본
복구 동작으로 사용하지 않는다. 완료된 관측은 변경된 입력이 없으면 재사용한다.

같은 host session의 재개는 같은 Task ID와 소유권을 유지한다. 다른 session으로 책임을
이관할 때는 명시적 사용자 지시 또는 기존 owner의 handoff가 필요하고, 기존 writer가
정지·반환했음을 확인한다. 원자적 adoption은 같은 Task ID를 유지하면서 owner와
ownership generation만 갱신한다. 이전 owner의 늦은 상태 변경은 거부한다. 이미 발행된
Assignment의 실제 보고는 원래 ID로 저장하고 새 owner가 수락한다.

사용자 취소는 대체 Task가 없어도 가능하다. 원래 Task를 withdrawn으로 보존하고 해당
범위의 새 실행을 금지하며, 진행 중 Assignment에는 취소를 요청한다. 실제 호스트 종료
또는 수신자의 취소 보고가 확인돼야 실행 의무와 writer lease를 정리한다. 취소 요청만
보내고 프로세스가 끝났다고 간주하지 않는다. 사용자 강제 중단은 관측된 사실로 기록하며,
남은 정리 의무를 다음 재개에서 복구한다. 취소를 성공으로 표시하지 않는다.

## 10. 구현 경계와 제거 대상

새 코어는 domain 모델·전이, 단일 저장소, application 명령, 얇은 host adapter로 구성한다.
패키지 installer, 공개 release·reporting transport, provider별 실제 모델 통신은 외곽 서비스다.
외곽 서비스가 task·phase·승인 상태를 따로 소유하지 않는다.

기존 session kernel, task/phase/adaptive 이중 원장, review 전용 상태 체계, legacy CLI replay,
산문 evidence 정규식 gate는 새 코어가 인수 시나리오를 만족하면 실행 경로와 배포본에서 제거한다.
이를 검증할 후보 배포본은 먼저 이전 코어를 포함하지 않도록 빌드한다. 후보 배포본의
실제 호스트 인수 시나리오를 통과한 뒤 저장소의 이전 구현을 최종 삭제하고 다시 배포 검증한다.
기존 엔진 위에 새 facade만 얹는 방식은 완료로 인정하지 않는다. 기존 실행 데이터를 새 코어가
성공으로 간주하거나 조용히 삭제하지 않는다. 명시적 export/adoption 경계에서 미완료 목표를 보존한다.

## 12. Codex 호스트 연결에서 확인한 경계

현재 [공식 hooks 문서](https://learn.chatgpt.com/docs/hooks)에 따르면 Stop의 block 응답은
새 continuation을 요청하며 이미 표시한 답변을 취소하지 않는다. SessionEnd는 통지이므로
사용자·호스트의 종료를 막지 못한다. 따라서 미완료 작업의 정상 완료 시도에는 continuation을
요청하고, 실제 중단에는 미완료 상태를 보존한다. 훅이 만든 continuation은 새 인간 승인으로
등록하지 않는다. Subagent 훅의 session_id는 부모 세션이고 agent_id로 참여자를 구분한다.
PreToolUse가 관측하는 호출에서 edit·MCP 등의 deny를 검증하며, 관측되지 않는 경로의 강제를
확인했다고 주장하지 않는다. 이 경계는 실제 설치된 호스트로 다시 확인한다.
