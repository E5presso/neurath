# Neurath 개발 작업 시작하기

[English](../../en/contributing/index.md) · [프로젝트 소개](../../../README.ko.md)

Neurath 자체를 수정하는 개발자와 새로 시작한 코딩 에이전트를 위한 진입 문서입니다. 허가된 변경을 수행하고, 기존 작업을 보존하며, 무엇을 검증했는지 정확히 보고하는 것이 목적입니다. 다른 저장소에서 Neurath를 쓰려면 [첫 사용 예시](../usage/start-here.md)와 [설치 안내](../usage/installation.md)부터 읽으세요. 그 저장소 안에서 작업하는 에이전트의 실행 절차는 [에이전트 참조](agents-reference.md)에 있습니다.

## 이 체크아웃에 적용되는 지침부터 읽습니다

현재 사용자 요청, 저장소의 `AGENTS.md`, 수정할 디렉터리에 적용되는 추가 지침을 먼저 읽습니다. 편집 전에는 현재 브랜치, 워크트리, 커밋하지 않은 변경을 확인합니다. 다른 세션이 남긴 작업과 기존 인수인계 내용을 보존합니다.

설치되어 있다면 `.neurath/policy.md`에서 실행 정책과 명시적인 네이티브 실행 예외를, `.neurath/project.json`에서 프로젝트 문서와 검증 연결을 읽습니다. 작업에 해당하는 설치 스킬의 지침도 확인합니다. 메모리와 이전 보고는 현재 상태를 살펴볼 단서로 사용합니다. 과거에 검사를 통과했다는 기록이 바뀐 체크아웃의 성공이나 현재 권한을 증명하지는 않습니다.

Neurath가 관리하는 원본은 `src/neurath/_assets`에 있습니다. 설치된 `.agents/skills`와 `.neurath/rules`는 배포 원본을 투영한 결과이므로 이 파일만 고쳐서는 패키지 소스가 바뀌지 않습니다. 다른 저장소는 빌드 입력이 아닙니다. 소유 범위는 [자산 개발](assets.md), 런타임 구성 요소의 관계는 [아키텍처](architecture.md)를 참고하세요.

## 실제 실행 상태를 확인합니다

소스 체크아웃, 설치된 배포본, 현재 호스트 연결을 구분해 기록합니다. 설치, 런타임 실행, 실제로 관찰한 네이티브 활성화, 적용 중인 정책, 워크트리 소유권을 각각 확인합니다. 파일이 있다는 사실만으로 훅이 실행되었다고 판단하지 않습니다. 프로토콜 검사를 통과해도 기존 MCP 연결이 다시 로드되었다는 뜻은 아닙니다. `session_status`는 상태를 진단하며 권한을 부여하지 않습니다.

Neurath가 설치되어 있지 않거나 이름 있는 도구가 없으면 그 상태를 보고합니다. 네이티브 바인딩을 만들어 내거나, 사용할 수 없는 런타임의 검문 절차가 적용된다고 가정하지 않습니다. 현재 저장소 지침과 적용 가능한 네이티브 실행 예외를 기준으로 진행하고, 허가된 초기 설치 작업에는 [설치 실행 안내](installation.md)를 사용합니다. 반대로 활성 런타임이 선행 조건을 거부했다면 실제 실패로 다뤄야 합니다. 다른 경로로 같은 동작을 재현해 우회할 근거가 되지는 않습니다.

활성 네이티브 세션에서는 쓰기 전에 세션 참여가 확인되었는지, 워크트리 클레임이 있는지 확인합니다. 클레임은 쓰기 권한을 가진 리스입니다. 다른 세션의 클레임, 피어의 수락, 가져온 체크포인트가 자신의 소유권을 대신하지 않습니다. 반환된 리스 값은 허가된 해제 시점에 정확히 사용하되 공개 문서에 넣지 않습니다. 활성화와 소유권의 자세한 조건은 [호스트 연동](hosts.md)과 [런타임 생명주기](runtime-lifecycle.md)에 있습니다.

## 현재 태스크 계약에 맞춰 시작합니다

현재 연결에 노출된 이름 있는 MCP 도구를 찾고 실제 인자 스키마를 확인합니다. Neurath를 개발할 때는 `src/neurath/runtime/task_schema.py`의 현재 정의와 대조합니다. 현재 소스는 공개 도구 128개와 내부 연산 138개를 갖지만, 개수나 저장된 예제만으로 지금 연결이 준비되었다고 판단할 수는 없습니다. 계약은 [태스크 도구](task-tools.md), 필요한 연산의 위치는 [기능 지도](capability-map.md)에서 찾습니다.

네이티브 참여가 확인되면 `task_list`를 읽고 반환된 목록 리비전을 사용합니다. `task_define`으로 실제 요구사항 출처, 관찰할 수 있는 완료 조건, 의존 관계를 담아 작업을 정의합니다. 첫 접수에는 네이티브 사용자 지시 리시트 또는 같은 세션에서 보존한 유효한 요청 출처가 필요합니다. 진행 상황을 묻는 질문을 새 요구사항으로 조용히 바꾸면 안 됩니다.

반환된 태스크 ID와 현재 목록·태스크 리비전을 사용하여 `task_start`로 선택한 작업을 시작합니다. `_neurath_binding`, 실행 주체, 리비전 값을 만들어 내지 않습니다. 리비전이 달라졌다면 새 상태를 읽고 충돌을 정리합니다. 다른 루트의 작업을 이어받을 때는 참고 자료를 읽는 것만으로 부족합니다. [프로바이더 연속성](provider-continuity.md)에 따라 허가된 인수를 끝낸 뒤 쓰기를 계속합니다.

태스크의 기준 상태는 원장이 관리하고 네이티브 TODO는 이를 표시합니다. 일반적인 소스 편집과 테스트는 네이티브 도구로 수행하며 material·verification 기록을 중복해서 만들지 않습니다. 사용자가 고른 스킬에 명시적인 단계나 검토 계약이 있다면 그 계약도 따릅니다. 추가 근거가 필요한 경우는 [스킬 계약](skills-reference.md)에 설명되어 있습니다.

## 허가된 변경을 구현하고 검증합니다

잠금 파일에 맞춰 Neurath 개발 환경을 준비합니다.

```sh
uv sync --locked
```

구현 변경의 저장소 검사 명령은 다음과 같습니다.

```sh
uv run --locked python tools/check.py
```

검사는 첫 실패에서 멈추며 실제 단계가 모두 성공해야 `NEURATH_CHECK_OK`를 출력합니다. 어떤 소스 상태에서 무엇을 실행했는지 기록합니다. 문서만 바꾸는 경우에는 변경에 맞는 공개 문서 규약 테스트와 링크·스키마 검사를 수행합니다. 문구 수정만으로 설치나 실제 호스트 실험이 필요해지지는 않습니다.

새 설치 동작은 먼저 실패하는 테스트로 정의한 뒤 구현합니다. 실행 자산을 변경했다면 필요한 검사와 패키지 빌드 전에 매니페스트를 갱신합니다.

```sh
uv run --locked python tools/build_manifest.py
```

자기 설치 명령은 다음과 같습니다.

```sh
./setup --self
```

허가된 개발 범위에 설치 하네스 갱신이 포함될 때 사용합니다. 개발 `.venv`와 분리된 지속적인 도구 런타임을 사용합니다. 설치 성공만으로 실제 호스트 활성화까지 확인된 것은 아니므로, 그 결과를 주장하려면 이후 네이티브 호스트 이벤트를 관찰해야 합니다. [검증 안내](validation.md)는 소스 검사, 패키지 실행, 설치 동작, 실제 호스트 시나리오를 구분하며, 초기 준비의 세부 사항은 [설정 참조](setup-reference.md)에 있습니다.

두 언어 문서는 같은 상대 경로에서 함께 유지합니다. 언어 전환 링크 외에는 같은 언어의 문서로 연결합니다. 공개 `usage` 문서는 자연어 요청과 관찰할 결과를 설명하고, 실행 명령과 설정은 개발자 참조에 둡니다. 비공개 프로젝트 정보, 원시 검증 기록, 설치 리시트는 공개 문서와 배포본에 넣지 않습니다.

## 원래 완료 조건을 기준으로 끝냅니다

`task_resolve`에 현재 리비전, 구체적인 참조, 완료 조건에 대응하는 결과 요약을 전달합니다. 이 연산은 담당 주체의 보고를 기록하며 독립적인 인증을 제공하지 않습니다. 태스크 상태는 `pending`, `in_progress`, `succeeded`, `failed`, `invalidated`이고 마지막 세 가지가 종료 상태입니다. `all_terminal`뿐 아니라 `all_succeeded`와 성공하지 못한 태스크 ID도 확인합니다. 한 시도의 실패가 여전히 수행 가능한 사용자 요구를 취소하지는 않으므로 필요한 후속 작업을 남깁니다.

Stop이 미완료 선행 조건을 보고하면 실제 사유에 맞춰 허가된 작업을 계속하거나 복구합니다. 답변받지 못한 질문, 곁가지 질문, 경과 시간, 소진된 연속 실행 예산은 선행 조건을 면제하지 않습니다. 사용자의 명시적 중단은 네이티브 호스트 동작으로 처리합니다. 일반 호스트 세션 종료는 재개 가능한 작업과 클레임을 보존할 수 있지만, 커널의 `SessionEnded`는 영구 종료입니다. 체크포인트에 completed라고 적는 것은 어느 상태 전이도 대신하지 않습니다.

필요한 작업과 명시적인 단계·검토 계약을 완료하고, 해당하는 미처리 결과를 읽어 반영한 뒤, 허가된 시점에 실제 반환된 리스 정보로 소유권을 해제합니다. 적용되는 선행 조건을 충족할 수 없다면 구체적인 장애와 다음 행동을 보고합니다. 사용자 목표를 완료했다고 바꾸어 보고하지 않습니다. 정확한 경계는 [태스크·TODO 계약](task-todo-contract.md)과 [런타임 생명주기](runtime-lifecycle.md)에 있습니다.

최종 보고에는 변경 내용, 사용자에게 달라지는 결과, 실제 관찰한 것, 아직 검증하지 않은 것을 담습니다. 빌드, 설치, 호스트 활성화, 검토·병합, 공개 릴리스는 별개의 근거입니다. 개발 요청만으로 GitHub 생성, push, 공개 배포가 허가되지는 않습니다. [릴리스 작업](releases-reference.md)은 요청된 범위 안에서 진행합니다.
