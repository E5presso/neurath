# 에이전트가 작업할 수 있도록 Neurath 설치하기

[English](../../en/contributing/installation.md) · [기여자 시작 안내](index.md)

프로젝트에서 Neurath를 사용하려면 패키지를 설치하고, 프로젝트의 지침과 검증 방법을 연결하고, 선택한 코딩 호스트가 실제로 연동을 불러왔는지 확인해야 합니다. 이 문서는 초기 설정을 맡은 에이전트가 그 과정을 수행하는 방법을 설명합니다. 사용자는 같은 일을 자연어로 요청할 수 있습니다. [사용자 설치 안내](../usage/installation.md)를 참고하세요.

**설치**는 관리 대상 파일을 배치하고 그 출처를 기록하는 일입니다. **활성화**는 실제 Codex 또는 Claude Code 세션이 훅과 도구를 불러온 상태입니다. **런타임**은 Neurath를 실행하는 별도 Python 환경입니다. 파일 배치가 올바르더라도 호스트에서 신뢰를 허용하지 않았거나 연동을 불러오지 않았을 수 있으므로 세 가지를 구분해 확인합니다.

## 대상 프로젝트와 실행 환경 준비하기

먼저 대상의 지침과 현재 변경 사항을 읽고 사용할 호스트와 파일 이름을 정합니다. 대상은 이미 Git 작업 트리의 루트여야 합니다. 파일이 없는 빈 Git 저장소도 지원합니다. macOS 또는 Linux에서 Git이 필요하며, 소스의 설치 스크립트는 공식 설치기로 `uv`를 준비하고 Python 3.14를 마련할 수 있습니다. 셸 프로필과 대상 프로젝트의 의존성 환경은 유지됩니다.

설치 권한이 있는 에이전트는 Neurath 소스 체크아웃에서 다음과 같이 미리 볼 수 있습니다.

```sh
./setup /path/to/saved-filter-project --host codex --dry-run --json
```

예시 경로는 사용자의 실제 Git 루트로 바꿉니다. `--dry-run`은 대상 파일을 변경하지 않지만 외부 도구 환경은 준비할 수 있습니다. 반환된 `changes`, `hosts`, `profile`, `skill_prefix`를 확인한 뒤 선택한 설정을 적용할 때는 `--dry-run`을 제외합니다.

```sh
./setup /path/to/saved-filter-project --host codex --json
```

새 설치에서 호스트를 생략하면 `generic` 프로필과 지원하는 두 호스트를 선택합니다. 재실행하면 기존 선택을 유지합니다. 프로젝트가 같은 이름의 스킬을 이미 사용한다면 새 설치에서 `--skill-prefix neurath-`를 지정해 `/neurath-debug`처럼 구분할 수 있습니다. 기존 프로젝트 스킬의 이름은 바뀌지 않습니다. 설치된 접두어를 변경하려면 먼저 제거해야 합니다. 접두어는 이름 충돌을 구분할 뿐, 서로 다른 하네스 지침의 권한 충돌을 해결하지는 않습니다.

설치 스크립트는 내용의 해시로 구분하는 영구 도구 환경을 만듭니다. 프로젝트의 실행기는 선택된 환경의 인터프리터를 가리키므로, 다른 프로젝트에 새 버전을 준비해도 기존 프로젝트의 런타임이 조용히 교체되지 않습니다. 공통 `neurath` 명령은 대상 설정에 성공한 뒤에만 갱신합니다. `NEURATH_NO_BOOTSTRAP=1`은 `uv` 자동 다운로드를 끕니다.

## 프로젝트 문서와 검사 방법 연결하기

기존 연결 설정이 없으면 `.neurath/project.json`에 빈 `documents`와 `verification` 객체를 설치합니다. 이 연결 설정은 프로젝트의 요구사항을 어디서 읽고 작업 결과를 어떤 명령으로 확인할지 알려 줍니다. 에이전트는 실제 문서와 명령을 조사한 뒤 값을 채워야 합니다.

예를 들어 사용자가 개발하는 웹앱에서 저장한 필터가 새로고침 후 사라진다고 가정해 보겠습니다. 그 저장소에 `SPEC.md`와 `npm test`가 이미 있다면 다음과 같이 연결할 수 있습니다.

```json
{
  "schema": 1,
  "documents": {"intent": "SPEC.md"},
  "verification": {
    "project-check": {
      "argv": ["npm", "test"],
      "cwd": ".",
      "success_codes": [0],
      "timeout_seconds": 300
    }
  }
}
```

가상의 사용자 앱을 설명하기 위한 예시입니다. Neurath가 제공하는 필터 기능이나 모든 JavaScript 프로젝트의 기본 설정을 뜻하지 않습니다. 실제 저장소의 문서와 검사 명령으로 바꿔야 합니다. `argv`에는 셸 문자열 대신 인자 배열을 넣고, `cwd`는 저장소 안의 경로를 사용합니다. 제한과 결과 해석은 [프로젝트 검증 설정](setup-reference.md#프로젝트-검증-명령-설정하기)에 설명되어 있습니다. 사용자가 편집한 연결 설정은 업데이트와 제거 후에도 보존됩니다.

## 설치 결과를 읽고 실제 호스트에서 확인하기

설정 결과에는 **receipt**, 즉 어떤 설치 변경을 수행했는지 식별하는 보존 기록과 진단 결과가 들어 있습니다. 설치를 되돌릴 때 이 기록의 ID를 사용할 수 있으므로 비공개 프로젝트 상태에 보관합니다. 진단은 배포본 무결성, 관리 파일 배치, 로컬 훅 프로토콜 동작을 확인합니다. 프로토콜 검사에 성공해도 실제 호스트 활성화는 미확인으로 남습니다.

설치된 네이티브 세션에서는 `diagnostics_project`에 다음 입력을 주어 프로토콜도 검사합니다.

```json
{"protocol": true}
```

`.neurath/policy.md`와 `.neurath/project.json`을 읽고, [기여자 시작 안내](index.md)에 따라 실제 세션과 현재 노출된 도구를 확인합니다. Codex에서는 프로젝트 신뢰와 `/hooks`의 정확한 Neurath 훅을, Claude Code에서는 `/hooks`의 훅 로딩을 확인합니다. 이후 정상적인 호스트 이벤트가 발생했을 때 실행 중인 연동이 의도한 작업 트리와 배포본에 속하는지 관찰합니다. 자세한 네이티브 근거는 [호스트 연동](hosts.md)을 참고하세요.

이제 저장 필터 수정을 앱에서 확인할 수 있는 결과를 가진 태스크로 이어갑니다. 설치 진단은 하네스 준비 상태를 확인합니다. 새로고침 후 필터가 유지되는지는 앱의 재현 절차와 테스트로 확인합니다.

## 설치 문제에서 이어가기

파일 적용 후 진단이 실패했다면 설치 기록을 유지하고 `diagnostics_project`의 `protocol=true` 결과를 읽습니다. 이 상태를 활성화 완료로 보고하지 않습니다. `stale plan`은 준비 이후 대상이 바뀌었다는 뜻이므로 변경 내용을 확인하고 계획을 다시 만듭니다. 관리 블록이나 스킬 충돌은 설치기가 두 소유권을 안전하게 합칠 수 없다는 뜻입니다. 파일을 보존하며 해당 충돌을 해결해야 합니다.

중단된 트랜잭션에는 `installation_recover`라는 별도 복구 경로가 있습니다. 복구 후 진단하고 새 계획을 준비합니다. [설치 설계](installation-design.md)는 원본을 보존하는 방식과 동시 편집이 있을 때 복구가 멈추는 이유를 설명합니다. 정확한 도구 입력과 초기 설치 명령은 [설정 참조](setup-reference.md)에 있습니다.

## Neurath 자체를 개발할 때

Neurath 소스를 새로 checkout하면 Codex·Claude의 공통 훅과 MCP 설정이 함께 들어 있습니다. 호스트에서 프로젝트를 신뢰하면 첫 훅이나 MCP 호출이 `tools/checkout_host`를 통해 로컬 런타임을 준비하고 원래 호출을 이어갑니다. 공통 설정에는 기여자의 홈 디렉터리나 checkout 경로를 기록하지 않습니다. 생성된 인터프리터 실행기와 설치 기록은 Git에서 제외되는 로컬 파일로 남습니다.

초기 실행기는 Git 비공개 영역에 소스 지문을 보관합니다. 런타임 매니페스트나 의존성 설정이 바뀌면 다시 준비하고, 실행기나 설치 기록이 누락된 중단 상태에서도 준비를 재시도합니다. 기존 설치를 공통 설정으로 전환할 때 사용자 설정과 다른 MCP 항목은 보존합니다. 이 자동 경로는 Neurath 소스 checkout에 적용되며, 다른 프로젝트에 Neurath를 설치할 때는 위의 설치 요청 절차를 사용합니다.

개발 환경과 설치된 런타임은 역할이 다릅니다.

```sh
uv sync --locked
./setup --self --json
```

첫 명령은 이 체크아웃의 개발 환경을 준비합니다. 두 번째는 별도 영구 런타임으로 이 체크아웃에 자기 설치를 수행합니다. 자기 설치는 승인된 작업에 포함될 때 실행합니다. 실행 자산을 변경했다면 [자산 개발](assets.md)의 매니페스트·검사·빌드·설치 순서를 따릅니다. 문서만 변경했다면 [검증](validation.md)의 문서 범위 검사를 사용합니다.
