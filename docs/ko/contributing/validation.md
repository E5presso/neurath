# 보고할 결과에 맞는 근거 선택하기

[English](../../en/contributing/validation.md) · [기여자 시작 안내](index.md)

검증은 특정 후보에 대한 구체적인 질문에 답합니다. 소스 테스트는 구현 동작을, wheel 테스트는 빌드한 패키지의 동작을, 실제 호스트 이벤트는 네이티브 연동이 실행됐음을 확인합니다. 각각의 관찰을 사용자가 요청한 결과에 연결해야 합니다. 예시 앱에서는 새로고침 후 필터가 유지되어야 하며, Neurath 설치가 정상이라는 사실만으로 그 앱 동작을 증명할 수는 없습니다.

**Receipt**는 작업과 관찰 결과를 보존한 기록입니다. 어떤 과정에서 생성했고 어느 소스·작업 트리·세션·턴을 가리키는지에 따라 의미가 달라집니다. 테스트가 통과했다는 문장은 실제 프로세스 결과를 대신하지 못합니다.

## 변경 범위부터 정하기

| 변경 또는 주장 | 관련 근거 |
| --- | --- |
| 공개 문서 | 공개 규칙, 로컬 링크·앵커, 언어별 범위, 현재 스키마에 맞는 예시 |
| 런타임·설치기 구현 | 변경 동작의 회귀 검사와 필요한 소스 검사 |
| 독립 패키지 | 소스 체크아웃 밖의 새 환경에 실제 wheel 설치 |
| 소스 초기 설치 | 격리한 도구·Python 경로와 임시 저장소에서 실제 setup |
| 릴리스 설치·복구 | 정확한 wheel 준비, 트랜잭션, 진단, 보존, 복원 관찰 |
| 네이티브 호스트 연동 | 대상 세션·턴의 실제 호스트 이벤트와 정확한 결과 확인 |
| 리뷰·병합·공개 릴리스 | 별도 권한이 있는 작업과 실제 원격 결과 |

새 설치 동작은 실패하는 테스트로 먼저 정의합니다. 문서만 변경했다면 문구 검증을 위해 네이티브 설치를 할 필요는 없습니다. 원시 검증 데이터, 개인 경로, 설치 receipt, 내부 출처 기록은 공개 산출물에 넣지 않고, 보고를 뒷받침하는 데 필요하면 비공개로 보관합니다.

## 재현 가능한 소스 검사 실행하기

```sh
uv sync --locked
uv run --locked python tools/check.py
```

현재 패키지는 Python `>=3.14,<3.15`가 필요하고 `claude-agent-sdk>=0.2.152,<0.3`을 런타임 의존성으로 선언합니다. POSIX 프로세스·파일 잠금 동작에 의존하며 macOS/Linux를 지원합니다. Windows는 지원하지 않습니다.

검사는 배포본 무결성, Ruff `E4,E7,E9,F`, `pytest-xdist` 작업자 최대 8개에 사례별로 나눈 전체 패키지 테스트, 같은 작업자 상한을 적용한 독립 런타임 회귀 검사 순서로 진행하고 첫 실패에서 멈춥니다. 모두 성공한 뒤에만 `NEURATH_CHECK_OK`가 출력됩니다. 같은 보호 동작을 독립적인 매개변수 조합으로 반복하던 사례는 줄이고, 서로 다른 보안·수명주기 경계는 유지합니다. 후보와 실제 명령 결과를 기록합니다. 예전 마커나 과거 테스트 개수는 변경된 후보의 근거가 아닙니다.

실행 자산이 바뀌었다면 검사 전에 매니페스트를 다시 생성합니다.

```sh
uv run --locked python tools/build_manifest.py
```

이 명령은 카탈로그의 파생 인덱스도 갱신합니다. 독립 런타임 회귀 실행기는 소유한 자산과 테스트를 임시 Git fixture에 복사합니다. 남겨 둘 경로를 `--target`으로 지정한다면 아직 존재하지 않아야 합니다. 선택자는 fixture의 pytest 실행 범위를 좁힙니다. 전체 소스·패키지 과정은 [자산 개발](assets.md)에 있습니다.

일반 소스 편집과 테스트는 네이티브 도구를 사용하며 `material_*`, `verification_*` 원장에 중복 기록할 필요가 없습니다. 프로젝트 검증 명령을 연결하면 설정과 실행 전후 작업 트리 지문을 가진 결과 기록을 추가로 남깁니다. 검증 도중 작업 트리가 바뀌거나, 제한 시간이 지나거나, 설정한 성공 조건을 만족하지 못하면 실패합니다. 정확한 설정은 [설정 참조](setup-reference.md#프로젝트-검증-명령-설정하기)에 있습니다.

## 체크아웃 밖에서 배포본 검사하기

현재 후보를 빌드한 뒤 실제 wheel 경로를 사용합니다.

```sh
uv build
uv run --locked python tools/validate_distribution.py dist/neurath-0.1.0-py3-none-any.whl --output PRIVATE_DISTRIBUTION_REPORT.json
uv run --locked python tools/validate_setup.py --output PRIVATE_SETUP_REPORT.json
uv run --locked python tools/validate_updates.py dist/neurath-0.1.0-py3-none-any.whl --output PRIVATE_UPDATE_REPORT.json
```

예시 버전은 현재 패키지 소스의 버전이며 실제 빌드한 파일 이름을 사용해야 합니다. 비용이 있는 배포 검증 절차이므로 문서 수정의 자동 요구사항으로 적용하지 않습니다.

배포 검증기는 외부의 새 Python 3.14 환경에 wheel을 설치하고 빈 저장소, Python 저장소, JavaScript 저장소를 다룹니다. 재설치가 변경 없이 끝나는지, 설정 보존·호스트 변경·진단·제거가 동작하는지, 소스 체크아웃 접근을 차단해도 독립적으로 import하는지 확인합니다. 검증 전후 wheel 다이제스트도 기록합니다.

설정 검증기는 최소 시스템 경로에서 공식 `uv`·Python 초기 설치를 수행하며 공백, 따옴표, 한글이 있는 경로도 다룹니다. 기존 의존성과 훅을 보존하고 실행기 검사 전에 소스 위치를 옮기며 자기 설치를 두 번 수행합니다. 업데이트 검증기는 실제 후보 wheel과 보존·복구 동작을 다룹니다. 이 로컬 절차가 모두 성공해도 실제 호스트 활성화는 미확인일 수 있습니다.

## 실제 네이티브 실행 관찰하기

설치는 관리 파일과 선택한 런타임이 있는 상태입니다. 활성화는 실제 이벤트에서 호스트가 이를 불러온 상태입니다. 네이티브 검증을 시작할 때 설치, 호스트 신뢰, 노출된 도구, 유효 실행 정책, 작업 트리 소유권을 확인합니다. 발견한 동료, 수락된 할당, 체크포인트는 소유권을 증명하지 않습니다. Claim에는 실제 반환된 lease epoch와 fencing 값이 필요하며, 임의 ID가 호스트·주체·턴을 증명하지는 못합니다.

원시 호스트 이벤트에서 의도한 태스크와 턴 하나를 선택합니다. 예상된 거부가 있다면 그것까지 포함해 해당 범위의 네이티브 도구 실행과 반환 상태를 확인합니다. `tools/native_evidence.py`는 다른 턴의 성공, 모델의 주장만 있는 결과, 예상하지 않은 훅 차단, 정확한 명령 결과가 없는 경우를 거부합니다. 일반 호스트 세션 종료는 재개할 태스크와 claim을 유지할 수 있으며, 영구적인 커널 세션 종료와 구분합니다.

수명주기 시나리오에서는 시작, 실제 사용자 방향 수정·재개, 미완료 작업 지속, 결과 수락, 필요한 최종 소유권 해제를 실행합니다. 완료에는 커널 선행 조건이 계속 필요하며, 명시적인 awaiting-input 기록은 미완료 태스크를 보존한 채 제어를 반환하는지 확인합니다. 제어 반환은 태스크 완료가 아닙니다. 오래된 Stop 진단으로 새 턴을 닫아서는 안 됩니다. 목표 리마인더는 태스크 결정과 주기적 작업 판단을 돕지만 권한을 부여하거나 무인 세션을 시작하지 않습니다. 세부 동작은 [런타임 수명주기](runtime-lifecycle.md)에 있습니다.

독립 평가는 실제 지원되는 직접 자식, 검증된 계보·역할, 정확한 후보, 인증된 보고와 그 소비를 관찰합니다. 위임 준비는 생성 의도를 기록할 뿐입니다. 동료 보고를 받았다는 사실만으로 평가자 권한이 생기지 않습니다. 후보 변경과 오래된 리비전을 드러내야 합니다.

## 협업과 복구는 관찰한 사례별로 검증하기

Provider 검사는 생성자·수신자 방향, 모델 목록·계획과 실제 선택 모델, 바로 위 생성자의 정책, 준비 상태, 할당, idle 전달, 결과 전달·읽기·ACK, 종료 상태를 구분합니다. 주장하는 기능에 맞춰 송신 전후 프로세스 종료, ACK 유실, 장기 작업 취소도 다룹니다. `accepted`, 프로세스 생성, 취소 요청은 각각의 완료 결과보다 앞선 상태입니다. 개별 요청의 제한 시간이 전체 태스크 수명을 제한하지는 않습니다. [Provider 전송](provider-transports.md)과 [모델 계획](model-planning-mcp.md)을 참고하세요.

수신자가 시작하는 memory pull은 미리보기·읽기와 채택의 근거가 다릅니다. 채택에는 정확한 불변 미리보기, 현재 수신자 리비전, 조용한 원본 상태, 태스크·lease의 원자적 이전이 필요합니다. 체크포인트는 소유자의 보고이며 태스크 완료나 해제가 아닙니다. 실제로 관찰한 네이티브 provider 간 복구 방향만 보고합니다. 사용량 소진 경계를 시뮬레이션했다면 그 사례만 확인한 것이므로 실제 계정 한도 소진을 검증했다고 주장할 수 없습니다. 학습은 같은 실패·성공 작업과 필요한 별도 노출 세션의 검사를 요구합니다. [메모리 참조](memory-reference.md)를 참고하세요.

모니터도 실행 접수, 첫 관찰, 이벤트 확인, 소유자 재개, 최종 취소를 나눠 확인합니다. 복구에는 이전 프로세스가 실제 종료했으며 현재 소유자의 정책이 지원된다는 근거가 필요합니다. 이벤트가 새 사용자 권한을 만들지는 않습니다. [협업 계약](collaboration-contract.md)을 참고하세요.

앱 소속도 별도 관찰입니다. `session_status.app_project`는 제한된 로컬 소속 상태를 `assigned`, `unassigned`, `unobserved`로 알려 줍니다. Provider의 프로젝트 메타데이터만으로 앱 소속을 증명할 수 없습니다. 앱에서 생성한 전달은 새 사용자 승인을 만들지 않고 네이티브 턴을 성립시킬 수 있습니다. 이를 실행 정책·메모리 채택과 구분합니다.

## 후보와 남은 범위를 보고하기

무엇이 바뀌었고 어떤 검사를 실제 실행했으며 그 결과가 무엇을 뒷받침하는지 설명합니다. 소스 검사, 패키지 설치, 자기 설치, 네이티브 활성화, 리뷰·병합, 공개 릴리스를 나눠 보고합니다. 일부 사례만 확인했다면 관찰한 경우와 미확인 범위를 밝힙니다. Fixture나 로컬 프로토콜 검사가 모든 네이티브 상황의 통과를 뜻하지는 않습니다.

두 언어 문서는 같은 상대 경로를 사용하며, 번역 링크를 제외한 탐색은 같은 언어로 연결합니다. GitHub 생성, push, 공개 릴리스에는 별도 권한이 필요합니다. 검증을 수행했다는 사실이 이를 승인하지는 않습니다.
