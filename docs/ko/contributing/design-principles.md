# 목표를 유지하며 작업을 이어가기 위한 설계 원칙

[English](../../en/contributing/design-principles.md)

코딩 에이전트는 효과가 없는 방법을 바꾸면서도 사용자가 요청한 결과를 계속 추구해야 합니다. Neurath는 이 구분을 영속 상태에 드러냅니다. 새로고침 후 저장한 필터가 사라지는 문제라면 목표는 저장·재조회 이후의 필터 유지입니다. 특정 디버깅 명령, 구현 계획, 리뷰어는 그 목표에 도달하는 방법입니다.

아래에서 **태스크**는 목표·지시 출처·관찰 가능한 **완료 조건**을 연결한 기록을 뜻합니다. 호스트 **세션**의 **루트 에이전트**가 태스크 목록을 소유합니다. **워크트리 claim**은 체크아웃의 작업 소유권을 기록합니다. **receipt**는 출처가 정해진 이벤트나 보고입니다. **phase**는 스킬의 절차를 나누고 **리뷰**는 정해진 범위를 평가합니다. 요소 간 관계는 [아키텍처](architecture.md)에 설명되어 있습니다.

## 요청한 결과는 유지하고 방법은 바꿀 수 있게 한다

태스크 정의는 목표, 지시 출처의 리비전, 완료 조건을 보존합니다. 소유자는 아직 충족하지 못한 요구에 기여하는 작업을 선택하고 이미 요구를 충족한 결과를 재사용합니다. 필요한 후속 작업이 구체화되면 현재 태스크를 마치기 전에 목록에 기록합니다.

시도한 저장 방식이 실패했다면 새 구현 작업이 필요할 수 있습니다. 그렇다고 저장·새로고침 동작을 포기하거나 관계없는 프레임워크 재작성을 시작할 근거가 되지는 않습니다. 시도의 실제 결과와 기록을 남기고 원래 요구에서 남은 작업을 정의합니다. 상태 질문은 대화 문맥을 더하지만 그 자체로 새 범위를 승인하지 않습니다.

태스크 도구와 자동 목표 알림이 이 판단을 돕습니다. 알림은 참고 문맥입니다. 태스크의 필요성을 자동 판정하는 분류기나 별도 완료 장부가 아닙니다.

## 태스크 완료의 기준은 하나의 목록에 둔다

태스크 원장은 `pending`, `in_progress`, `succeeded`, `failed`, `invalidated`를 기록합니다. 호스트 TODO는 이 기록을 더 적은 수의 화면 상태로 표시합니다. 표시를 갱신해도 태스크 성공이 만들어지지 않습니다. phase나 체크포인트에 “completed”를 써도 태스크 결과 기록을 대신할 수 없습니다.

완료 상태를 중복 관리하지 않되 서로 다른 질문에 답하는 검사는 유지합니다. 현재 신원, 소유권, 정확한 리비전, 위임 결과, 전경 턴이 이에 해당합니다. 모든 실행이 종료된 것과 모든 결과가 성공한 것의 차이는 [태스크와 TODO 계약](task-todo-contract.md)을 참고하세요.

## 실제 행동 주체는 호스트가 입증한다

호스트가 세션·에이전트·지시·호출의 근거를 제공합니다. 이름이 정해진 MCP 호출은 호스트가 발급한 정확한 연결을 사용합니다. 인자에 세션이나 프로젝트를 적는 것은 대상을 지정하는 것이며 호출자를 인증하는 행위가 아닙니다.

구현 에이전트가 다른 에이전트에게 필터 API 리뷰를 맡길 때 이 구분이 중요합니다. 같은 세션의 하위 에이전트와 독립 제공자 세션은 호스트 신원과 실행 구성이 다릅니다. 작업 배정 기록이나 `prepared` 결과만으로 실제 실행을 입증할 수 없습니다. 부모가 프롬프트에 식별자를 넣었다고 해서 자식이 루트의 쓰기 권한을 물려받지도 않습니다.

## 소유권을 현재 작업 위치에 명시한다

워크트리 claim은 체크아웃의 작업 소유자를 조정합니다. 상태 조회 성공은 claim 획득도 아니고 다른 에이전트의 소유권을 대신하는 행위도 아닙니다. 해제에는 관찰한 lease epoch와 fencing token이 필요합니다. 늦게 도착한 해제 요청이 새 소유자를 해제하지 못하게 하기 위해서입니다.

소유권과 호스트 권한도 다릅니다. 유효한 claim이 샌드박스를 넓히거나 외부 작업을 승인하지는 않습니다. 제공자 계획은 실행 정책을 상속하거나 명시적으로 비교합니다. 구현은 라우팅 성공을 정책 근거로 취급하지 않고 설정 불일치를 거부합니다.

## 조건을 확인해 상태를 바꾸고 같은 요청을 재현할 수 있게 한다

상태 변경에는 호출자가 관찰한 상태와 현재 상태를 비교하는 리비전을 사용합니다. 멱등성 키는 하나의 논리적 작업을 식별합니다. 같은 키와 같은 내용으로 다시 호출하면 기록된 결과를 반환할 수 있지만 같은 키에 다른 내용을 넣으면 거부합니다.

두 장치는 서로 다른 문제를 해결합니다. 리비전은 오래된 관찰이 새 상태를 덮어쓰는 것을 막고 멱등성은 응답이 불확실할 때 이미 접수된 작업이 중복되는 것을 막습니다. 어느 쪽도 새 리비전을 추측하거나 요청을 바꾸면서 이전 키를 재사용할 근거가 되지 않습니다.

예를 들어 API 리뷰에서 새 근거가 도착했다면 소유자는 필터 태스크를 마치기 전에 현재 상태를 다시 읽습니다. 리뷰 전의 목록 리비전이 아직 유효하다고 가정하지 않습니다.

## 근거가 입증하는 범위를 정확히 설명한다

호스트 도구 제출, 태스크 결과 보고, 리뷰 수용, 설치, 앱 관찰은 각각 다른 사실을 입증합니다. 태스크 결과 artifact는 소유자·정의·참조·보고를 식별합니다. `agent-report`라는 보장 수준은 의미를 독립 검증했다는 주장까지 포함하지 않습니다.

제공자 실행도 마찬가지입니다. `accepted`는 영속 실행 접수를, 생명주기 이벤트는 진행 상태를, 인증된 최종 결과는 평가할 내용을 제공합니다. 메시지 ACK는 수신자가 읽었다는 기록입니다. 소유자는 보고된 동작이 태스크 완료 조건을 충족하는지 별도로 판단해야 합니다.

## 중단을 거쳐도 미완료 작업을 보존한다

메모리는 문맥을 저장하고 명시적 이전을 지원합니다. 체크포인트는 에이전트가 작성한 인계 기록이고 미리보기는 참고 자료입니다. adopt는 원본이 정지했는지와 리비전을 확인하는 별도 상태 변경이며 원본 세션을 사칭하지 않습니다. 이전이 반영되면 원본의 실행 쓰기를 차단하고 이전 결과 기록을 유지합니다.

필터 예시의 좋은 인계에는 저장·새로고침 재현, 변경한 저장 경로, API 리뷰 결과, 남은 관찰, 검증된 프로젝트 테스트 명령이 들어갑니다. 받는 세션은 이미 수행한 명령을 전부 반복하지 않고 이 근거를 이용해 같은 목표를 계속 수행합니다.

## 정상 Stop은 현재 도메인의 조건을 충족해야 한다

Neurath는 커널 선행 조건이 충족될 때까지 현재의 모든 정상 Stop을 거부합니다. 상태 질문, 경과 시간, 반복된 거부, `stop_hook_active`에는 예외가 없습니다. 사용자의 명시적 중단은 별도로 호스트가 처리합니다.

Stop 어댑터는 호스트에 계속 실행을 요청하기 전에 현재 루트·턴·transcript·연결을 다시 확인합니다. 오래되거나 다른 주체의 이벤트는 새로운 작업을 닫거나 다른 실행 턴의 권한을 만들 수 없습니다. 거부가 발생하면 실제 미해결 조건을 확인하고 해결해야 합니다. 거부 자체는 태스크 실패나 취소의 근거가 아닙니다.

## 개발 환경에 의존하지 않는 제품을 유지한다

실행 자산은 패키지가 소유합니다. 설치 대상은 기존 지침·훅·권한·의존성을 유지합니다. 공개 문서는 지원 동작과 재현을 설명하며 비공개 저장소 출처, 로컬 런타임 상태, 설치 receipt를 포함하지 않습니다.

Neurath를 확장할 때는 요구가 속하는 경계에 구현합니다. 호스트 근거는 어댑터에, 도메인 불변식은 커널에, 입력 계약은 스키마에, 재사용할 절차는 원본 스킬에 둡니다. 검증도 그 경계를 관찰하게 만듭니다. 이미 존재하는 판단을 반복하려고 새 장부·상태 플래그·게이트를 추가하지 않습니다.

상태 전이는 [실행 생명주기](runtime-lifecycle.md), 정확한 호출은 [태스크 도구](task-tools.md)를 참고하세요.
