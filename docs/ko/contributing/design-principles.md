# 설계 원칙과 하네스 철학

[English](../../en/contributing/design-principles.md) · **한국어**

[아키텍처](architecture.md) · [실행 수명주기](runtime-lifecycle.md) · [기능 지도](capability-map.md)

Neurath의 설계는 **에이전트가 계속 일할 수 있게 하면서, 그 판단과 실행의 근거를 잃지 않는 것**으로 해석할 수 있습니다. 이 문장은 구현 전반을 종합한 설명이며 프로젝트 이름의 유래나 작성자의 개인적 철학을 주장하지 않습니다. 아래에서는 명시된 정책, 코드가 집행하는 조건, 그로부터 도출한 설계 해석을 연결합니다.

## 원칙과 비용

| 원칙 | 실제 장치 | 얻는 것 | 부담과 한계 |
| --- | --- | --- | --- |
| 현재 의도에 충실하기 | 목표·비목표·제약·수용 기준·입력 출처 | 과거 작업이나 동료 요청으로 목표가 바뀌는 것 방지 | 모호한 사용자 결정은 추가 확인 필요 |
| 권한의 출처 유지 | 네이티브 신원·호출 결속·권한 승계 | 문자열로 권한을 자칭하는 오류 차단 | 호스트 관측이 없으면 일부 실행이 막힘 |
| 효과를 관측하기 | 기준 상태·도구 결과·변경 후 대조 | 말로 한 완료와 실제 효과 구분 | 중단·실패 결과의 대조 비용 |
| 독립적으로 반증하기 | 분리된 검토자·근거 소비·finding 정리 | 작성자의 자기 확신에만 의존하지 않음 | 검토자와 평가 실행 비용 |
| 맥락을 이어 가기 | 공유 기억·Enclave·Graphify | 재탐색 비용 감소 | 오래된 정보는 현재 소스로 재확인 |
| 학습을 되돌릴 수 있게 하기 | candidate·trial·active·reverted·stale | 나쁜 전략을 계속 적용하는 것 방지 | 성공 한 번으로 즉시 일반화하지 못함 |
| 전달을 포기하지 않기 | 영속 메시지·안정된 ID·재전달·ACK | 일시 장애로 인한 메시지 누락 억제 | 중복 수신 가능; 효과의 단일 실행은 별도 문제 |
| 기존 환경과 공존하기 | 독립 번들·보존적 병합·저널·복구 | 프로젝트의 지침과 개발환경 유지 | 관리 파일 충돌을 임의 덮어쓸 수 없음 |
| 사용자에게 운영 부담을 넘기지 않기 | 자연어 요청·명명된 작업·에이전트 실행 | 사용자는 목표와 결정을 중심으로 작업 | 실제 인증·신뢰 결정은 호스트에서 필요할 수 있음 |

## 1. 의도는 현재 입력에서, 사실은 해당 소유자에게서

작업 절차는 요청의 단어보다 주된 목적과 입력 근거로 선택합니다. 코드 설명과 코드 수정, 승인된 이슈 구현과 새 제품 설계는 다른 작업입니다. `GoalContract`와 `GapInventory`는 목표·수용 기준과 미해결 질문을 표현하며, 질문을 사용자 결정, 저장소 사실, 국소적이고 되돌릴 수 있는 가정으로 구분합니다.

이 구분의 설계상 의미는 “알 수 없는 것을 모두 사용자에게 묻기”도 “에이전트가 모두 채워 넣기”도 적절하지 않다는 것입니다. 저장소에서 확인할 수 있는 사실은 조사하고, 기존 승인 안에서 가능한 작업은 진행하며, 사용자가 소유한 결정만 적절한 입력 경계로 돌려보냅니다.

근거: [적응 제어 모델](../../../src/neurath/_assets/scripts/agent_harness/adaptive_control.py), [정책 원본](../../../src/neurath/install/projection.py), [프로젝트 연결](../usage/profiles.md).

## 2. 권한은 문구가 아니라 실제 실행 관계

“나는 부모의 자식이다”, “이 모드로 실행했다”, “사용자가 승인했다”는 도구 출력만으로 사실이 되지 않습니다. 호스트의 세션·프로세스·턴·호출 근거와 실제 정책을 대조해야 합니다. `StateHandle`과 worktree 소유권은 기억 저장소나 동료 주소록과 별도로 검사합니다.

MCP는 에이전트가 하네스를 운용하는 표면입니다. 현재는 통신뿐 아니라 상태·검증·provider·모델·유지보수 작업도 포함합니다. 다만 범용 셸이나 임의 파일 편집 API를 제공하지 않으며, 실행 작업에는 해당 정책과 소유권 검사가 적용됩니다. 도구 스키마에 설정 필드가 있다는 사실은 그 모드의 제약을 MCP가 집행한다는 증거가 아닙니다.

근거: [호스트 신원](../../../src/neurath/hosts/identity.py), [MCP 호출 결속](../../../src/neurath/agents/mcp.py), [작업 dispatch](../../../src/neurath/runtime/tasks.py), [권한 승계](../../../src/neurath/providers/permission_inheritance.py).

## 3. 계획, 실행, 관측, 수락을 구분하기

```mermaid
flowchart LR
    P[계획과 승인 범위] --> B[대상 기준 상태]
    B --> X[실제 도구 실행]
    X --> O[실행 결과와 변경 후 관측]
    O --> E[독립 검토와 목표 대조]
    E --> C[소유자의 근거 소비]
    C --> F[계약에 따른 종료]
    X --> U[결과 미확인]
    U --> R[상태 조사와 대조]
    R --> O
```

이 그림은 증거의 책임 흐름입니다. 모든 간단한 읽기에 workflow를 만들라는 뜻은 아닙니다. 상태를 소유하는 작업에서는 준비가 실행을 대신하지 않고, 성공 종료 코드가 목표 달성을 대신하지 않으며, 검토 보고가 자동 수락을 대신하지 않습니다.

등록 검사는 정확한 argv·cwd·성공 조건을 실행하고 변경 전후 저장소 지문을 비교합니다. 실행 중 파일이 달라졌다면 성공 코드라도 해당 검증은 실패입니다. 독립 평가는 목표·소스 revision·후보 산출물·근거의 출처를 연결합니다. 다른 테스트의 통과를 원하는 동작의 증거로 바꾸지 않습니다.

근거: [변경 작업](../../../src/neurath/_assets/scripts/agent_harness/material_action.py), [등록 검사](../../../src/neurath/runtime/verification.py), [평가 권한](../../../src/neurath/_assets/scripts/agent_harness/adaptive_control_authority.py).

## 4. 건설적 회의주의: 반증할 수 있는 의문만 남기기

소스의 `Constructive Skeptic` 정책은 유용한 반론과 근거 있는 의문을 강조합니다. 검토는 막연한 불신이나 스타일 취향을 결함으로 바꾸는 절차가 아닙니다. 재현 가능한 문제, 영향을 받는 동작과 근거를 연결하고 같은 근본 원인의 finding은 정리해야 합니다.

`EvaluationLoop`는 finding의 정리와 평가 회차를, 적응 제어는 목표 충족·모호성·정체와 회복을 표현합니다. 자원 사용 관측도 결과 변화와 연결합니다. 따라서 “검사를 많이 했다”는 사실보다 “어떤 불확실성이나 결함을 해결했는가”가 중요하다는 설계 해석이 가능합니다.

근거: [검토 태도 정책](../../../src/neurath/_assets/scripts/harness_persona_policy.py), [평가 루프](../../../src/neurath/_assets/scripts/agent_harness/evaluation_loop.py), [효율 관측](../../../src/neurath/_assets/scripts/agent_harness/efficiency_assessment.py).

## 5. 기억은 연속성을 제공하고 권한은 현재 상태에서 확인하기

| 장치 | 답하는 질문 | 권위와 범위 |
| --- | --- | --- |
| ProjectMemory | 이전 작업의 목표·결정·남은 일은 무엇인가 | 프로젝트 공유 참고 기록 |
| EnclaveStore | 이 세션이 이어 가야 할 현재 사실은 무엇인가 | 세션 내부의 제한된 최신 사실 스냅샷 |
| Graphify | 코드·문서·개념이 어떻게 연결되는가 | 탐색용 지식 그래프; 현재 소스로 확인 |
| 실행 전략 학습 | 관측된 실패에서 어떤 실행 방법이 회복했는가 | 검증과 철회가 있는 제한된 전략 |
| memory-to-rules | 반복된 개인 선호를 프로젝트 규칙으로 옮길 것인가 | 검토·승인을 거치는 별도 문서 변경 |

기억이 있다고 현재 worktree의 소유권을 얻는 것은 아닙니다. 인계에 완료라고 기록해도 workflow 종료 조건을 통과한 것은 아닙니다. 그래프의 오래된 경로나 연결은 탐색 단서로만 쓰고 현재 파일을 읽어야 합니다. 이 분리가 세션 간 연속성을 제공하면서 과거의 지시나 잘못된 가정이 굳어지는 것을 억제합니다.

근거: [공유 기억](../../../src/neurath/memory/store.py), [Enclave](../../../src/neurath/_assets/scripts/agent_harness/enclave_store.py), [Graphify 스킬](../../../src/neurath/_assets/.agents/skills/graphify/SKILL.md), [규칙 승격 스킬](../../../src/neurath/_assets/.agents/skills/promote-memory/SKILL.md).

## 6. 학습의 성공 기준에는 철회도 포함하기

명령 실행 학습은 같은 명령 계열의 실패와 성공한 대안을 관측하는 것에서 시작합니다. 명령 계열은 테스트 선택 인자까지 유지하므로 무관한 테스트 성공을 회복으로 쓰지 않습니다. 출처 세션의 검사가 trial을 허용하고, 전략을 실제로 전달받은 다른 세션의 동일 전략 실행과 검사 성공이 active 전환의 근거가 됩니다.

후속 실패는 reverted, 연결된 검증 계약 변경은 stale로 이어질 수 있습니다. 검사를 할 수 없어 defer해도 성공으로 바뀌지 않습니다. 이는 하네스 소스나 정책을 자동 수정하는 일반적 자기 개선과 범위가 다릅니다. 상세 전이는 [실행 수명주기](runtime-lifecycle.md)에 있습니다.

근거: [학습 구현](../../../src/neurath/memory/learning.py), [학습 회귀](../../../tests/test_learning.py).

## 7. 메시지는 다시 전달하고, 불확실한 변경은 먼저 대조하기

동료 메시지는 저장한 뒤 알리고, ACK가 없으면 같은 ID·key·본문으로 다시 전달할 수 있습니다. `at-least-once`는 중복 수신을 허용하는 전달 계약입니다. ACK는 본문 수신을 뜻하며, 요청한 작업의 효과가 정확히 한 번 실행됐거나 결과가 수락됐다는 뜻이 아닙니다.

설치·업데이트·보고 같은 변경은 별도 요청 기록과 대조 규칙을 사용합니다. 결과가 uncertain일 때 다른 도구로 같은 변경을 곧바로 반복할 권한은 생기지 않습니다. 메시지 재전달 원칙을 모든 변경 작업의 재실행 정책으로 일반화해서는 안 됩니다.

근거: [메시지 저장소](../../../src/neurath/agents/store.py), [전달 서비스](../../../src/neurath/agents/delivery.py), [유지보수 작업](../../../src/neurath/runtime/maintenance_tasks.py).

## 8. 실패를 숨기지 않으면서 사용자 개입은 계속 전달하기

루트 사용자 입력 경계는 내부 bookkeeping 실패가 사용자의 새 지시를 막지 않도록 설계되어 있습니다. `bookkeeping deferred` 진단을 전달하되 상태 갱신이나 도구 권한이 성공했다고 간주하지 않습니다. 반면 신원·소유권·변경 결과가 필요한 실행은 근거가 없으면 계속 제한됩니다.

이것은 모든 오류를 허용한다는 정책이 아닙니다. 사람의 개입 통로와 실행 권한 검사를 분리한 것입니다. 에이전트의 일반 작업 수명에는 timeout을 두지 않는 provider 계약과, 개별 검사·연결·요청의 제한 시간도 같은 이유로 구분합니다.

근거: [호스트 이벤트 처리](../../../src/neurath/hosts/hooks.py), [입력 전달 회귀](../../../tests/test_prompt_delivery.py), [소유 연결](../../../src/neurath/providers/supervision.py).

## 9. 설치와 개선은 되돌릴 수 있어야 하기

설치 계획은 대상, 배포 내용과 변경 전후 bytes·mode·link를 결속합니다. 적용 직전 현재 상태를 다시 확인하고 잠금·저널·원자적 파일 교체를 사용합니다. 복구가 필요한 경우 기존 기록을 사용하며, 동시에 바뀐 사용자 파일은 보존합니다. 독립 번들·환경과 보존적 설치는 특정 스택에 종속되지 않는 하네스라는 제품 경계를 구현합니다.

공통 결함 보고와 프로젝트 전용 기여도 구분합니다. 공통 보고 동의가 전용 코드의 공개 승인이 되지는 않으며, 업데이트의 정확한 대상 확인과 설치 동의도 별도입니다. 공개 문서에는 개인 경로·세션 기록·설치 원문을 넣지 않습니다.

근거: [설치 트랜잭션](../../../src/neurath/install/transaction.py), [업데이트 적용](../../../src/neurath/release_install.py), [보고](../../../src/neurath/reporting.py), [네이티브 사용자 선택](../../../src/neurath/runtime/user_choices.py).

## 설계 판단에 적용하기

새 기능을 설명하거나 수정할 때는 다음 질문을 사용할 수 있습니다. 이는 새로운 실행 gate를 추가하는 규칙이 아니라 위 원칙을 점검하기 위한 독해 도구입니다.

1. 목표와 성공 기준을 누가 소유하며, 어떤 현재 근거로 확인하는가?
2. 안내 문구와 실제로 집행되는 조건은 어디서 나뉘는가?
3. 접수·시작·관측·수락·종료 중 어느 상태를 보고하는가?
4. 실패·중단·중복·오래된 revision에서 무엇이 보존되는가?
5. 해당 테스트는 어떤 성질을 증명하며, 실제 호스트에서는 무엇을 더 관측해야 하는가?

## 발견 가능한 도구 계약으로 탐색 비용 줄이기

하네스 사용법을 기억하도록 긴 CLI 사용 설명을 주입하는 대신, 현재 서버가 제공하는 도구 이름과 입력
