# 요청 작업과 네이티브 TODO 표시 계약

작업 원장은 사용자가 이루려던 결과를 보존한다. 호스트의 계획·TODO 목록은 수행 중인 일을 화면에 보여 준다. 작업 상태의 기준은 원장이며 화면은 그 투영이다. 표시가 늦거나 실패해도 기록된 작업 결과는 바뀌지 않는다.

## 측정 가능한 작업을 정의한다

각 작업에는 안정적인 ID, 리비전, 그리고 `key`, `title`, `goal`, `sources`, `acceptance`, `dependencies`가 들어 있는 정의가 있다. 출처는 `kind`(`prompt`, `ticket`, `spec`), `reference`, `revision`을 기록한다. 출처 리비전과 완료 조건도 정의 해시에 포함되므로 결과를 다른 목표에 조용히 옮겨 붙일 수 없다.

작업 변경은 활성 전면 턴에 있는 인증된 네이티브 루트 소유자만 할 수 있다. 작업 접수에는 실제 사용자 지시 수신 근거가 필요하다. `sources`에 프롬프트 출처가 없으면 현재 프롬프트 근거를 자동으로 보존한다. 직접 넣은 프롬프트 출처는 해당 소유자의 기존 수신 근거와 일치해야 하며 만든 참조는 거부한다.

`task_define`은 이전 작업 이력과 의존 관계를 보존하면서 정의를 추가한다. 작업 키는 세션 안에서 정의의 안정적인 신원을 제공한다. 의존 관계에는 제목이나 임의 ID 대신 반환받은 작업 ID를 사용한다. 요청이 대체되면 기존 종료 이력을 남기고 새로 측정 가능한 작업을 추가한다.

## 작업이 구체화될 때 후속 태스크 등록하기

태스크는 단계적으로 정의합니다. 처음에는 사용자가 요청한 결과와 현재 파악한 작업을 등록합니다. 조사·구현·검증 중 필요한 다음 작업이 드러나면 보고서에만 남기지 않고 `task_define`으로 등록합니다. 추가하거나 선택하기 전에 어떤 미충족 요구를 해결하는지, 기존 결과로 이미 충족됐는지, 선택한 방법을 완벽하게 만들려고 범위를 넓히는지를 판단합니다. 기존 `goal`·`acceptance`에 필요한 범위와 관측 가능한 결과를 담고 원래 지시의 `sources`를 연결합니다. 별도 판단 스키마나 승인 단계는 만들지 않습니다.

`task_resolve` 전에 발견한 필수 후속 작업이 등록돼 있는지 확인합니다. 과거 종료 기록은 보존하고 이후 결과와 대조하여 여전히 필요한 부분만 `task_define`·`task_start`로 이어갑니다. 완료한 일을 중복 등록하거나 취소된 요구를 다시 열지 않으며, 답변만 요청한 턴에서 실행을 시작하지 않습니다. 태스크 수를 줄이려고 필요한 일을 누락하거나, 수를 채우려고 일을 만들지 않습니다.

주기적인 환기와 함께, 인증된 루트의 태스크 변경 도구 세 가지에 대한 `PreToolUse` 훅에서도 호출별로 크기가 제한된 목표 환기를 전달합니다. 원장이 비어 있는 최초 정의도 포함하며 대상 태스크가 있으면 먼저 보여 줍니다. 도구 설명은 호출을 선택하기 전 같은 판단을 안내합니다. 환기는 원장·네이티브 권한·기존 훅 결정을 변경하지 않으며 관련성과 범위는 에이전트가 판단합니다. 전달 여부와 상태 보존은 테스트할 수 있지만 모든 의미 판단의 정확성을 보장하지는 않습니다.

## 상태와 의존 관계

| 상태 | 의미 | 네이티브 표시 상태 |
| --- | --- | --- |
| `pending` | 정의되었지만 시작하지 않은 작업 | `pending` |
| `in_progress` | 시작한 작업 | 첫 활성 행은 `in_progress`, 추가 활성 행은 `pending` |
| `succeeded` | 소유자가 완료 조건 달성을 보고함 | `completed`, 행 본문에 `Succeeded` 표시 |
| `failed` | 소유자가 실제 종료 실패를 기록함 | `completed`, 행 본문에 `Failed` 표시 |
| `invalidated` | 실제 취소나 대체 결정을 기록함 | `completed`, 행 본문에 `Invalidated` 표시 |

두 호스트의 시각적 상태는 세 가지다. 따라서 읽을 수 있는 행 본문에 다섯 가지 작업 결과와 병렬 진행 상태를 남긴다. 활성 표시가 한 행뿐이라고 실제 진행 작업도 하나라는 뜻은 아니다.

`task_start`는 의존 작업이 모두 종료된 대기 작업만 받는다. 별도 시작을 기록하지 않았더라도 `succeeded` 확정에는 의존 작업의 종료가 필요하다. `failed`, `invalidated`는 의존 작업이 미해결이어도 기록할 수 있다. 의존 작업 자체가 실패나 무효화로 끝났을 수도 있다. 이 조건은 순서를 보장하며 종속 작업의 성공 주장은 여전히 그 작업의 완료 조건에 맞아야 한다.

종료 작업에는 불변 근거가 있고 화면 편집으로 다시 열 수 없다. 실패와 무효화는 실제 결과를 설명해야 하며 미완료 요청을 숨기는 수단이 아니다.

## 결과를 한 번 기록한다

`task_resolve`에는 정확한 작업·목록 리비전, 종료 상태, 간결한 요약, 서로 다른 참조 1~32개를 전달한다. 참조는 결과와 관련된 실제 소스, 검사, PR, 취소 결정을 가리킬 수 있다. 서비스는 작업 ID, 정의 해시, 소유자, 상태, 참조, 요약을 묶은 결과 보고를 내용 해시로 저장한다.

보고 형식은 `schema=neurath.task-result.v1`, 보증 수준은 `assurance=agent-report`다. 누가 무엇을 보고했는지 인증하지만 모든 완료 조건을 독립적으로 인증하지는 않는다. 일반 완료에 별도 material batch, 워크플로, 조건별 보고서, 독립 작업 검토자는 필요하지 않다. 명시적으로 요청한 검토 워크플로는 자체 평가 계약을 유지한다.

다음 호출에는 변경 결과에서 받은 리비전을 사용한다. 오래된 리비전은 `revision-conflict`를 반환한다. 실제 충돌이나 중단 후 다시 읽고, 결과가 불확실한 동일 요청에만 같은 키를 유지한다. 요청을 바꾸면 새 키가 필요하며 동일 키의 다른 입력은 거부한다.

### 실행 종결과 목표 달성을 구분한다

`all_terminal`은 실행 기록이 모두 끝났다는 뜻이다. `all_succeeded`는 비어 있지 않은 목록의 모든 작업이 성공했을 때만 참이며, `unsuccessful_task_ids`는 실패·무효화된 작업을 가리킨다. 모두 같은 소유자 보고 원장의 표시이며 독립 인증이 아니다. 한 시도의 실패, Stop 거부, 경과 시간, 상태 질문을 사용자 목표의 취소 근거로 삼지 않는다. 실패를 보고할 때는 미달 조건, 실제 장애, 다음 행동을 남긴다.

작업 등록에는 검증된 네이티브 사용자 지시 출처가 필요하다. 동료 메시지로 재개되어 `current_prompt_source`가 null이어도 동일 세션에 보존된 실제 프롬프트 출처를 명시해 사용할 수 있다. 요청의 각 작업이 그 출처를 제공해야 하며, 서비스는 소유자·참조·해시를 검사하고 새 사용자 입력 기록을 만들지 않는다. 원장에서 아직 참조하지 않은 프롬프트 뒤에도 관련 출처를 명시적으로 선택한다. 출처를 보존했다고 확장된 범위가 의미상 승인된 것은 아니다. 주기적 [목표 환기](runtime-lifecycle.md)는 원장을 바꾸지 않고 이 구분을 유지하도록 돕는다.

이 재개 턴에서 네이티브 자식을 준비할 때는 진행 중인 작업의 `task_id`와 `expected_task_revision`을 `delegation_prepare`에 함께 전달한다. 준비 기록은 작업 정의를 현재 네이티브 세대·턴에 결속하며 생성·연결과 트랜잭션 저장 시점에 다시 검사한다. 완료한 작업이나 이전 턴의 결속으로 새 자식 작업을 허용하지 않는다. 실제 부모·자식 확인과 현재 실행 권한도 필요하며, 동료 메시지 수락만으로 이 권한을 얻지는 않는다.

이미 실행된 자식은 부모 태스크가 끝나도 명명 도구 `artifact_put`과 `evaluation_report`로 결과를 저장·보고할 수 있다. 기존 위임과 보존된 지시 출처에 결속된 예외이며, 추가 실행이나 자식 자신의 결과 수락을 허용하지 않는다.

## 반환된 표시 내용을 그대로 제출한다

작업 결과의 `native_todo`에는 `tool`, `arguments`, `list_revision`, `projection_digest`, `task_ids`, 도구 지원 관찰이 있다. 호스트 어댑터는 지정된 네이티브 도구를 사용한다. Codex는 `update_plan`, Claude Code는 `TodoWrite`다. 제출 근거의 범위는 `native-tool-submission`이다.

행은 다음 형식을 따른다.

```text
[Neurath] TITLE (DISPLAY_STATUS; TASK_ID; list LIST_REVISION)
```

다음은 구조 예제다. 실제 호출에서는 예제의 식별자를 만드는 대신 현재 `native_todo.arguments`의 모든 행과 값을 복사한다.

```json
{
  "plan": [
    {"step": "[Neurath] Verify parser behavior (In progress; TASK_ID; list 2)", "status": "in_progress"}
  ],
  "explanation": "The task has started; acceptance checks are in progress."
}
```

```json
{
  "todos": [
    {
      "content": "[Neurath] Verify parser behavior (In progress; TASK_ID; list 2)",
      "activeForm": "[Neurath] Verify parser behavior (In progress; TASK_ID; list 2)",
      "status": "in_progress"
    }
  ]
}
```

Codex는 정확한 기준 `plan` 행 옆에 문자열 `explanation`을 넣을 수 있다. 이 필드는 표시 구조를 비교할 때만 제외한다. 호스트 결과와 짝지을 요청 해시에는 설명을 포함한 전체 원래 입력을 보존한다. 문자열이 아닌 설명, 빠진 작업, 순서나 내용이 바뀐 행, 추가 표시 필드, 결과에서 바꿔 넣은 입력은 거부한다. Claude의 `content`와 `activeForm`은 동일한 반환 행 본문을 사용한다.

## 제출 근거가 확인하는 범위

| 기록 상태 | 관찰 내용 | 복구 방법 |
| --- | --- | --- |
| `submitted` | 검증된 루트가 네이티브 호출 ID로 정확한 현재 목록을 제출함 | 해당 호출의 실제 결과를 기다린다. |
| `current` | 짝이 맞는 결과가 성공했고 표시 내용도 최신 원장에 일치함 | 원장 상태를 기준으로 계속한다. |
| `stale` | 제출은 성공했으나 그 사이 작업 목록이 바뀜 | 새로 반환된 전체 표시 내용을 제출한다. |
| `failed` | 네이티브 도구가 실패를 보고함 | 작업 원장을 보존하고 표시 실패를 진단한다. |

결과에는 미리 준비된 네이티브 요청이 있어야 하며 호스트, 도구, 전체 입력 해시가 일치해야 한다. 일치하는 중복 이벤트는 멱등 처리하고, 모순되는 결과나 바뀐 호출 신원은 거부한다. 성공한 최신 투영만 최근 게시 기록이 된다.

지원 관찰은 `unobserved`, `observed-supported`, `unsupported-runtime`으로 표현한다. 표시 도구가 없거나 실패했는데 화면 갱신 성공으로 보고하면 안 된다. 이 기록은 네이티브 도구와의 상호작용을 확인하며 렌더링된 화면 픽셀의 독립 검사는 아니다.

## Stop은 최신 작업 상태를 사용한다

기준 작업 목록이 있으면 Stop 트랜잭션은 비어 있지 않은 작업 집합이 모두 종료 상태인지 확인한 뒤 루트 턴을 닫는다. 확인과 종료를 원자적으로 처리해 그 사이 접수된 작업이 사라지지 않게 한다. 빈 목록의 `task_list`는 `all_terminal=false`를 반환하며 목록이 없거나 비었다고 완료가 확인되는 것은 아니다.
