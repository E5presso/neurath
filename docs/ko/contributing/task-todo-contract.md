# 측정 가능한 태스크와 정본 TODO List

[English](../../en/contributing/task-todo-contract.md) · **한국어**

[아키텍처](architecture.md) · [실행 수명주기](runtime-lifecycle.md)

상태: 명명 작업 API, SQLite 기반 저장, 네이티브 표시와 task-aware Stop 판정의 소스 구현은
존재합니다. 실제 호스트 활성화와 종단 간 수용 검증은 아직 대기 중이며, 이 문서만으로
이를 인증하지 않습니다.

## 결정과 용어

**태스크**는 명시한 완료 조건과 근거로 결과를 판별할 수 있는 지시사항의 단위입니다.
지시사항에는 네이티브 사용자 프롬프트, 티켓, 스펙이 포함됩니다. 에이전트가 의미를
해석해 작업을 분해하고, 커널이 그 기록을 보존하고 검증합니다. **TODO List**는 커널에
보존된 태스크 기록의 조회 결과이며 별도로 편집하는 저장소가 아닙니다. 기존 phase
워크플로는 태스크를 수행하고 근거를 제공합니다. 단계나 워크플로 하나의 완료가
최초 요청 전체의 완료를 뜻하지는 않습니다.

현재 소스 작업 표면은 `task_define`, `task_list`, `task_start`, `task_resolve`입니다.
이 작업들은 정본 태스크 기록과 native TODO 표시를 관측하지만, 소스에 존재한다는 사실이
특정 호스트에서 실제로 노출·활성화됐다는 증명은 아닙니다.

| 요구사항 | 필수 동작 |
| --- | --- |
| T01 측정 가능한 정의 | 출처, 범위, 완료 조건, 필요한 근거를 기록합니다. 모호한 활동 이름만으로 정의하지 않습니다. |
| T02 지시사항 연결 | 프롬프트·티켓·스펙의 참조와 revision을 보존하고, 파생 작업을 그 작업이 필요한 원래 지시사항에 연결합니다. |
| T03 영속 ID | 명명 MCP 정의 도구가 고유 태스크 ID를 발급하고 같은 키의 재시도는 같은 결과를 반환합니다. 처리 커널에 보존하며 호출자가 신원을 주입할 수 없습니다. |
| T04 조회 | 명명 MCP로 태스크, 현재 상태, 의존성, 근거, 목록 revision을 조회합니다. 산문이나 UI에서 상태를 재구성하지 않습니다. |
| T05 가시성 | 정의·추가·전이 뒤 호스트의 기존 TODO 시각화 도구에 현재 목록을 반영합니다. UI가 커널의 완료 권한을 변경하지 않습니다. 시각화 도구를 사용할 수 없으면 그 상태를 알리고 표시 성공을 가장하지 않습니다. |
| T06 근거에 따른 종결 | 필요한 근거와 정확한 현재 revision을 검증한 뒤에만 성공·실패·무효를 수락합니다. 인계 기록이나 완료 주장만으로는 충분하지 않습니다. |
| T07 Stop 차단 | 비종결 태스크가 하나라도 있으면 에이전트의 정상 Stop을 거부합니다. 곁가지 질문에 대한 답변, 경과 시간, 재개 횟수 소진으로 이 조건을 면제하지 않습니다. |
| T08 실행 중 확장 | 목록을 교체하거나 기존 ID를 바꾸지 않고 실행 중 새 태스크를 추가합니다. 추가 즉시 가시성과 Stop 판정에 포함합니다. |
| T09 통합 저장 | 변경 가능한 실행 상태는 공통 프로젝트의 SQLite에 저장합니다. 별도 JSON 파일을 병행하는 실행 상태 정본으로 유지하지 않습니다. |

## SQLite 저장 결정

태스크, 세션, 워크플로, 소유권, 메시지, provider 실행, 모델 목록, 수행 근거, 검증
의무와 실행 체크포인트의 영속 저장소는 SQLite입니다. 필요에 따라 프로젝트·worktree·
세션·행위자로 기록을 구분합니다. 권한과 상태 전이는 계속 타입이 있는 커널이 검증하며,
저장 방식의 변경이 기존 검증을 약화하지 않습니다.

관련 상태 변경은 하나의 트랜잭션에서 반영합니다. 태스크 추가와 Stop 판정은 같은
확정 revision을 확인해야 합니다. 동시 요청·중단·재시작에도 재시도 키, 소유권 fence와
근거 출처를 보존합니다. DB 내부 직렬화나 외부 인터페이스에 JSON을 사용할 수 있지만,
이를 별도의 로컬 실행 상태 저장소로 유지하지 않습니다. 버전 관리하는 프로젝트 설정,
설치 manifest와 사용자 산출물은 실행 상태 정본이 아닌 외부 입출력이므로 필요한 파일
형식을 유지합니다.

기존 실행 기록은 트랜잭션으로 이전하고 ID·revision·참조를 검증한 뒤 조회 경로를
전환합니다. 이전 버전을 기록하고 예전 writer가 두 번째 정본을 되살리지 못하게 합니다.
이전 검증 전에는 복구 자료를 보존하며, 누락·손상·일부만 이전된 상태를 작업 완료로
간주하지 않습니다.
현재 구현은 legacy 경로의 변경을 감지하지만, writer 전환을 guard하는 절차의 독립 수용
검증은 아직 남아 있습니다. 그 전환이 별도로 확인되기 전에는 예전 writer가 영구적으로
배제됐다고 주장하지 않습니다.

## 상태와 수행 근거

비종결 상태는 `pending`, `in_progress`입니다. 종결 상태는 `succeeded`, `failed`,
`invalidated`입니다. 종결 기록과 근거를 보존합니다. 실패에는 실제 실패 결과와 사유가,
무효에는 작업이 불필요해진 출처 결정이나 중복·대체 근거가 필요합니다. Stop을 빠져나오기
위해 실패·무효로 처리해서는 안 됩니다. 중복으로 무효화한 태스크는 그 완료 조건을
이미 충족한 작업이나 결과를 참조합니다.

각 정의에는 간결한 제목, 출처 참조, 완료 조건, 필요한 근거 종류와 선택적 의존 태스크
ID가 있습니다. 서버가 발급한 ID와 변경 키로 재시도를 구분합니다. 태스크와 목록의
revision을 보존하며, 오래된 전이나 같은 키로 바꾼 입력은 부분 적용 없이 거부합니다.
없는 의존성과 순환 의존성을 거부합니다. 새 지시사항은 진행 중인 목록을 확장하고,
곁가지 질문에 답한 사실은 이전 작업을 대체하지 않습니다.

종결에는 완료 조건에 따라 기존의 권위 있는 워크플로 결과, 실제 검사 기록, 소비된
독립 검토 또는 인증된 출처·사용자 결정을 참조합니다. 근거의 발행자, 대상, 소스 기준과
결과를 검증합니다. UI 상태, 에이전트 보고와 준비된 근거는 수락된 근거와 구분합니다.

전부 종결됐다는 것은 세션의 작업이 정리됐다는 뜻이며, 전부 성공했다는 뜻은 아닙니다.
최종 보고는 성공·실패·무효를 나눕니다. 사용자의 명시적 일시 정지·취소는 호스트의
권한으로 유지하며, 미완료 태스크를 보존하고 성공을 만들어내지 않습니다.

## 원자적 종료와 네이티브 표시

태스크 추가·종결과 Stop 판정은 같은 처리 커널 revision을 사용합니다. 최종 Stop
트랜잭션에서 현재 목록을 다시 검사하여, 전부 끝난 과거 목록을 근거로 새 태스크가
추가된 세션을 종료하지 못하게 합니다. 턴 변경, 네이티브 알림, 중단, 컨텍스트 압축과
재시작에서도 이 조건을 유지합니다. 태스크 기록이 없거나 읽기에 실패한 상태를
완료된 빈 목록으로 간주하지 않습니다.

네이티브 TODO 표시에는 안정된 태스크 ID와 목록 revision이 포함됩니다. 대기·진행
상태를 정확하게 표시하고, 기본 도구가 일반 완료 상태만 제공하더라도 실패·무효는
텍스트에서 구분합니다. 표시 결과는 태스크 종결과 별도로 기록합니다. 오래되거나
사용 불가능한 UI가 태스크 정본을 바꾸거나 Stop 권한을 부여하지 않습니다.

모델 catalog 관측은 native issuer와 provider별로 cache하고 턴과 worktree 사이에서
재사용합니다. 명시적 refresh 요청이나 구체적인 stale catalog 근거가 있을 때만 갱신합니다.
새 assignment나 target은 새 plan과 target/policy admission을 요구할 수 있지만 catalog를
새로 발견해야 하는 조건은 아닙니다. 협업 bulk send는 구조화된 `messages`를 원자적으로
commit하고 정확한 수신자에게 fan-out하며, queued/submitted는 수신 확인이나 task 완료가 아닙니다.


## 구현 순서와 수용 검증

1. 커널 태스크 기록, ID, revision, 추가·전이 조건과 이전 상태의 호환 로딩.
2. 명명 MCP의 묶음 정의·조회·종결과 기존 근거 생산 도구 연결.
3. 네이티브 TODO 표시와 태스크 기준 Stop 판정, 사용자의 명시적 호스트 중단 보존.
4. 입력·autopilot 연결: 이미 처리된 작업 판별, 필수 자가 수정 작업 추가, 설명 질문
   사이의 작업 유지, phase·검토 결과를 정확한 태스크에 연결.
5. 양 언어 문서, 패키지·설치 검사와 실제 Codex·Claude 호스트 수용 검증.

회귀 시나리오는 정의 재시도, 타인·오래된 근거, 일부 실패, 중복 무효화, 수행 중·Stop
중 태스크 추가, 재시작 후 ID·이력 보존, 일부 태스크만 성공한 상태, UI 불일치,
반복 Stop과 사용자의 명시적 일시 정지를 포함합니다. 모델 목록 재사용, 묶음 메시지,
긴 검사 동시 처리, 소유권 해제 후 마감, 매개변수화된 검사 수정도 최초 작업 범위 안의
개별 측정 가능한 태스크로 유지합니다.

## 요구사항과 수용 기준 연결

| 기능 ID | 결정 | 수용 ID와 관찰할 결과 |
| --- | --- | --- |
| FR-001 | T01 | SC-001: 완료 조건이나 필요한 근거 종류가 없는 태스크를 커널이 거부합니다. |
| FR-002 | T02 | SC-002: 태스크 조회에 정확한 프롬프트·티켓·스펙 출처와 revision이 남습니다. |
| FR-003 | T03 | SC-003: 동일 정의 재시도는 같은 ID를 반환하고, 같은 키로 바꾼 입력은 거부합니다. |
| FR-004 | T04 | SC-004: 정본 상태를 다시 열어도 태스크 ID·상태·근거·목록 revision이 유지됩니다. |
| FR-005 | T05 | SC-005: 네이티브 TODO에 현재 태스크 전체와 revision을 표시하고, 기능 부재는 명시적 사용 불가 결과로 남습니다. |
| FR-006 | T06 | SC-006: 미확정·타인·불일치 근거로는 종결할 수 없고, 수락된 종결 기록에는 근거가 남습니다. |
| FR-007 | T07 | SC-007: 곁가지 질문에 답했더라도 태스크 하나가 대기 중이면 반복된 정상 Stop을 거부합니다. |
| FR-008 | T08 | SC-008: Stop 조회와 반영 사이에 태스크가 추가되면 종료가 실패하며, 기존 ID와 종결 이력을 보존합니다. |
| FR-009 | T09 | SC-009: 이전된 실행 기록의 ID·revision·참조가 유지되고, 동시 변경과 이전 중단에도 JSON과 SQLite가 서로 다른 정본이 되지 않습니다. |

커널 구현은 FR-001~FR-004와 FR-008, 근거 연결은 FR-006, 호스트 연결은 FR-005와
FR-007을 담당합니다. 공유 의존성인 커널 스키마가 연결부보다 먼저 반영돼야 합니다.
네이티브 TODO 표시와 종결 근거의 수용 기록은 분리합니다. 이 계약을 결정 기록과 재개
출처로 사용합니다. 명시된 사용자 결정과 상태·표시의 관계가 이미 기록됐으므로 같은
내용의 ADR을 별도로 만들지 않습니다.

### 작업 결과 보고

성공·실패를 종결할 때 `task_resolve`에 해당 태스크와 연결된 종결 워크플로의
정확한 `workflow:<id>:<revision>` 참조와 네이티브 루트의 `assessment`를
전달합니다. 보고에는 요약과 모든 완료 조건별 `condition`, `outcome`
(`met` 또는 `unmet`), `explanation`, 정확한 워크플로 `reference`가
포함됩니다. 성공은 모든 조건 충족, 실패는 하나 이상의 미충족 조건을 요구합니다.
서비스는 소유권, 원래 태스크와 워크플로의 연결, revision과 조건 누락을 검증합니다.
기존 워크플로의 phase·평가자 검토 요건은 그대로 적용됩니다.

독립 태스크 검토는 선택 사항입니다. `delegation:<consumed-id>`를 추가하면
소비된 네이티브 자식 보고, 정확한 태스크·워크플로 연결과 루트 판정의 일치를
검증합니다. 일반 태스크 종결을 위해 별도 검토자를 추가할 필요는 없습니다.

무효화에는 인증된 현재 또는 보존된 네이티브 프롬프트의 참조·해시에 연결한
루트 `decision`을 사용할 수 있습니다. 결정에는 분류와 사유를 기록하고,
중복·대체 작업에는 이를 이미 충족하는 출처 또는 완료 워크플로 참조도 필요합니다.
기존의 소비된 독립 결정 보고 경로도 지원합니다.

서비스는 간결한 결과 보고를 아티팩트로 한 번 저장하고 태스크에서 참조합니다.
워크플로 근거와 로그는 참조로 재사용합니다. 보고의 보증 수준은
`agent-assessment`이며, 기록 자체가 독립 검증을 의미하지 않습니다.

새 네이티브 루트 워크플로를 시작하려면 같은 워크플로 ID·목표를 가진 대기 또는
진행 태스크가 먼저 등록돼 있어야 합니다. 등록 누락으로 거부된 시작 요청은
태스크 정의 후 같은 키로 다시 사용할 수 있습니다. 기존 워크플로와 직계 자식의
실행에는 기존 재개·평가자 규칙을 유지합니다.

태스크 목록을 정의하지 않은 기존 세션에는 기존 Stop 규칙을 적용합니다.
워크플로 상태만으로 전부 종결된 태스크 목록을 만들어내지 않습니다. 목록이
존재하면 실행 중 추가된 태스크를 포함해 모든 미종결 태스크가 정상 Stop을 차단합니다.
