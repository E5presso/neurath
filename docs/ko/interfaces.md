# 공개 스킬과 CLI 명령

[명세](specification.md) · [기능 배치](capability-continuity.md) · [English](../en/interfaces.md)

현재 CLI·설치 스킬의 계약입니다. 설치 파일 적용, 실제 훅 실행, 모델 맥락 전달은 각각 검증합니다.

코어와 세 접점의 책임은 [명세](specification.md)에, 실행·훅·상태 전이는 [구조](architecture.md)에 정의합니다. 이 문서는 스킬 선택과 CLI의 공개 계약을 설명합니다.

CLI 컨트롤러는 소유 책임으로 나눕니다. `memory`는 기억 조회·검색·저장·현재 맥락 갱신을, `session`은 인수 미리보기·재개를 제공합니다. 실제 명령·옵션은 배포본의 `--help`와 자동 생성된 CLI 가이드가 기준입니다.

## 1. 선택 기준

스킬은 **재사용할 판단·순서·검증 기준이 있는 작업 절차**입니다. Neurath 내부 관리에만 한정하지 않습니다. 명세 정의·구현·디버깅·리뷰·QA·UI·문서 작업에 필요한 절차를 제공합니다. 의존성 감사·갱신은 프로젝트/전문 도구에서 선택하며 Neurath 기본 스킬로 배포하지 않습니다. 커밋·워크트리 생성·PR 생성·단순 파일 수정은 호스트 도구의 단일 작업이므로 별도 스킬을 두지 않습니다. 한 테스트 명령 실행과 여러 사용자 시나리오의 QA는 구분합니다.

CLI는 에이전트가 직접 전달해야 하는 의도 또는 직접 조회할 Neurath 정보만 노출합니다. 테이블마다 CRUD를 만들지 않습니다. 현재 작업 맥락의 조회는 하나로 묶고, 수행 결과 보고는 같은 작업/시도 경로를 사용합니다. 독립적인 효과를 감추는 만능 `execute(action=...)`도 만들지 않습니다. 아래 목록은 스킬 14개와 기능별 업무 CLI입니다. 도움말·버전 및 기존 설치/복구 관리 명령은 별도로 제공하며 MCP 서버나 선택적 MCP 어댑터는 제공하지 않습니다.

## 2. 스킬

### Rules를 통한 스킬 시작

설치된 rules를 Neurath의 기본 진입점으로 사용합니다. 사용자가 매 작업마다 별도 모드나 진입 명령을 켤 필요는 없습니다. Rules는 스킬의 목적·적용 조건·제외 조건과 CLI를 통한 시작 방법을 안내하고, 에이전트가 사용자 요청의 의미에 맞는 스킬을 선택합니다. 사용자가 스킬을 직접 지정하면 그 지정을 따릅니다. 단순 질문·설명·상태 확인에는 스킬 실행을 강제하지 않습니다.

스킬 선택은 에이전트의 판단이며, 선택된 스킬의 실행 정의·phase·시도·결과·완료 조건은 기존 phase runner가 관리합니다. 스킬을 읽거나 이름을 언급한 것만으로 run이 시작된 것으로 기록하지 않습니다. 선택한 스킬은 `workflow start`로 시작하며 호스트 수행 결과는 `workflow report`로 연결합니다. 스킬 선택은 사용자 요청의 범위를 확대하거나 추가 권한을 부여하지 않습니다.

설치된 `AGENTS.md`/`CLAUDE.md`의 Neurath 관리 영역에는 이 기본 진입 정책과 14개 스킬의 목적·적용·제외 조건 및 실제 `SKILL.md` 링크가 포함됩니다. 목록은 스킬 catalog에서 CLI 가이드와 함께 생성하며, 설치 시 해당 호스트의 실제 스킬 폴더 경로를 치환합니다. 에이전트는 필요한 스킬만 찾아 읽고 같은 `workflow start` 경로로 연결합니다. 사용자에게 매번 모드 선택이나 별도 진입 명령을 요구하지 않습니다.

명시적으로 선택한 네이티브·프로젝트·사용자 스킬은 기본 스킬 추정보다 우선하며 기존 호스트/프로젝트 지침의 우선순위를 유지합니다. 이미 수행 중인 태스크/run은 재사용하고 필요한 경우 `workflow show/revise`로 이어갑니다. 단순 질문·설명·상태 조회와 커밋·워크트리 같은 단일 호스트 작업 때문에 별도 스킬이나 run을 만들지 않습니다. 저장 맥락이 필요할 때만 조회하고, 스킬 선택을 요청 범위나 실행·공개 권한의 확대로 해석하지 않습니다.

설치 회귀는 실제 관리 영역·스킬 경로·메타데이터·기존 CLI 시작/보고 연결과 단순 프롬프트·조회에서 태스크/run이 자동 생성되지 않는 사실을 검증합니다. 대표 요청과 스킬 쌍은 시험 입력이며 문자열 검사나 fixture가 네이티브 모델의 의미 선택 정확도를 증명하지는 않습니다. 실제 호스트의 rules 적재·스킬 선택·모델 수행은 별도 검증 경계입니다.

| 스킬 | 사용할 요청 | 절차 | 제외 |
| --- | --- | --- | --- |
| `define-spec` | 사용자 의도를 실행 가능한 명세로 정하거나 보완할 때 | 의도·범위·대안 논의→동작/수용 기준→실행 순서·의존성·검증 계획→결정/미결정 기록 | 단순 질문; 이미 충분한 명세를 불필요하게 다시 정의 |
| `implement-spec` | 명세·요청에 따른 기능을 구현할 때, UI 포함 | 명세/현재 동작 확인→필요 부분 구현→관련 검사→요구 대비 결과 확인; UI는 화면·상태·상호작용 검증 포함 | 단순 파일 수정; 이슈 생성이나 별도 plan은 필수 아님 |
| `autopilot` | 여러 작업·의존성을 자율적으로 끝내 달라는 요청 | 원 요청→분해/배정→실행/검증→미완료 재조정→결과 | 한 번의 명령, 일반 질문, 상태 조회 |
| `review-spec` | 요구·명세·구현의 전체 일치 감사 | 원문/범위 고정→누락·과잉·모순 반례→수정 후 재감사 | 단순 문구 수정, 코드 diff만의 일반 리뷰 |
| `review-code` | 변경 코드 또는 PR의 정확성을 검토할 때 | 대상/기준 확인→실제 실행 경로 분석→결함과 영향→수정 재검토 | 스펙 논의, PR 생성만 요청 |
| `qa` | 여러 사용자 시나리오의 수락 여부를 검증할 때 | 시나리오/환경→실제 UI/API/저장 동작→결과/회귀 확인 | 테스트 명령 한 번 실행 |
| `debug` | 원인이 불명확한 실패를 조사하고 수정할 때 | 재현→원인 가설 구별→수정→같은 실패의 회귀 확인 | 이미 정해진 작은 변경 |
| `design-ui` | UI 방향과 사용자 동작을 설계할 때 | 목적/사용 흐름→대안→상태/상호작용→선택한 방향 기록 | 단일 스타일 값 변경 |
| `review-ui` | 구현된 UI의 동작/사용성을 검토할 때 | 실제 화면과 주요 상태→기준 대조→문제/재검증 | 스크린샷 읽기만 요청 |
| `sync-design` | 디자인 원본과 구현의 차이를 동기화할 때 | 양쪽 변경 확인→기준 판별→영향 범위 반영→일치 확인 | 새 디자인을 임의로 선택 |
| `sync-docs` | 소스/스펙 변경을 관련 문서와 언어에 반영할 때 | 변경 사실→독자/페이지 영향→작성/동기화→예제/링크 검증 | 오탈자 하나 수정 |
| `pr-feedback` | PR 피드백을 판단하고 수정·검증·답변할 때 | 현재 변경과 대조→타당성 분류→수정/검증→답변 | 댓글 게시 한 번 |
| `finish-session` | 진행 작업을 마무리하고 인계 가능한 상태로 끝내기 | 남은 결과/runner→관련 검사·제3자 결과 평가→범위 내 Git/그래프→인계·소유권 정리; 문제가 드러났으면 선택적 회고 제안 | 일반 답변의 매 턴 종료, 커밋 하나 |
| `update-neurath` | Neurath 설치·업데이트 요청 | 배포본/소유 설정→작성 정지·자료 보존→적용→실제 활성화/재개 | 버전 조회, 다른 의존성 업데이트 |

명세 중심 절차의 이름은 **`define-spec` → `implement-spec` → `review-spec`**으로 통일합니다. `define-spec`은 무엇을 만들지와 어떻게 수행·검증할지를 같은 명세에 정합니다. 실행 순서·의존성·검증·마무리 계획은 그 일부이며 별도 `plan` 호출이나 중복 문서를 요구하지 않습니다. 이미 충분한 명세가 있으면 그대로 구현할 수 있고, 변경이 필요하면 관련 부분만 갱신합니다.

`implement-ui`는 `implement-spec`에 통합합니다. 화면·상태·상호작용·접근성 등의 참조와 실제 검증은 UI 작업일 때 적용합니다. UI 방향을 정하는 `design-ui`와 구현된 UI를 검토하는 `review-ui`의 역할은 유지합니다.

`audit-deps`·`update-deps`는 first-party 기본 스킬에서 제외합니다. 필요한 의존성 작업은 에이전트가 프로젝트 도구나 선택한 전문 스킬로 수행하며 기존 사용자/프로젝트 스킬은 삭제하지 않습니다.

`recover-session`은 제공하지 않습니다. 명시적인 재개/인수는 기존 **`session resume` CLI**로 충분합니다. 자동 맥락 복원은 런타임이 수행하고, 운영 저장소가 고장 나도 필요한 진단·복구 명령은 사용할 수 있어야 합니다. 별도 복구 스킬을 거치지 않습니다.

`test-harness`·`optimize-harness`는 사용자 배포 스킬이 아닙니다. 해당 검증과 개선 기능은 Neurath 개발 및 아래 사용자 요청에 따른 자가개선 과정에 유지합니다. `review-pr`는 `review-code`의 대상 선택으로, `dev-docs`·`user-docs`는 독자별 지침을 가진 `sync-docs`로 통합합니다. Graphify는 기존 전문 도구/스킬을 사용합니다.

작업 묶음을 마무리하는 스킬은 [결과 평가 phase](architecture.md#3-skills와-phase-runner의-실행-계약)를 수행합니다. 스킬을 중첩해도 같은 유효 평가를 재사용합니다.

### 배포 정의·설치 본문·runner 연결

`resources/skills.json`은 14개 스킬별 목적·적용/제외 조건·필요 입력·상황별 분기·최종 결과와 단계의 결과 조건·검사 이름을 함께 정의합니다. 같은 catalog가 설치용 `SKILL.md`와 기존 `WorkflowDefinition`을 만듭니다. `define-spec`은 수용 기준과 실행 순서·의존성·검증 계획을 함께 남기며, `implement-spec`은 UI 작업일 때 화면·상태·상호작용·접근성 검증을 수행합니다. UI가 없을 때 이를 수행한 것으로 기록하지 않습니다.

설치 파일은 첫 줄부터 YAML frontmatter의 `name`과 구체적인 선택·제외 `description`을 제공하고 이어서 스킬 본문을 둡니다. Codex는 `.agents/skills`, Claude는 `.claude/skills`의 해당 폴더를 사용합니다. 관리 스킬을 갱신할 때 다른 frontmatter 항목과 관리 영역 밖 사용자 본문을 보존합니다. 다른 프로젝트/사용자 스킬은 수정하지 않으며 같은 경로의 비관리 스킬과 충돌하면 덮어쓰지 않습니다. 형식 근거는 [공식 Codex 스킬 문서](https://learn.chatgpt.com/docs/build-skills)와 [Claude 스킬 문서](https://code.claude.com/docs/en/skills)입니다. 파일 형식·설치를 검증한 사실과 실제 호스트의 발견·선택·모델 수행은 구분합니다.

스킬을 읽는 것만으로 run이나 단계 결과가 생기지 않습니다. 이미 현재 요청을 수행하는 태스크와 run이 있으면 재사용합니다. 실제 수행할 일이 원장에 없을 때만 `task create`를 호출하고, 새 절차를 선택했을 때 `workflow start`를 사용합니다. `workflow show --run-id UUID`는 기존 고정 정의·입력·시도·현재 단계를 읽습니다. 패키지나 원문 파일 변경은 진행 중인 run을 덮어쓰지 않습니다. 정의가 달라진 `start`는 기존 run을 변경하지 않고 명시적 `workflow revise` 경로를 안내합니다. 이름이 바뀐 옛 스킬의 run도 저장된 정의로 계속 읽고 보고할 수 있습니다.

`workflow report`는 실제 호스트 작업 뒤 현재 단계의 `checks` 항목만 반복 `--check`로 전달합니다. 일반 단계의 보고는 독립 결과 평가를 통과시킬 수 없습니다. 하위 절차나 `finish-session`을 이어 수행할 때 같은 run을 `revise`하고 유효한 동일 평가 phase와 시도를 보존합니다. 관련 요구·후보가 바뀌면 기존 평가 경로가 재평가를 요구하며, 단순 마무리 때문에 새 평가 태스크를 만들거나 검토자를 재귀 평가하지 않습니다. 원 작업의 요구 변경과 수행 방법 변경은 구분합니다.

### 선택한 프로젝트·사용자 전문 스킬

기본 목록 밖의 스킬도 호스트가 원본 `SKILL.md`를 읽어 선택한 절차를 기존 runner로 수행할 수 있습니다. 에이전트는 원 스킬의 의미를 보존한 명시적 정의를 `workflow start --task-id UUID --skill project-check --definition @workflow.json`으로 전달합니다. `--definition -`는 stdin, JSON 문자열은 인라인 입력입니다. 원본 스킬을 Neurath 형식으로 덮어쓰거나 사용자에게 상태 관리를 맡길 필요는 없습니다.

```json
{
  "version": "project-1",
  "source": ".agents/skills/project-check/SKILL.md",
  "inputs": {"target": "requested artifact"},
  "phases": [
    {"key": "inspect", "purpose": "Read the selected inputs", "checks": ["scope"]},
    {"key": "verify", "purpose": "Perform the project check", "result": "Verified actual output", "checks": ["content"]}
  ]
}
```

`version`과 `phases`는 필수이며 각 단계는 `key`, `purpose`, `checks`를 가집니다. `inputs`는 선택적 문자열 값 객체이고, `source`를 지정하면 실제 작업 폴더 기준 또는 절대 경로의 스킬 원문과 경로를 run 입력에 고정합니다. 원문 읽기나 JSON 형식·중복 단계·검사 조건 검증이 실패하면 태스크 시작이나 run 저장이 없습니다. 알려지지 않은 이름에 정의도 없으면 기본 목록과 기존 run 조회/정정 경로를 안내하며 임의 절차를 만들지 않습니다.

일반 호스트 수행 단계는 실행 인자 없이 진행할 수 있습니다. 실제 작업은 호스트 도구로 수행하고 근거를 보고합니다. 선택 절차에 필요한 독립 평가는 기존 evaluation phase로 연결하며 전문 스킬이라는 이유로 일반 작업에 일괄 추가하지 않습니다. 기본에서 제외한 커밋·워크트리·이슈/PR, 의존성 관리, Graphify, 복구는 기존 호스트·전문 도구와 `session resume` 경로로 수행합니다.

## 3. CLI 전용 인터페이스

**기술 스택은 Python + spakky-typer (Typer)입니다.** `neurath` 진입점과 업무·관리 명령을 Typer 애플리케이션으로 정의합니다. Python 타입 힌트와 Typer의 명령·인자·옵션·도움말 정의를 사용하고, 실제 도메인 동작은 기존 Application 유스케이스에 위임합니다. Typer 의존성은 CLI 전송 계층에 두며 Domain에 넣지 않습니다. [공식 Typer 문서](https://typer.tiangolo.com/).

CLI Controller는 기능별 그룹을 명시하고 업무 명령은 그 그룹 아래에 둡니다. 그룹이 대상을 나타내면 하위 명령은 `list/read/publish`처럼 동사를 사용하며, 대상 구분이 더 필요한 이름은 동사-목적어 형식의 kebab-case로 작성합니다. 스킬은 동작 이름에 kebab-case를 사용하며 `autopilot`, `qa`는 확립된 절차 이름을 유지합니다.

프로젝트·세션·피어·현재 개정은 기본적으로 실제 호스트와 DB에서 조회합니다. 명시적 범위 옵션은 다른 저장 상태를 선택할 때 사용합니다. CLI 가이드는 실제 Typer 정의에서 생성하며 스키마 내부 전이를 모두 공개 명령으로 만들지 않습니다.

| 도구 | 입력·결과와 효과 경계 | 효과 |
| --- | --- | --- |
| `context show` | 지정 세션/작업의 현재 원문·TODO·배정·runner·사실·피어/모델·감시/진단 요약. sections/filter/cursor로 필요한 부분만 읽음 | read |
| `task create` | 원 요청에 연결한 결과 조건·의존 관계로 작업 생성 | write |

| `task report` | 작업·시도·대상의 수행/검토 결과와 근거 보고. 담당자의 적용 가능한 결과로만 task/phase 전이; 수신자 보고는 상위 완료가 아님 | write |

| `neurath memory update` | 같은 사실 저장소의 예상 개정에 set/remove 변경 목록 적용; 원문/작업은 삭제하지 않음 | write |

| `neurath newsroom revise` | 예상 개정과 정정 이유로 기사 수정; 이력 보존 | write |

CLI는 같은 애플리케이션 유스케이스를 직접 호출합니다. MCP 서버 등록·도구 발견·재연결을 전제로 하지 않습니다. 호스트의 셸 실행 도구로 호출하고, 스킬은 설치된 가이드에 따라 명령을 선택합니다. 결과는 에이전트가 읽기 쉬운 구조화된 JSON으로 제공하고 로그/진단과 구분합니다. 종료 코드는 명령 처리의 성공/실패를 나타내며 작업 목표 달성 여부는 실제 결과로 구분합니다. 잘못된 인자는 변경 전에 검증하고 필요한 사용법을 함께 반환합니다. 복잡한 본문은 파일 또는 표준입력으로 전달할 수 있게 하며 오류 난 변경을 추측으로 재시도하지 않습니다. 정확한 옵션 이름·형식은 실제 CLI 정의와 함께 확정합니다.

일반 업무 명령은 호출 시 선택된 설치 버전으로 실행합니다. 업데이트 이후 새 호출은 새 배포본을 사용하고, 진행 중 호출은 안전한 경계까지 처리·정리합니다. 코어는 상주 상태를 보유하지 않습니다. 진행 중인 호스트 실행의 버전 전환·인계는 해당 실행의 계약으로 확인합니다. CLI 사용만으로 모든 상주 실행이 자동 교체되거나 진행 중인 대화의 지침이 바뀐다고 주장하지 않습니다.

요청된 회고의 교훈은 `memory propose-lesson`과 `memory observe-lesson`으로 후보·실제 효과를 기록하고 `memory search/read`로 조회합니다. 이 명령은 회고 승인이나 실제 코드 적용을 대신하지 않습니다. `monitor status/tick`은 현재 감시의 읽기/단일 관찰 경로이며, 실제 후속 실행은 [감시 콜백](monitoring.md)을 사용합니다. 설치·초기화·진단·독립 장애 기록은 `maintenance`, 호스트 사건은 `hook` 그룹입니다.

`newsroom subscribe --enabled/--disabled`는 현재 대화의 제목 알림 설정이며 다른 주제·배정·이력을 변경하지 않습니다. 새 네이티브 피어의 기본 수신과 기존 구독 선택을 구분합니다.

### 범위와 다음 페이지

`context show`는 현재 호스트 세션을 자동 선택합니다. `--session`은 관찰된 다른 호스트 세션 주소를, `--section`은 `current/sources/collaboration/memory`를 선택합니다. `current --task-id UUID`는 선택 세션이 소유한 작업과 관련 runner·사실로 좁힙니다. 세션 공통 사실과 원문 참조는 유지하므로 TODO에 빠진 요구도 확인할 수 있습니다. 다른 세션의 작업이나 다른 section의 작업 필터는 오류입니다.

목록별 기본 출력은 20개, `--limit`은 1~100개입니다. 현재 맥락은 기존 인수 미리보기의 읽기 전용 스냅샷에서 출력 페이지를 구성하며 DB 조회량 전체를 제한하는 계약은 아닙니다. 항목의 본문을 중간에서 잘라 원문이나 현재 사실을 훼손하지 않습니다. 목록이 나뉘면 다음 커서를 반드시 반환합니다.

| 조회 | 다음 커서 | 순서 |
| --- | --- | --- |
| `context show` | `next_after_ids`의 `tasks/workflows/facts/source_ids` | 기존 조회 순서: 작업은 생성 시각·UUID, runner/사실은 UUID, 원문은 생성 시각·UUID 오름차순 |
| `context show --section sources` | `{sources, next_after_id}`의 `next_after_id` | 생성 시각·UUID 오름차순 |
| `context show --section collaboration` | 인박스 `next_after_id`, 피어 `next_peer_after_id`, 배정 `next_delegation_after_id` | 각 목록의 UUID 오름차순 |
| `context show --section memory` | `next_after_ids`의 `memory_ids/applied_lessons` | 생성 시각 최신순·동일 시각 UUID 오름차순 |
| `memory search` | `next_after_id` | 생성 시각 최신순·동일 시각 UUID 오름차순 |

각 목록은 독립적으로 이어 읽습니다. 같은 세션·section·작업/검색 필터·limit에 해당 목록의 커서를 `--after UUID`로 전달하고 **그 목록만** 모읍니다. 커서가 `null`이 될 때 끝입니다. 기억 검색과 적용 교훈의 마지막 페이지가 limit과 같으면 빈 후속 페이지가 올 수 있습니다. 여러 목록의 커서를 하나로 합치거나 첫 페이지를 전체 TODO·원문으로 간주하지 않습니다. 페이지 사이에 새 작업이나 정정이 생기면 최신 첫 페이지를 다시 확인합니다. 원문 응답은 페이지 메타데이터를 위해 과거의 bare 배열 대신 `sources` 배열과 커서를 가진 객체를 사용합니다.

```sh
neurath context show --section sources --limit 10
neurath context show --section sources --limit 10 --after <next_after_id>
neurath context show --task-id <task_uuid> --limit 10
neurath memory search --text "handoff" --limit 10 --after <next_after_id>
neurath maintenance version
```

`maintenance version`은 현재 호출된 설치 배포본의 이름과 버전을 JSON으로 반환하며 저장소를 열거나 초기화하지 않습니다. DB 부재·손상 상황에서도 버전을 확인할 수 있습니다. 버전 조회가 실제 호스트 활성화·업데이트 완료를 뜻하지는 않습니다.

## 4. 줄인 도구의 실행 경로

- 세션·작업 목록·현재 phase·enclave·피어·모델·메시지 제목·감시 상태는 `context show`의 제한된 조회입니다. 기본 응답은 현재 작업의 간결한 맥락이며 관련 없는 이력 전체를 주입하지 않습니다. sections는 명시한 조회 영역만 선택하고 임의 내부 메서드를 실행하지 않습니다. 본문이 큰 기억·메시지·기사는 별도 선택 조회합니다.
- `task report`는 같은 task/attempt에 결과를 연결합니다. 수신자는 보고만 하고, 담당자의 판정과 실제 근거가 해당 조건을 충족할 때 내부에서 task/phase를 전이합니다. 모든 보고가 성공이나 소유자의 수용으로 바뀌지 않습니다. `task update`에는 성공·근거·승인 직접 설정 필드가 없습니다.
- 피어 위임과 provider 실행은 `collaboration delegate`의 대상 선택입니다. 내부 어댑터가 모델·정책을 검증하고 실제 실행합니다. 관찰은 `context show`, 취소는 해당 배정 작업의 `task update`로 처리합니다. 제출과 실제 시작/중단은 구분합니다.
- 외부 감시는 요청된 작업의 대기 의존성으로 관리합니다. `task update`가 실제 요청에 해당하는 관찰 대상·해소 조건·허용된 후속 범위를 기록하면 내부 모니터가 그 의존성을 관찰합니다. 대기 사유만으로 임의 감시를 만들지 않습니다. 취소·재개·인계는 같은 작업 수명주기를 따릅니다.
- Enclave의 set/remove는 같은 사실 변경 목록인 `memory update`에 통합합니다. 삭제는 명시적인 remove와 예상 개정이 있어야 하며 null 값과 혼동하지 않습니다.
- 피어 구독/대화 알림 종료는 프로젝트 알림 설정입니다. 현재 대화의 뉴스룸 구독은 `newsroom subscribe`로 변경합니다. 이 변경은 배정 작업을 취소하거나 이력을 지우지 않습니다. 모델이 매 턴 호출할 도구로 노출하지 않습니다.
- 학습의 생성·검증·보류·철회는 사용자가 요청한 회고 안에서 처리합니다. 읽기는 기억 조회를 사용합니다. 명시적 교훈 정정은 출처 있는 교훈 자료의 개정으로 남기고 런타임이 반영합니다. 이전 효과·실패 이력은 보존하며 사용자가 말하지 않은 지시를 학습으로 만들지 않습니다.
- 우회·깊은 진단·설치·업데이트·DB 복구는 업무 명령이 실패해도 사용할 수 있는 관리 명령입니다. 정상 상태의 진단 요약은 `context show`에서 보입니다. `update-neurath`와 런타임 복구 과정에서 필요에 따라 관리 경로를 사용합니다. 상세 CLI 문법은 구현 문서에서 정의합니다.

위임과 발신 맥락은 [원문 해석 기준](specification.md#3-요청과-결과)을 따릅니다.

## 5. 유지할 경계와 검증

Stop, TODO 표시, 사건 수집, 실제 임대·ACK, 단계 종결은 내부 처리입니다. 실제 사건 없이 모델이 신원·인간 승인·성공한 검사·읽음 상태를 생성할 도구는 없습니다. `read+receipt`는 순수 read-only로 선언하지 않으며 전체 전달이 불명확하면 읽음도 미확인입니다.

선택한 스킬은 runner가 정의·현재 시도·남은 결과를 보존해 수행합니다. 기존 스킬의 이름 변경으로 진행 중인 run을 삭제하지 않습니다. 설정·호스트 경로로 옮긴 기능도 실제 결과를 검증하며 사용자 수작업으로 떠넘기지 않습니다. 프로젝트/사용자 스킬은 설치기가 임의로 삭제하지 않습니다.

공개 발견 목록, 동사 우선 이름, 128개 과거 기능의 대체 경로, 명세(실행 계획 포함)→구현→감사의 연결, 일반 작업에서 불필요한 스킬 미실행, 결과 보고의 역할 구분을 요구사항 검증으로 확인합니다. 숫자가 줄었다는 사실만으로 단순화나 기능 보존이 검증되지는 않습니다.

## 6. 사용자가 선택하는 회고

회고 제안과 사용자 선택에 따른 제3자 회고 평가도 스킬의 phase와 분기로 관리합니다. 거절·무응답이면 선택적 회고 분기를 실행하지 않고 마무리하며, 사용자가 이미 요청했다면 제안 없이 평가 단계로 진행합니다.

세션 중 사용자 지적, 수행 실패 또는 결과 검토 등에서 드러난 문제가 있고 사용자가 회고를 이미 요청하지 않았다면, 원래 작업 결과를 정리하며 한 번 제안합니다.

> 이번 세션에서 개선할 문제가 확인됐습니다. 제3자 평가를 바탕으로 회고와 자가개선을 수행할까요?

사용자가 요청하거나 일반 대화로 수락하면 실행자와 별개의 서브에이전트 또는 다른 provider에게 회고 평가를 위탁합니다. 사용자 지시·실제 작업 결과·문제 기록을 제공하고 원인, 개선 후보, 근거를 받습니다. 실행자는 그 결과를 검토하여 요청 범위의 개선을 수행하고, 같은 실패 사례와 정상 사례로 효과를 검증합니다. 악화된 개선은 철회합니다. 평가자의 제안을 사용자 지시로 승격하거나 무관한 작업·외부 공개·권한 변경으로 확대하지 않습니다.

- 거절하거나 답하지 않으면 회고를 실행하지 않습니다. 원래 작업의 완료·인계·임대 해제를 막거나 미완료 의무로 등록하지 않습니다. 다음 턴/세션의 반복 질문·자동 재시도도 하지 않습니다.
- 이미 회고를 지시했다면 다시 묻지 않고 그 범위에서 수행합니다. 문제가 없거나 일상적인 대화 턴이 끝났다는 이유만으로 제안을 생성하지 않습니다.
- 전용 선택 토큰·해시·서명·승인 객체·새 CLI 명령을 요구하지 않습니다. 모호한 응답은 수락으로 간주하지 않되 원래 작업은 정상 마무리합니다.

회고 평가·교훈 저장·개선 제안만으로 자가개선 완료를 선언하지 않습니다. 실제 적용과 관련 검증 결과를 구분해 보고합니다. 필요한 검증은 요청한 회고 작업 안에서 수행하며 모든 사용자 작업에 하네스 전체 검사를 강제하지 않습니다.

## 7. CLI 가이드 프롬프트와 릴리스 자동화

**원천은 실제 Typer CLI 정의 하나입니다.** 명령 설명·인자·필수값·허용값·입력/출력·오류 처리·검증 가능한 예시를 CLI 구현과 같은 정의에서 읽습니다. 별도 수기 도구 목록을 맞추거나 LLM으로 매 릴리스마다 사용법을 재작성하지 않습니다. 새 명령이 없는 현재 설계 문서를 실제 구현의 도움말로 배포하지 않습니다.

릴리스 자동화 스크립트는 다음을 수행합니다.

1. 릴리스할 코드의 Typer 명령·인자·옵션·도움말 정의에서 짧은 에이전트용 가이드 프롬프트를 결정적으로 생성한다.
2. 가이드에 배포 버전, 진입 명령, 각 업무 명령의 용도·필수 입력, 결과 읽기, 오류 시 도움말 조회, 필요한 관리 경로를 포함한다. 상세 옵션은 실제 --help로 확인할 수 있게 한다.
3. 문서의 명령/옵션과 실제 Typer 파서가 일치하는지 확인한다. 예시는 격리된 자료에서 검증하며 게시·삭제 등의 실제 외부 부작용을 만들지 않는다.
4. 오래된 가이드나 생성 실패를 발견하면 해당 릴리스 제작을 실패시킨다. 런타임에서 사용자 작업을 막는 새 승인 검사로 만들지 않는다.
5. CLI 배포본과 생성된 가이드를 같은 버전의 패키지로 묶는다.

설치·업데이트 스크립트는 해당 패키지의 가이드 본문을 하네스가 읽는 **Neurath 관리 프롬프트 영역**에 삽입·갱신합니다. 명령 위치 등 설치 환경의 값만 치환하고 의미를 다시 생성하지 않습니다. 가이드 파일의 위치만 알려 주는 것으로 사전 제공을 대신하지 않습니다. 기존 사용자 지침·프로젝트 스킬·다른 확장의 영역은 보존하고 같은 버전 재설치는 내용을 중복 추가하지 않습니다. 실행 파일과 가이드의 전환 실패 시 두 항목이 대응하는 기존 조합으로 복구합니다.

새 세션에는 이 가이드를 미리 제공합니다. 진행 중인 세션에서 업데이트했다면 설치 성공 응답으로 바뀐 버전/호출법과 갱신 가이드를 제공하거나 실제로 다시 읽게 합니다. 파일만 갱신한 것을 현재 대화에 반영됐다는 증거로 삼지 않습니다. 매 호출마다 전체 매뉴얼을 다시 주입하지 않으며, 안내 실패로 같은 모델 턴을 반복 생성하지 않습니다.

릴리스 시점에 가이드를 생성하고 해당 릴리스의 설치·업데이트 때 적용합니다. 릴리스 게시 자체가 모든 사용자의 설치를 원격 변경하는 것은 아닙니다. 가이드 버전은 대응 확인과 진단용이며 해시·서명·인간 승인 증명이나 사용자 재입력 요구를 추가하지 않습니다.

스킬은 절차와 판단 기준을 유지하고, 생성 프롬프트는 실제 CLI 호출법을 담당합니다. CLI 변경을 이유로 새로운 사용자용 스킬이나 MCP 어댑터를 만들지 않습니다.

Typer가 제공하는 명령/도움말 정의를 입력으로 Neurath의 릴리스 스크립트가 가이드 프롬프트를 생성합니다. 프롬프트 생성·패키징·설치는 Typer의 내장 기능으로 가정하지 않고 Neurath 자동화로 구현합니다. 명령 정의를 읽거나 도움말을 생성하는 것만으로 실제 업무를 실행하지 않습니다.

## 8. Enclave와 훅의 역할

에이전트는 `memory update`로 현재 사실·가설·판단과 근거를 저장하고 `context show`로 조회합니다. 생성된 CLI 가이드는 보존할 맥락과 호출법을 안내합니다. 압축 뒤 자동 적재와 실패 처리는 [Enclave 복원](architecture.md#5-enclave기억graphifypull)의 훅 경로가 담당합니다.
