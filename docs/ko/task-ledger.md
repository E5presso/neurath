# 태스크 원장 연결

새 원장은 `transport.core_requests.build_task_ledger(path)`로 구성하며 `build_core(path)`와 같은 사용자 단위 DB를 사용합니다. 명시적 초기화가 core 스키마 `core_0001`을 `core_0002`로 이전합니다. 일반 요청은 저장소를 초기화하거나 원본 legacy DB를 이전하지 않습니다.

- `record_source`는 원문·참조·작성자·선택적인 상위 출처를 보존합니다. `request`와 `correction`은 작업을 정의할 수 있고 `question`과 회상 `context`는 새 작업을 만들지 않습니다. 발신 맥락은 인간 인증 장치가 아닙니다. 같은 프로젝트의 기존 출처를 다른 세션에서도 재사용합니다.
- `create_task`는 pending 작업을 만듭니다. `revise_task`는 예상 개정을 검사하고 지정 작업의 정의 이력을 추가합니다. 취소 정정은 작업을 invalidated로 바꿀 수 있습니다. 이전 정의·출처·시도 결과는 `history`와 `get_source`로 계속 조회합니다.
- `start_task`는 의존성을 확인하고 `(task, attempt)`를 반환합니다. 실패 재시도는 같은 작업에 새 시도를 연결합니다. 외부 대기 후 재개는 미종결 시도를 재사용하므로 외부 동작을 다시 제출하지 않습니다.
- `report_result`는 관찰된 제출·성공·실패·부분 결과를 산출물·명령·검토 참조와 저장합니다. 제출은 작업을 active로 유지합니다. 실패·부분 결과에는 남은 작업이나 구체적 장애가 필요하며 같은 작업을 재시도할 수 있습니다. 종결된 시도는 다시 확정할 수 없습니다. 옛 정의의 결과는 보존하되 정정·취소된 작업을 완료시키지 않습니다.
- `add_dependency`는 프로젝트를 넘는 참조와 순환을 거절합니다. `wait_for_external`에는 대상·관찰 근거·해소 조건이 필요하고 `resolve_external`에는 해소 관찰이 필요합니다. 이 API는 호출자가 관찰한 조건을 기록하며 원격 사실 자체를 독립적으로 증명하지 않습니다. 독립 작업은 계속 실행 가능합니다. 감시·알림은 후속 감시 어댑터의 책임입니다.
- `list_tasks(project_id, session_id)`는 전체 원장과 `ready_ids`, 같은 상태에서 생성한 `todo` 표시를 반환합니다. `all_terminal`에는 실패·무효가 포함되며 `all_successful`은 성공만 인정합니다. 빈 목록은 두 조건을 모두 만족합니다. 이 값 자체가 전체 Stop 구현은 아닙니다. TODO 표시 실패는 작업 결과를 바꾸지 않습니다.

원장은 참조 문자열만으로 산출물의 의미를 검증할 수 없습니다. 호스트 어댑터가 실제 실행 결과를 전달하고, phase runner가 평가를 포함한 선택 절차의 완료를 확인한 뒤 최종 결과를 반영해야 합니다. Runner·훅·평가자·CLI 연결은 별도 구현 티켓이며 이 API는 공개 명령이나 자동 폴링을 추가하지 않습니다.
