# Neurath 전면 재설계 명세

[문서 안내](index.md) · [구조](architecture.md) · [요구사항 검증](acceptance.md) · [English](../en/specification.md)

**2026-10-13 재작성한 설계. 현재 배포된 0.3.1의 동작 설명이나 구현 완료 보고가 아닙니다.** 이전 초안에 기능을 덧붙이는 대신 전체 기능과 실행 흐름을 기준으로 다시 정의합니다.

## 1. 목적과 기준

Neurath의 목적은 사용자의 지시를 확대해석한 자의적 과잉행동과 축소해석한 행동누락을 막고, 실제 수행을 회고해 스스로 개선하는 것입니다. 긴 실행·컨텍스트 압축·재개·위임 중에도 같은 의도를 유지해야 합니다.

사용자 원문이 기준이고 태스크·절차·기억·검사는 수단입니다. 필요한 세부 판단은 에이전트가 수행하지만 사용자 목표를 새로 만들거나 시킨 일을 줄일 수 없습니다. 이전 기록이나 에이전트의 해석이 반복됐다고 새 사용자 지시가 되지 않습니다. 하네스의 오류를 사용자의 추가 입력 의무로 바꾸지 않습니다.

**기존 하네스의 실행·기억·협업 기능을 이어갑니다.** TODO, 중단 방지 훅, phase runner, enclave, 기억과 인계, 협업, Newsroom, provider, 스킬·리뷰·검증, 설치·업데이트·마무리가 모두 범위에 있습니다. 기존 코드·실패한 제약은 복제하지 않습니다. 기능을 조용히 삭제하거나 수동 작업으로 돌려주는 것은 재작성 완료가 아닙니다.

Neurath는 **하나의 코어와 세 가지 에이전트 접점**으로 구성합니다.

| 접점 | 역할 | 코어와의 관계 |
| --- | --- | --- |
| Skill + rules 프롬프트 | 에이전트가 Neurath 위에서 작업한다는 사실, 수행 절차, CLI 사용법을 인지하도록 하는 소프트 하네스 | 릴리스에서 생성한 CLI 가이드를 설치하고 필요한 상태 관리 행동을 안내 |
| Hook | 도구 실행·종료 등 호스트 경계에서 다음 동작을 제약하고, 압축 뒤 맥락을 자동 복원하는 강제 집행 경로 | 실제 사건과 코어의 현재 상태를 대조한 판정을 호스트가 지원하는 동작으로 집행 |
| Typer CLI | 태스크·phase·메모리·enclave·뉴스룸·위임·메시지의 명시적 조회와 상태 변경 | 에이전트의 호출을 같은 코어 유스케이스로 전달 |

**코어는 SQLite 기반의 구조화된 메모리 영속성 계층이자 상태머신이며, 메시지·협업 인프라입니다.** 원문·작업·시도·현재 사실·메시지·배정·결과를 저장하고, 그 상태와 사건에 따라 허용되는 전이·다음 행동·대기를 판단합니다. 메시지의 저장·전달·읽기·배정·수락·결과를 연결하여 협업 과정을 관리합니다. 이 세 역할을 별도 서비스나 중복 원장으로 나누지 않습니다.

프롬프트는 행동을 안내하고, CLI는 코어와 통신하며, 훅은 코어의 판단을 실제 호스트 경계에서 집행합니다. 상태와 전이 규칙의 기준은 코어입니다. 훅에 별도 태스크 원장이나 독립적인 완료 규칙을 복제하지 않습니다. SQLite에 기록한 것만으로 실제 도구 실행·중단·메시지 전달이 일어난 것은 아니므로 호스트 어댑터가 실제 동작을 수행하고 결과를 코어에 반영합니다.

### 코어의 요청 처리 모델

**Neurath Core는 stateless service입니다.** Hook과 CLI 호출을 웹 서비스의 request처럼 처리합니다. 요청이 들어오면 필요한 현재 상태를 SQLite에서 조회하고, 해당 유스케이스의 규칙으로 처리한 뒤 필요한 변경을 저장하고 응답합니다.

```text
Hook 또는 CLI 호출 → 요청 처리 → SQLite 상태 조회 → 판단/전이 → 변경 저장 → 응답
```

**저장소는 로컬 사용자 단위 SQLite 하나를 사용합니다.** 같은 사용자의 hook·CLI 요청은 프로젝트나 작업 디렉터리가 달라도 이 DB를 사용하며, 프로젝트·세션의 식별과 관계를 DB 안에서 관리합니다. 프로젝트별·세션별 DB 파일은 만들지 않습니다. 관련 작업·phase·enclave·메시지·배정·결과는 해당 프로젝트/세션 관계로 구분해 조회·변경합니다. DB를 공유한다는 이유로 무관한 프로젝트의 맥락을 자동 주입하지 않으며, 요청한 프로젝트 간 협업은 같은 저장소 안의 명시적인 관계로 처리합니다. **Neurath 프로젝트는 하나의 로컬 Git 저장소를 단위로 합니다.** 주 작업 트리와 그 저장소에 연결된 linked worktree, 저장소 내부 하위 디렉터리는 같은 프로젝트에 속합니다. 같은 원격 주소를 쓰더라도 별도로 clone한 저장소는 다른 프로젝트로 구분합니다. Codex 앱의 프로젝트 묶음이나 호스트별 작업 디렉터리 표시는 이 공통 기준을 대신하지 않습니다. 동일성은 로컬 Git 저장소와 worktree의 관계로 판별하며, 원격 URL 일치만으로 합치지 않습니다. Git이 없는 경우 작업 폴더를 프로젝트 단위로 사용하고, 이후 git init을 해도 기존 프로젝트의 task와 메모리를 이어갑니다. 요청·세션의 프로젝트 지정 방법은 별도로 정합니다.

에이전트·태스크·phase·enclave·메시지·배정 등의 지속 상태는 DB에 있습니다. 다음 요청의 올바른 처리가 이전 요청을 처리한 프로세스의 메모리, 살아 있는 코어 인스턴스, 세션의 계속된 연결에 의존해서는 안 됩니다. 요청 안에서 사용하는 객체와 계산은 가능하지만, 그것이 요청 사이 상태의 기준이 되지 않습니다.

이는 HTTP 서버를 만들라는 뜻도, 코어를 별도 데몬으로 상주시킨다는 뜻도 아닙니다. 프롬프트·훅·CLI의 세 접점은 유지하고, CLI/훅 어댑터가 동일한 stateless 코어 유스케이스를 호출합니다. 에이전트 실행이 끝나더라도 보존할 상태는 DB에 남습니다.

코어의 상태머신은 프로세스 안에 살아 있는 에이전트 객체가 아니라 DB에서 읽은 상태에 적용하는 전이 규칙입니다. 메시지·협업 관리 역시 DB의 배정·전달·수락·결과를 바탕으로 요청별로 처리합니다. 외부 실행이 필요하면 기존 호스트 어댑터를 사용하고 실제 결과를 저장하며, 외부 호출 동안 DB 쓰기 잠금을 유지하지 않습니다. 동시 요청은 기존 트랜잭션·관련 리비전 규칙으로 조정하고, 프로세스 내 메모리 잠금만으로 해결했다고 가정하지 않습니다.

## 2. 구성요소와 책임

| 구성 | 담당하는 질문 | 보존할 기능 |
| --- | --- | --- |
| 태스크 원장·TODO | 사용자가 무엇을 요구했고 무엇이 남았는가? | 원문 연결, 작업·의존 관계·결과, 전체 진행 표시 |
| 스킬·phase runner | 선택한 절차의 어느 단계를 어떻게 수행하는가? | 단계 시작·현재 상태·실제 실행 연결·결과·다음 단계·재시도·재개·종결 |
| 런타임·Stop 훅 | 누가 실행하며 지금 정상 종료해도 되는가? | 세션·턴·자식 관계, 작성 충돌 조정, 성급한 종료 방지, 명시적 중단 |
| Enclave·기억 | 지금 유효한 사실과 과거의 근거는 무엇인가? | 제한된 현재 사실, 관련 이력 회상, 체크포인트, 수신자 주도의 인계 |
| 협업·위임·provider | 누가 어떤 일을 맡았고 실제로 수행했는가? | 피어 발견·메시지·배정·결과·독립 리뷰·다른 호스트 실행 |
| Newsroom | 다른 활성 동료에게 유용한 발견은 무엇인가? | 게시·제목·본문·댓글·정정·이력·열람과 활성 피어 알림 |
| 회고·학습 | 무엇을 고쳤고 다음 수행도 나아졌는가? | 원인·개선·적용 범위·효과·재사용·철회 |
| 유지보수·배포 | 자료와 기능을 보존하면서 적용하고 끝냈는가? | 진단·우회·복구, 설치·릴리스·업데이트·finish-session·공개 보고 |

모든 구성은 필요할 때 연결합니다. 간단한 질문에 워크플로와 독립 리뷰를 강제로 시작하지 않습니다. 반대로 사용자가 선택한 스킬의 phase runner나 요구된 검사를 생략하지 않습니다.

## 3. 요청과 결과

프롬프트와 사용자가 지정한 티켓·명세를 보존하고, 필요한 작업과 결과에 연결합니다. 한 번 받은 지시로 필요한 프로젝트에 일을 맡길 수 있습니다.

사용자 원문과 에이전트의 해석·배정·교정은 발신 맥락으로 구분합니다. 이것은 요구 범위를 잘못 늘리지 않기 위한 해석 기준이며 입력을 인증·거부하는 별도 보안 체계가 아닙니다. 에이전트가 전달한 말이어도 기존 사용자 지시 범위의 위임·수행·교정·보고는 그대로 처리합니다. 인간이 직접 보낸 메시지가 아니라는 이유로 일괄 거절하거나 새 인간 입력을 요구하지 않습니다. 이를 위해 해시·전자서명·부인방지·승인 증명서·별도 동의 원장을 추가하지 않습니다. 보통의 대화 맥락과 기존 요청 참조를 사용하며, 발신 표지가 불완전해도 이미 확인한 지시로 할 수 있는 일은 계속합니다. 실제로 요청 범위를 바꾸는지 불분명해 다음 행동을 결정할 수 없을 때만 그 모호한 부분을 확인합니다.

태스크는 `pending`, `active`, `waiting`, `succeeded`, `failed`, `invalidated`를 구분합니다. 실패한 시도는 보존하고 아직 유효한 요구는 후속 작업이나 구체적인 장애와 연결합니다. 모든 태스크가 종료됐다는 사실과 모든 요구가 성공했다는 사실은 다릅니다. 취소·정정은 실제 사용자 지시에 따라 반영하며 별도 승인 형식으로 다시 말하게 하지 않습니다.

TODO는 같은 원장의 전체 현재 상태를 호스트에 표시합니다. 호스트가 결과 상태를 축약하면 본문에 성공·실패·무효를 구분합니다. 표시가 늦거나 실패했다고 작업 결과가 바뀌지는 않습니다. 지원되지 않는 화면 기능은 명시하고 같은 내용을 대체 표시합니다.

조사·문서·구현·검토에는 그 결과에 맞는 근거를 씁니다. 보고를 보존하면서 확인 수준을 명시하고, 무관한 프로세스 성공으로 의미 판단을 대신하지 않습니다. 검증은 실제 대상·검사·결과에 연결합니다. 대상 변경이나 후속 관련 실패가 있으면 이전 성공의 유효성을 다시 판단합니다.

## 4. Phase runner

Phase runner는 스킬 정의와 특정 실행을 구분합니다. 정의에는 목적, 단계, 필요한 입력, 수행할 작업, 결과 조건, 다음 단계가 들어갑니다. 실행에는 현재 단계와 실제 시도·결과가 남습니다. 정의를 읽거나 모델이 통과했다고 말한 것만으로 단계를 진행하지 않습니다.

실행 가능한 단계의 작업을 실행자 또는 호스트에 연결하고 실제 결과를 받아 진행합니다. 기계적으로 확인 가능한 조건은 코드가, 내용 검토가 필요한 조건은 지정된 검토자가 평가합니다. 수정·검토·재검증의 반복도 같은 실행 안에서 이전 실패와 연결합니다. 중단·재시작 시 끝낸 외부 동작을 무작정 다시 수행하지 않습니다.

실패, 대기, 건너뛰기, 완료를 구분합니다. 필수 단계를 임의로 건너뛰지 않으며 범위가 실제로 바뀌면 해당 단계와 이유를 갱신합니다. 사용자가 선택한 절차의 완료 조건은 유지하되, phase·TODO·체크포인트가 서로 별도의 일반 완료 투표가 되지 않게 합니다. 태스크는 사용자 결과를, runner는 그 결과를 얻는 절차를 관리합니다.

## 5. 정상 종료와 실제 중단

Stop 훅은 해당 실행과 최신 원장을 확인합니다. 수행할 일이 남았는데 정상 완료로 종료하려 하면 남은 작업을 알려 거절합니다. 조회 이후 추가된 작업, 다른 턴의 오래된 Stop, 실패를 성공처럼 표시하는 경우를 구분해야 합니다. 시간 경과·상태 질문·반복된 거절은 완료 근거가 아닙니다.

사용자의 중단, 정당한 외부 입력 대기, 예산 소진, 하네스 장애로 인한 일시 중지는 정상 완료가 아닙니다. 실제로 제어권을 반환하면서 남은 작업·runner·enclave를 보존합니다. 같은 장애를 만난 훅이 무한히 계속 실행을 요구해서는 안 됩니다. 연결 종료는 재개 가능한 작업의 삭제나 영구 종료가 아닙니다.

## 6. Enclave·기억·인계

Enclave는 세션의 현재 목표·정정·확인된 사실·중요한 결정·남은 일을 제한된 크기로 보존하는 현재 맥락입니다. 조회·갱신·삭제와 리비전 비교를 지원합니다. 가정과 사실을 구분하고 근거로 돌아갈 수 있어야 합니다. 과거 회고가 현재 사실을 덮어쓰거나 새로운 요구를 만들어서는 안 됩니다.

프로젝트 기억은 출처가 있는 과거 이력, 체크포인트는 인계 보고, Graphify는 관련 코드·문서 관계를 제공합니다. 압축·재개 후 에이전트는 enclave와 작업 목록을 읽고 필요한 원문을 찾습니다. 요약으로 원문을 대체하지 않습니다.

후속 세션은 이전 세션의 마지막 체크포인트가 없어도 보존된 자료를 찾아 인계를 진행할 수 있습니다. 맥락 조회와 작업·작성 소유권의 이전은 구분합니다. 살아 있는 작성자의 작업을 강제로 빼앗지 않고, 종료·유실이 확인된 실행은 안전하게 재개할 경로를 제공합니다. 옛 자료를 보관했지만 다시 사용할 수 없다면 이전이 끝난 것이 아닙니다.

Enclave는 CLI로 쓰고 압축 후 훅으로 모델 컨텍스트에 자동 적재합니다. 저장과 자동 적재를 에이전트의 기억에 함께 맡기지 않습니다. 훅은 코어의 현재 상태를 읽어 사용합니다.

## 7. 협업·Newsroom·provider

독립 피어, 네이티브 자식, 별도 provider 세션을 구분합니다. 피어 등록·발견, 질문·답장, 인박스·본문 읽기·ACK, 작업 배정·수락·진행·결과·검토·인계를 유지합니다. 기록 저장, 실제 전달, 읽기, 수락, 수행 완료를 구분합니다. 원래 작업의 지시 범위를 전달하며 동료 메시지를 사람의 새 승인으로 해석하지 않습니다.

Newsroom은 프로젝트 내부 발견과 토론 공간입니다. 작성자·근거·개정 이력과 댓글을 보존하고, 활성 동료에게 제목과 식별 정보만 전달합니다. 필요한 본문을 선택해 읽으며 정정이 실제로 영향을 주는 작업에 반영되게 합니다. 대기·종료 세션을 뉴스 때문에 깨우거나 모든 글을 모든 맥락에 주입하지 않습니다.

Provider는 실제 지원 기능·모델·실행 정책을 확인해 계획·실행·상태·취소·복구를 지원합니다. 모델 선택과 실행 권한은 별개이며 지원하지 않는 상속을 몰래 다른 정책으로 대체하지 않습니다. 프로젝트 간 연결은 원래 요청에 필요한 대상만 사용하고, 같은 URL의 별도 클론이나 컴퓨터를 자동 공유하지 않습니다.

## 8. 결과 평가와 회고

태스크/TODO는 수행할 일과 결과를 관리합니다. 종료 훅은 현재 세션의 모든 태스크가 완료됐는지 결정론적으로 확인합니다. `failed`나 `waiting`을 성공으로 간주하지 않으며, 사용자 취소·정당한 대기·장애에 따른 제어권 반환은 정상 완료와 구분합니다.

세션 결과물이 사용자의 본래 의도를 충족하는지는 실행자와 별개의 서브에이전트 또는 다른 provider에게 위탁해 평가합니다. 사용자 원문·최신 정정, 전체 TODO, 실제 산출물과 검증 근거를 함께 제공합니다. TODO에 처음부터 빠진 요구도 원문과 대조합니다. 검토자는 충족 여부와 근거, 미달 항목을 보고하며 직접 작업을 성공 처리하지 않습니다.

결과 평가는 작업 묶음을 마무리하는 스킬의 phase로 수행합니다. 미달 항목은 관련 수행 단계로 돌아가 보완하며, 같은 유효 평가를 재사용하고 평가 작업을 재귀 평가하지 않습니다. 구체적인 전이는 [runner 실행 계약](architecture.md#3-skills와-phase-runner의-실행-계약)에 정의합니다.

확인된 미달 항목은 같은 태스크 목록에 반영해 수행하고 변경된 결과를 재평가합니다. 관련 요청·산출물이 바뀌지 않은 유효한 평가 결과는 재사용합니다. 평가 결과가 없거나 전달에 실패하면 검증 미완료로 보고하며, 이를 기다리는 동안 같은 모델 턴을 반복 생성하지 않습니다. 결정론적 종료 판정과 내용 평가는 같은 작업 상태에 연결하며 별도 승인 원장을 만들지 않습니다.

세션 중 드러난 문제가 있으면 마무리할 때 회고를 한 번 제안합니다. 사용자가 요청하거나 수락하면 제3자에게 회고 평가를 위탁하고, 그 결과를 바탕으로 요청 범위에서 개선·검증·효과 확인·철회를 수행합니다. 회고 제안 자체는 실행 지시가 아니며, 거절·무응답은 원래 작업의 종료를 막지 않습니다. 상세 절차는 [스킬·CLI 명세](interfaces.md)에 따릅니다.

## 9. 비용·장애·유지보수

외부 작업 모니터는 실제 상태 변화에 따라 요청된 후속 일을 이어갑니다. 같은 대기 상태에는 모델을 반복 호출하지 않으며 사용자 요청 없이 반복 자동화를 만들지 않습니다.

SQLite를 SQLAlchemy·Alembic으로 관리하며 기존 DB·미완료 일·원문·과거 소유권을 보존합니다. 설치기는 정확히 소유한 설정 부분만 갱신하고 복구 자료와 이전·재개 검증을 전환에 포함합니다. 읽기·진단에 작성 임대를 요구하지 않습니다. 공식 우회는 하네스 차단을 멈추며 기록 가능한 자료는 유지합니다. 장애를 고친 뒤 실제 동작을 확인해 복원합니다.

릴리스·업데이트·공개 보고·finish-session은 기존 기능으로 유지합니다. 이미 받은 사용자 권한 안에서 수행하고, 필요한 별도 호스트 승인은 정확히 구분합니다. 정상 동작·문서·설치·실제 활성화·작업 마무리는 각각 실제 근거로 보고합니다.

종료·대기 판정, 위임 정정, 결과 불명 재시도, 자료 전환의 구체적인 규칙은 [구조](architecture.md)에 정의합니다. 기능 보존은 [기능 대조표](capability-continuity.md)의 관찰할 결과와 [요구사항 검증](acceptance.md)으로 확인합니다. 문서의 감사 완료와 실제 호스트에서의 구현 검증은 별개입니다.

## 10. 스킬과 CLI 공개 경계

설치된 rules를 기본 진입점으로 삼고 에이전트가 사용자 요청에 적합한 스킬을 선택합니다. 사용자 지정 스킬은 그 지정을 따르며, 단순 대화에는 실행을 강제하지 않습니다. 시작한 스킬의 phase와 결과는 기존 runner가 관리합니다. 상세 조건은 [스킬 시작 명세](interfaces.md)에 따릅니다.

기능은 유지하되 일반 작업을 스킬로 포장하거나 내부 전이를 전부 CLI로 노출하지 않습니다. [공개 목록](interfaces.md)의 **스킬 14개·CLI 명령 20개**를 적용합니다. 커밋·워크트리·이슈/PR 생성은 호스트 도구, 체크포인트 저장은 CLI, 임대·ACK·Stop은 내부 처리입니다. 선택한 프로젝트 전문 스킬은 계속 사용할 수 있습니다. 과거 128개 작업/33개 스킬은 삭제 누락을 찾는 감사 목록이며 새 설치 개수가 아닙니다.

명세 정의(실행 계획 포함)·구현·리뷰·QA처럼 판단과 검증이 반복되는 개발 절차를 제공합니다. 핵심 이름은 define-spec·implement-spec·review-spec으로 통일합니다. 커밋·워크트리 생성 같은 단일 호스트 작업을 제외한다는 이유로 이 절차까지 제거하지 않습니다. CLI 명령 이름은 동사-목적어로 통일합니다.

## 11. CLI 전용 배포와 사전 사용 가이드

Neurath의 공개 실행 경로는 Python + Typer로 구현한 CLI만 제공합니다. MCP 서버·등록·선택적 어댑터는 새 설계에 포함하지 않습니다. 실제 CLI 정의에서 사용 가이드 프롬프트를 자동 생성하고 릴리스 검증 후 같은 배포본에 포함합니다. 설치·업데이트 시 하네스 관리 영역에 가이드 본문을 배치해 에이전트가 호출 전에 사용법을 받게 합니다. 자세한 생성·적용·복구 규칙은 [CLI 명세](interfaces.md)에 따릅니다.
