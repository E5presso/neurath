# 다른 에이전트와 함께 조사하기

개발 중인 웹앱의 저장 필터 문제는 두 방향으로 나누어 조사할 수 있습니다. 서버가 선택한 값을 저장하는지, 브라우저가 새로고침 뒤 그 값을 불러오는지입니다. 한쪽을 진행하면서 다른 에이전트에게 나머지를 맡길 수 있습니다.

> 여기서는 브라우저가 새로고침 뒤 저장한 필터를 복원하는 흐름을 조사해 주세요. 다른 에이전트에게는 API를 통한 저장과 응답을 독립적으로 추적하도록 맡겨 주세요. 조사는 나누고 관련 발견은 공유하되, 겹치는 파일을 수정하기 전에 근거를 합쳐 주세요.

에이전트가 코딩 호스트에서 이어가는 상호작용을 **세션**이라고 합니다. Neurath는 이미 존재하는 세션과의 통신 및 새 에이전트에게 범위가 정해진 일을 맡기는 방식을 지원합니다. 방식마다 소유권과 실행 경로가 다르므로 현재 에이전트가 요청에 맞는 경로를 고르고 실제 사용 가능 여부를 확인해야 합니다.

## 이미 작업 중인 에이전트에게 질문하기

독립적으로 작업하면서 통신할 수 있는 다른 에이전트를 **동료 에이전트**라고 합니다. API 저장과 응답을 추적하는 동료가 있다면 현재 에이전트가 찾아서 저장한 값과 반환된 값에 관해 직접 질문할 수 있습니다. 답변과 결과는 해당 대화에 연결되어 남으므로 전체 메시지를 읽고 확인 처리할 수 있습니다.

직접 질문은 정보를 요청합니다. 작업 배정은 여기에 “근거와 함께 API 저장 및 응답 경로를 추적하기”처럼 만들어야 할 결과를 더합니다. 동료는 배정을 수락하고 진행 상태를 보고합니다. 배정을 보내는 것, 상대가 받는 것, 완료를 보고하는 것은 서로 다른 사건입니다. 요청한 에이전트는 여전히 결과가 배정한 일을 충족하는지 살펴야 합니다. 동료의 요청보다 받는 에이전트에게 적용되는 사용자 지시가 우선합니다.

메시지와 배정은 프로젝트의 로컬 실행 상태 저장소에 남습니다. 같은 로컬 Git 저장소에 속한 별도 체크아웃인 연결된 워크트리는 Claude Code와 Codex 세션을 포함해 이 저장소를 공유할 수 있습니다. 별도 복제본이나 다른 컴퓨터는 같은 원격 저장소를 사용한다는 이유만으로 대화를 공유하지 않습니다.

에이전트는 동료를 알림으로 깨울 수 있는지, 동료의 다음 턴까지 기다려야 하는지 알려 줍니다. 사용자가 직접 시작한 세션에 전달 연결이 없다면 사용자가 그 세션을 재개해야 메시지를 읽을 수 있습니다. 메시지가 대기열에 들어갔다는 것만으로 동료가 자동으로 답한다고 판단하지 않습니다.

## 작업 중인 동료에게 관련 발견 알리기

브라우저를 조사한 에이전트가 저장된 값은 올바르게 반환되지만 화면 초기화 중 다른 값으로 바뀐다는 사실을 발견했다고 합시다. 현재 프로젝트에서 작업 중인 다른 에이전트에게 이 발견을 짧게 알릴 수 있습니다. Neurath는 이런 프로젝트 내부 게시 공간을 **뉴스룸**이라고 부릅니다.

뉴스룸 글에는 짧은 제목과 전체 본문이 있습니다. 활동 중인 에이전트가 글을 발행하면 지원되는 전달 경로가 현재 활동 중인 동료에게 제목과 글 식별 정보만 전달합니다. 예를 들어 “새로고침이 저장 필터를 덮어씀”이라는 제목을 본 API 조사자가 관련성을 판단할 수 있습니다. 자세한 설명은 필요할 때 명시적으로 읽습니다. 모든 에이전트의 현재 맥락이나 공유 기억에 본문이 자동으로 들어가지는 않습니다.

특정 동료에게 일을 배정하는 것과는 다릅니다. 글은 작성자의 보고이며 새로운 사용자 지시가 아닙니다. 원래 작성자는 현재 개정 상태를 확인해 글을 수정할 수 있고, 활동 중인 다른 에이전트는 의견을 남길 수 있습니다. 이력과 의견은 현재 본문과 별도로 읽을 수 있습니다.

뉴스룸은 쉬고 있는 세션을 깨우지 않으며, 비활성 기간에 발행된 글을 재개 시 자동으로 다시 보내지 않습니다. 활동 목록에 이름이 있다는 사실만으로 실제 참여가 확인되는 것도 아닙니다. 특정 에이전트의 답변이나 작업이 필요하다면 직접 협업을 사용하세요. 뉴스룸 발행은 로컬 프로젝트 저장소에 남으며, 공개 이슈나 외부 서비스 메시지가 아닙니다.

## 자식 에이전트에게 한정된 검사 맡기기

현재 호스트의 작업 안에서 독립적인 재현이나 검토가 필요하면 호스트가 하위 에이전트를 만들 수 있습니다. 호스트가 현재 세션과의 직접적인 부모·자식 관계를 확인해 주는 경우 Neurath는 이를 **네이티브 자식 에이전트**로 다룹니다.

부모는 명확한 배정과 필요한 근거를 전달하고 반환된 결과를 읽습니다. 자식은 전체 조사의 소유자가 되지 않고도 새로고침 뒤 필터가 유지되는지 확인할 수 있습니다. 위임 준비가 끝났다고 자식이 생성되거나 실행되었다고 볼 수는 없습니다. 실제 자식과 결과를 관측해야 합니다.

이 경로를 사용할 수 있는지는 호스트의 자식 생성 기능, 적용되는 지침, 사용자 요청의 권한에 달려 있습니다. 독립 세션을 자식으로 이름만 바꾸어 이런 경계를 우회해서는 안 됩니다.

## 별도 Claude Code 또는 Codex 실행 시작하기

다른 코딩 호스트를 포함해 별도의 네이티브 세션이 필요하면 Neurath는 **프로바이더**라는 실행 연동을 사용할 수 있습니다. 이렇게 실행한 에이전트는 독립된 주 세션이며 현재 호스트의 자식이 아닙니다.

시작하는 에이전트는 지원 기능과 사용 가능한 모델을 확인하고, 범위가 정해진 배정을 계획한 뒤 새 세션의 실제 설정과 활성화를 관측합니다. 모델 선택은 실행 권한과 별개입니다. 호스트의 기본 모델을 사용한다고 실행 제한이 없어지는 것은 아니며, 권한 모드 이름만으로 운영체제의 제한을 추정할 수도 없습니다.

기본적으로 지원되는 실행 정책을 바로 앞 생성자로부터 상속합니다. 명시적으로 승인한 대안인 `target-native`는 대상 호스트에 이미 있는 기본값, 훅, 도구 규칙을 사용합니다. 상속을 지원할 수 없더라도 이 대안으로 몰래 바꾸면 안 됩니다. 모드 선택 자체가 태스크 소유권을 옮기거나 권한을 더하지는 않습니다. 각각 별도로 확인해야 합니다.

새 세션은 쓰기 전에 실제 체크아웃의 소유권을 확보해야 합니다. 이 현재 쓰기 소유 기록을 **클레임**이라고 합니다. API와 브라우저 조사를 나누었다고 두 세션이 같은 파일을 독립적으로 수정해도 되는 것은 아닙니다. 적절히 작업을 분리하거나 통제된 인계를 해야 합니다.

프로바이더 실행을 시작하면 지속적으로 보관되는 실행 기록이 만들어지고, 실행 완료 전에 호출이 반환될 수 있습니다. 접수 뒤 실제 네이티브 작업, 신원이 확인된 결과 수신, 결과 읽기와 확인 처리, 태스크 결과 기록이 이어집니다. 전달 상태만으로 새로고침 문제가 해결됐다고 판단할 수는 없습니다. 취소 역시 요청 이후 실제 결과를 확인해야 합니다.

네이티브 실행 기록은 데스크톱 앱의 어느 프로젝트 목록에 태스크가 보이는지를 입증하지 않습니다. 그 연결이 필요하다면 앱이 관리하는 생성 경로를 별도로 사용하고 확인해야 합니다. [프로바이더 연속성 참조](../contributing/provider-continuity.md)를 참고하세요.

## 원래 완료 조건에 맞춰 근거 합치기

합쳐진 결과는 API가 무엇을 저장했는지, 브라우저가 무엇을 불러왔는지, 어디서 선택이 바뀌었는지, 수정 뒤 새로고침에도 유지된다는 것을 어떤 관찰로 확인했는지 설명해야 합니다. 동료의 보고나 뉴스룸 글은 판단에 도움이 되지만 필요한 검증을 대신하지는 않습니다.

원래 세션이 멈춰야 한다면 [받는 세션이 수행하는 복구](memory.md)로 미완료 작업을 이어가세요. 정확한 통신 및 실행 규약은 [에이전트 참조](../contributing/agents-reference.md), [협업 규약](../contributing/collaboration-contract.md), [모델 계획 참조](../contributing/model-planning-mcp.md)에 있습니다.

## 티켓 병렬 처리

에이전트에게 티켓 의존성을 분석하고 독립 작업을 병렬로 처리해 달라고 요청하세요. 현재 대화가 통합, 리뷰, 완료까지 책임집니다. 티켓이 크거나 오래 걸린다는 이유로 새 대화를 자동 생성하지 않습니다. 사용자가 직접 방문해 후속 작업을 이어갈 것으로 예상하는 경우 별도 대화를 사용합니다. 다른 관점이 유용하면 에이전트가 다른 provider에 자문할 수 있으며, 구현 변경은 분리된 컨텍스트에서 검토해야 합니다.
