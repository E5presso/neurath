# 프로젝트에서 올바른 작업의 기준 알려 주기

저장한 필터가 사라지는 문제를 조사할 때는 그럴듯한 코드 수정만으로 충분하지 않습니다. 에이전트는 저장된 설정을 설명하는 문서가 어디에 있는지, 저장소를 어떻게 검사하는지, 어떤 기존 동작을 유지해야 하는지 알아야 합니다.

> 이 저장소의 기존 요구사항, 설계 결정, 검증 절차를 Neurath에 연결해 주세요. 저장 필터 문제를 고칠 때 그 검사를 사용하고 현재 화면은 유지해 주세요. 검증됐다고 판단하기 전에 빠진 기준이 있으면 알려 주세요.

Neurath는 공통 설치 구성을 **프로필**이라고 부릅니다. 제공되는 프로필은 `generic`입니다. 애플리케이션 프레임워크를 선택하거나 다른 프로젝트의 관례를 가져오지 않고 공통 에이전트 지원을 제공합니다. 이 조사의 화면 쪽과 서버 쪽을 위해 서로 다른 프로필을 고를 필요는 없습니다.

## 이미 있는 기준 연결하기

에이전트는 필요한 문서 역할을 저장소의 기존 문서에 연결합니다. 예를 들어 제품 요구사항에는 필터가 사용자별로 저장되는지, 설계 결정에는 설정을 어디에 보관하는지가 적혀 있을 수 있습니다. 문서 역할을 연결했다고 해서 Neurath가 그 결정을 새로 만드는 것은 아닙니다.

프로젝트에서 이미 사용하는 검사도 실행 위치와 성공 판정 방법을 포함해 등록합니다. 이후 검증이 정해진 프로젝트 기준을 사용하도록 하기 위해서입니다. 검사가 통과했다고 브라우저 새로고침까지 검증된 것은 아닙니다. 에이전트는 사용자가 요청한 동작을 입증할 근거를 별도로 확인해야 합니다.

이 연결은 프로젝트의 로컬 Neurath 설정에 저장됩니다. 사용자가 수정한 연결은 업데이트나 제거에서도 보존됩니다. 도메인별 규칙은 대상 저장소의 지침이 담당합니다. Neurath가 배포하는 공통 지원과 애플리케이션의 관례는 관리 주체가 다릅니다.

## 방법이 바뀌어도 완료 기준 유지하기

이 조사에서는 필터가 사라지는 현상을 재현하고, 원인을 찾아 수정하고, 기존 화면을 유지하면서 새로고침 뒤에도 저장한 선택이 남는지 보여 주어야 합니다. 요청한 일과 이런 확인 가능한 완료 조건을 함께 기록한 단위가 **태스크**입니다. 호스트의 TODO 표시는 이 태스크 기록을 반영합니다.

API 검사가 통과해도 브라우저에서 선택이 사라진다면 태스크는 아직 끝나지 않았습니다. 시도가 실패하면 다음 방법을 바꿀 수 있지만, 원래 요청이 취소되는 것은 아닙니다. 지원되는 호스트 이벤트는 조사가 진행되는 동안 현재 작업 중인 주 에이전트에게 요구사항과 미완료 작업을 다시 알려 줍니다. 이 알림은 독립적인 백그라운드 타이머로 보내는 것이 아니라 조건을 충족한 네이티브 활동 이벤트에서 전달됩니다. 판단에 필요한 맥락을 제공하며, 수정이 옳은지 판정하거나 새 권한을 부여하지는 않습니다.

## 프로젝트가 바뀌면 연결도 갱신하기

문서 위치나 검사 절차가 바뀌면 에이전트에게 연결 갱신을 요청하세요. 검사가 빠져 있다면 임의의 검사로 대체하지 말고 부족한 부분으로 명시해야 합니다. 등록된 검증 기준이 바뀌면 이전에 학습한 환경 수정 방법의 유효성에도 영향을 줍니다. 이 관계는 [기억과 학습](memory.md)에서 설명합니다.

다음으로 [필요한 작업을 요청](skills.md)하세요. 설정의 구체적인 입력은 [설정 참조](../contributing/setup-reference.md), 목표와 완료 조건을 기록하는 방법은 [태스크 참조](../contributing/task-todo-contract.md)에서 다룹니다.
