# 목적에 맞게 작업 요청하기

[English](../../en/usage/skills.md)

필요한 일을 자연어로 설명하면 에이전트가 적절한 스킬을 선택하고 프로젝트 지침과 검사 방법을 적용합니다. 아래 공개 스킬 이름은 작업 방식을 구분하기 위한 것으로, 명령처럼 외우거나 직접 호출할 필요는 없습니다. 설치할 때 이름 충돌을 피하려고 접두사를 붙일 수 있습니다.

## 변경 전에 동작과 문제 파악하기

| 요청할 작업 | 스킬 | 확인할 결과 |
| --- | --- | --- |
| 현재 구현과 테스트를 근거로 이 부분이 어떻게 동작하는지 설명해 줘 | `explain-code` | 소스에 근거한 동작 설명과 한계 |
| 이 결함을 재현하고 원인을 좁혀 줘 | `debug` | 재현 가능한 실패, 원인 근거, 수정 범위 |
| 이 변경에 결함이 있는지 검토해 줘 | `review-code` | 살펴본 변경과 연결된 근거 있는 발견 사항 |
| 구현 전에 요구사항을 검토해 줘 | `review-spec` | 작업 기준으로 삼기 전에 해소해야 할 누락과 충돌 |


## 계획하고 승인된 작업 구현하기

| 요청할 작업 | 스킬 | 확인할 결과 |
| --- | --- | --- |
| 이 제품 목표를 구체적인 결정과 관리할 수 있는 작업으로 나눠 줘 | `plan` | 제품 선택 사항과 문서·이슈 단위의 작업 분해 |
| 승인한 작업 항목을 생성해 줘 | `create-issue` | 허용된 이슈와 명시된 작업 범위 |
| 이 승인된 이슈를 구현해 줘 | `implement-issue` | 해당 이슈의 요청 동작과 실제 검사 결과 |
| 명시한 여러 이슈의 진행을 조정해 줘 | `autopilot` | 요청한 이슈 집합의 진행 상황과 남은 작업 |
| 이 이슈를 위한 격리된 작업 공간을 준비해 줘 | `create-worktree` | 해당 이슈용 워크트리와 필요한 소유권 상태 |

이슈 하나의 구현 요청이 여러 이슈의 자동 진행으로 확대되지는 않습니다. 병렬 작업과 제공자 선택은 [에이전트와 공동 작업](agents.md)에 설명합니다.

## 디자인에서 배포된 결과까지 확인하기

| 요청할 작업 | 스킬 | 확인할 결과 |
| --- | --- | --- |
| 화면 디자인을 탐색하고 정확한 캔버스를 선택하게 해 줘 | `design-ui` | 디자인 후보와 구체적인 캔버스 선택 |
| 저장소의 디자인 토큰과 컴포넌트 연결 정보를 캔버스에 반영해 줘 | `sync-design` | 저장소의 디자인 정의와 맞춘 캔버스 정보 |
| 승인한 이 디자인 노드를 그대로 구현해 줘 | `implement-ui` | 선택한 노드에 대응하는 구현 |
| 승인한 디자인과 실행 중인 화면을 비교해 줘 | `review-ui` | 사용자가 판단할 차이점과 실행 근거 |
| 배포된 화면, API, 저장 결과를 검증해 줘 | `qa` | 요청한 배포 흐름 전체에서 관찰한 동작 |

예를 들어 배포된 화면에서 변경을 저장했을 때 API 결과가 기대와 맞고 새로고침 후에도 값이 유지되는지 확인하도록 요청할 수 있습니다. 화면 이미지 하나로 데이터 저장까지 확인됐다고 볼 수는 없습니다. 승인한 캔버스나 노드를 특정하면 구현이 사용자의 선택을 기준으로 진행됩니다.

## 변경 저장·검토·전달하기

| 요청할 작업 | 스킬 | 확인할 결과 |
| --- | --- | --- |
| 되돌릴 수 있는 작업 중 체크포인트를 저장해 줘 | `checkpoint` | 복구 가능한 중간 저장과 인계 상태 |
| 허용하고 검증한 변경을 커밋해 줘 | `commit` | 승인 범위를 담은 로컬 커밋 |
| 이 변경을 푸시하고 풀 리퀘스트를 만들어 줘 | `create-pr` | 허용된 원격 변경과 PR |
| 이 PR에 대해 로컬에서 검증한 리뷰를 게시해 줘 | `review-pr` | 실제로 검토한 정확한 PR 헤드에 연결된 공개 리뷰 |
| 이 리뷰 의견을 판단하고 응답해 줘 | `pr-feedback` | 의견별 처리 판단과 허용된 응답 |
| 이 풀 리퀘스트의 변화를 지켜봐 줘 | `watch-pr` | 요청과 관련해 관찰한 PR 변화 |
| 이슈나 프로젝트 상태를 갱신해 줘 | `update-status` | 요청한 메타데이터 변경 |
| 지정한 전달 절차를 수행하고 세션을 마무리해 줘 | `finish-session` | 요청 범위에서 허용된 커밋·푸시·그래프 갱신·소유권 해제 |

체크포인트는 되돌릴 수 있는 저장과 다시 이어갈 지점을 남깁니다. 전달할 준비가 됐다면 로컬 커밋, 푸시, 풀 리퀘스트 중 원하는 범위를 지정해 주세요. 결과가 의도한 대상까지 도달했는지 확인할 수 있습니다.

## 문서·의존성·하네스 유지관리하기

| 요청할 작업 | 스킬 | 확인할 결과 |
| --- | --- | --- |
| 어떤 문서를 갱신해야 하는지 정리해 줘 | `sync-docs` | 범위에 맞게 배정한 문서 작업 |
| 개발자 문서를 갱신해 줘 | `dev-docs` | 개발자가 사용하는 동작과 절차의 문서화 |
| 승인되고 구현된 사용자 동작을 문서화해 줘 | `user-docs` | 구현된 기능과 일치하는 사용자 안내 |
| 의존성의 보안·라이선스·최신성·불일치를 점검해 줘 | `audit-deps` | 요청한 의존성 위험에 관한 발견 사항 |
| 변경 범위를 통제하며 의존성을 업데이트하고 검사해 줘 | `update-deps` | 선택한 업데이트와 검증 결과 |
| 실패 상황에서 하네스가 규칙을 집행하는지 확인해 줘 | `test-harness` | 실제 집행 결과와 확인되지 않은 부분 |
| 기능을 유지하면서 하네스가 주입하는 지침을 줄여 줘 | `optimize-harness` | 줄어든 프롬프트 내용과 동작 유지 근거 |
| 반복되는 비공개 경험을 프로젝트 규칙으로 삼을지 검토해 줘 | `memory-to-rules` | 프로젝트 사용 승인을 위해 검토한 규칙안 |
| 코드와 문서 사이의 관계를 살펴봐 줘 | `graphify` | 프로젝트 자료에 근거한 관계 그래프나 설명 |

반복되는 경험을 프로젝트 규칙으로 제안하기 전에 [프로젝트 메모리](memory.md)에서 그 근거를 확인할 수 있습니다.

이 안내에는 현재 공개 스킬 31개를 담았습니다. `create-package`, `local-dev`, `onboard`, `refactor-code`, `impact-analysis`, `improve-coverage`, `property-test`는 더 이상 독립 스킬 이름으로 사용하지 않습니다. 원하는 결과를 설명하면 에이전트가 현재 작업 방식으로 처리할 수 있습니다.

작업 추적과 완료 근거는 [Neurath로 작업하기](index.md), 스킬이 사용할 문서와 검사 연결은 [프로젝트 설정](profiles.md)을 참고하세요.
